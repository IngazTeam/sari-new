# تاريخ نتائج التحويل المبلّغ عنها عبر بيان وواجهة API

استكمال B037 وB040 وB041 وB065 فوق `864ad7ad`، في 28 سبتمبر 2026.

## المشكلة والنتيجة

كان سجل التحويلات يحتفظ بالحالة الأخيرة فقط، دون تاريخ يوضح مَن أبلغ عنها ومتى تغيرت. وكانت صلاحية مفتاح API تُفحص في بداية الطلب دون إعادة تثبيتها داخل معاملة الحفظ. كذلك كان الحقل `created` يعتمد على عدد الصفوف المتأثرة بعملية upsert؛ إعداد `FOUND_ROWS` في MySQL قد يعيد القيمة 1 لطلب مكرر، فيظهر الرد 201 بدل 200.

أصبح كل سجل يحتفظ بأول ملاحظة لكل حالة من `pending` و`completed` و`cancelled`، مع مصدرها وتوقيتها. الحالة وسلسلة تاريخها تحفظان ذريًا، ويُعاد التحقق من صلاحية النشاط والمالك ومفتاح API وصلاحياته وانتهائه وتطابقه مع المفتاح المصادق عليه. تُحدد `created` من وجود الهوية المحفوظة تحت قفل النشاط، فتُنشأ هوية واحدة ويعود تكرارها بالرد 200.

هذه حالات أبلغ عنها المتصل أو الكود الداخلي. لا يثبت وصف `payment/completed` تحصيلًا لدى بوابة دفع، ولا يربط العملية تلقائيًا باتفاق أو محادثة أو أثر سياسة مبيعات. العقد الحالي لا يتضمن العملة أو هوية بوابة مالية موثقة؛ يبقى اعتماد التحصيل والتعلم المالي خارج هذا المسار.

## مصدر كل ملاحظة

- `api_key_report`: بلاغ عبر مفتاح API أعيد التحقق منه في SQL وقت الحفظ. تحفظ هوية المفتاح، ولا يحفظ سره أو بصمته المستخدمة للمصادقة في التاريخ.
- `internal_unverified`: استدعاء داخلي قائم، ومنه تسجيل عمليات Byaan الحية. هذا الوصف يحافظ على عمل المسار الحالي دون منح استجابته تصنيف تحقق مالي أو عقد مزوّد لم يُفحص.
- السجلات السابقة للترحيل تظهر `legacy_unrecorded`. لا تُملأ لها تواريخ أو مصادر بالتخمين. بلاغ جديد مطابق لهوية قديمة قابلة للإعادة يسجل وقت ملاحظته الحالي، لا وقت الإنشاء القديم.

يحافظ تكرار الحالة نفسها على الملاحظة الأولى وهوية صاحبها. إعادة إرسال تسجيل داخلي عبر مفتاح API لا تحول مصدره بأثر رجعي إلى بلاغ ذلك المفتاح. بعد تبديل المفتاح أو حذفه تبقى الملاحظات القديمة قابلة للقراءة بواسطة مفتاح حالي مصرح له، دون الحاجة لإعادة تفعيل المفتاح السابق.

## واجهة القراءة والصلاحيات

أضيف `GET /api/v1/conversions/:id/history` بصلاحية `conversions:read`. صلاحية الكتابة وحدها لا تسمح بقراءة التاريخ، وصلاحية القراءة لا تسمح بتغيير الحالة. هوية النشاط والمفتاح مشتقتان من المصادقة؛ المدخلات العامة لا تختار مصدر البلاغ أو هوية كاتبه.

يُرجع المسار الحالة الحالية والملاحظات وتوقيتاتها ومصادرها، مع `paymentEvidence='not_verified'` و`attribution='not_recorded'`. لا يُرجع الهاتف أو الاسم أو مفتاح API أو بصمته. معرّف تحويل يخص نشاطًا آخر يعامل كمعرّف غير موجود. التاريخ غير المتسق يتوقف للمراجعة بدل إصلاحه أو استكماله بالتخمين.

تبقى قراءة قائمة التحويلات وملخصاتها القائمة متوافقة مع العقد السابق؛ الأرقام فيها مبنية على البلاغات المسجلة. لا تتغير إلى حقائق مالية موثقة بمجرد إضافة التاريخ.

## الذرية والتزامن وسلامة التاريخ

أضيف جدول `api_conversion_observations` وبصمة نهاية التاريخ `sari_conversions.history_digest`. لكل حالة ملاحظة واحدة، وترتبط كل ملاحظة ببصمة سابقتها وبالبيانات الثابتة للعملية وهوية النشاط. الحد الأقصى ثلاث ملاحظات؛ الإلغاء نهائي وفق عقد الانتقال القائم.

التحقق يقارن السلسلة بالحالة الحالية وبصمة نهايتها. حذف البداية أو التاريخ كله، أو تغيير المصدر أو البيانات أو الحالة خارج العقد، يمنع القراءة والتعديل. هذه بصمات لاكتشاف عدم الاتساق، وليست حماية من مسؤول قاعدة بيانات يستطيع إعادة كتابة السجل والأدلة كلها.

فشل حفظ الملاحظة أو تحديث نهاية التاريخ يعيد المعاملة كلها، بما فيها أول إنشاء للسجل. إذا نجح commit وضاع تأكيده، تُتلف وصلة قاعدة البيانات الملتبسة وتقرأ إعادة المحاولة النتيجة المحفوظة دون حدث مكرر. الإلغاء أو فقدان الصلاحية لا يجيزان إنشاء حقيقة جديدة. لا تُنفذ اتصالات مزوّد أو رسائل واتساب ضمن هذا المسار.

## الترحيل والتشغيل

الترحيل `0147_api_conversion_history` إضافي: عمود اختياري وجدول جديد، دون حذف أو تعديل بيانات الأعمال القديمة. فُحص إنشاؤه على قاعدة جديدة، وترقية الإصدار السابق، وحالة اكتمال DDL قبل تسجيل الترحيل، وإعادة تشغيله. فُحصت قيود الحالة والمصدر والبصمات ومنع التكرار.

تتحقق جاهزية التطبيق من المخطط الجديد قبل التشغيل. يستخدم النشر مسار التحديث المعتاد الذي يجري الترحيلات قبل تفعيل الإصدار. إذا كتب إصدار قديم حالة تخالف تاريخًا أُنشئ بالإصدار الجديد، يتوقف السجل للمراجعة؛ لا يُخترع له انتقال مفقود. يبقى تمرين ذلك على ملف السيرفر الفعلي من بوابات الاعتماد التشغيلي.

## التحقق

نجح **2206 اختبارًا**: 120 لأدوات النشر، و1103 للوحدات والأمن في 39 ملفًا، و983 على MySQL في 17 ملفًا، دون فشل أو تخطٍّ. اجتازت الحزمة المستهدفة 86 حالة، منها 38 حالة SQL وREST للتاريخ الجديد.

نجح **168 سيناريو متصفح** لانحدار الواجهات القائمة بالعربية والإنجليزية والهاتف وسطح المكتب، مع نجاح الأنواع والمخطط والبناء والترحيلات الـ148. فُحصت ثلاثة مسارات للترحيل: تاريخ التحويل الجديد، وسلال سلة، وسجل مراجعتها، على قاعدة جديدة وترقية وإعادة تشغيل. فحص الترجمة: 7996 استدعاءً و311 مفتاحًا ديناميكيًا، دون نقص أو أخطاء. [نتائج الفحص وبصمات المصدر](./audits/sales-brain-implementation-2026-09-23/api-conversion-history-verification.json).

تضم الحالات المستهدفة رحلة HTTP حقيقية محلية عبر المصادقة وتحديد الصلاحيات والحدود التشغيلية، والتسجيل 201 ثم الإعادة 200، وقراءة التاريخ، ومنع حقن هوية المصدر من جسم الطلب. كما تشمل التزامن، والتراجع وفقد commit عند أول إنشاء وعند الانتقال، وسحب المفتاح وانتهائه وتدويره، وتغير صلاحياته أو حالة النشاط والمالك، وعزل الأنشطة، وفساد الأدلة، وحذف المفتاح القديم، والسجلات السابقة للترحيل.

التحقق ببيانات مصطنعة على MySQL محلي، مع حجب الشبكة الخارجية. لا اختبار على حساب بيان حي أو اتصال ببوابة دفع أو عملاء حقيقيين. لم تتغير واجهة إنتاج أو مفاتيح ترجمة في هذه الدفعة؛ فُحصت الواجهات القائمة ضمن الانحدار.

## المتبقي

يبقى توثيق عقود استجابات Byaan الحية ومعرّفات التسجيل والفاتورة والدفع، وربطها باتفاق وموافقة وهوية عميل مثبتة. يلزم التمييز بين إنشاء رابط دفع والتحصيل والاسترداد، واعتماد العملة ومنع ازدواج العملية بين Tap وByaan وبقية الموصلات قبل إدخالها في حقائق البيع والتعلم.

لا يُستخدم هذا التاريخ لتفعيل سياسة أو احتساب أثر سببي لرد المخ. تبقى بوابات القياس والمراجعة البشرية والتفعيل المحدود والاعتماد الحي. حالة المصفوفة **4 مكتملة / 62 جزئية / 5 مفتوحة**؛ لا اعتماد 10/10 أو نشر للإنتاج.
