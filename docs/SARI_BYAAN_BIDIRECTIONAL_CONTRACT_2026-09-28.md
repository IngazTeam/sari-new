# عقد التكامل الفعلي بين ساري وبيان

تاريخ المراجعة: 28 سبتمبر 2026. المستودعان: `sari` على `main` و`byaan-v2` على `master`.

## النتيجة وحدودها

فحص كود المشروعين كشف أن اختبارات ساري السابقة كانت تتحقق من استجابات افتراضية لا يطابق بعضها واجهات بيان. هذا الإصلاح يؤسس عقد اتصال ومزامنة فعليًا في الطرفين، ويضيف عرض سعر ورابط إتمام شراء. **لا يعتمد اكتمال المسار المالي أو وصول المخ إلى 10/10.** لم تُرسل رسائل واتساب ولم تُنفّذ مدفوعات أو تسجيلات على الإنتاج.

## العمليات الحالية

| الاتجاه | العملية | التنفيذ والحدود |
|---|---|---|
| بيان ← ساري | إثبات الملكية `POST /api/sari/verify-ownership` | تحدٍّ موقّع مرتبط بتاجر ساري ونطاق الأكاديمية؛ لا يقبل إثبات تاجر آخر |
| بيان ← ساري | الصحة `GET /api/sari/health` | عقد `sari-byaan/1` وهوية التاجر وقدرات حقيقية؛ استجابة تسجيل دخول أو 4xx لا تعني نجاحًا |
| بيان ← ساري | تحديد المتدرب `POST /api/sari/identify` | طالب داخل الأكاديمية، تطبيع رقم سعودي كامل، ورفض الهوية الملتبسة؛ لا مطابقة بآخر أرقام الهاتف |
| بيان ← ساري | النتائج والشهادات | صلاحيات الأكاديمية وعزل الطالب؛ الدرجة من خدمة تقييمات بيان، والشهادة تمر بسياسة صلاحية الشهادات |
| بيان ← ساري | الدورات `GET /api/sari/courses` | دورات منشورة وعامة، سعر من خدمة التسعير، مواعيد ومقاعد |
| بيان ← ساري | `POST /api/sari/checkout-quote` | مبلغ بوحدات الهللة، الضريبة، `schedule: {date,time,timezone}`، المواعيد المتاحة ورابط الأكاديمية؛ لا ينشئ تسجيلًا أو فاتورة أو دفعًا |
| واتساب ← ساري ← بيان | دعوة إتمام الشراء | اختيار دورة ثم موعد مرقّم عند الحاجة، عرض فعلي قصير الصلاحية، موافقة مرتبطة بإثبات إرسال العرض، إعادة تحقق السعر والموعد، رابط داخل نطاق الأكاديمية؛ سجل `byaan_checkout` منفصل عن التسجيل والدفع |
| بيان ← ساري | `POST /api/sari/request-resync` | طلب موقّع مرتبط بالتاجر، استجابة `202 queued`، مهمة مرتبطة بهوية الاتصال على database/default |
| بيان ← ساري | `GET /api/sari/operations/{deliveryId}` | قراءة إيصال داخل الأكاديمية؛ `processing/completed/unknown`؛ ليست تسوية مالية |
| بيان ← ساري | أحداث الاشتراك `/api/sari/webhook` | تفعيل/إلغاء فقط، حصر الباقات، ربط التاجر والنطاق، منع التكرار، حفظ إيصال مشفّر؛ معالجة إعادة الاتصال في اليوم نفسه |
| ساري ← بيان | products/trainees/settings/faqs | أسماء الحقول والمصفوفات مطابقة للمستقبِل؛ البيانات الفارغة تُرسل لإزالة البيانات القديمة |
| ساري ← بيان | `POST /api/v1/platform/sync/site-content` | محتوى عام منشور حتى 50,000 وحدة UTF-16؛ حذف scripts/styles؛ تجاوز الحد يفشل صراحة |
| ساري ← بيان | knowledge | بعد نجاح المصادر فقط؛ يستعمل اللقطة المخزنة بدل قصّ المحتوى العام عند 5,000 حرف |
| ساري ← بيان | لوحة ساري وحالة الاتصال وتبديل البوت | طلب مستقل موقّع لكل مسار واستعلام؛ `isActive` يطابق عقد التبديل في ساري |

تُستخدم `id` و`productUrl` و`priceUnit: major` و`currency: SAR` للدورة، و`enrolledCourses` كمصفوفة للمتدرب. موعد الدورة ليس موعد إغلاق التسجيل. السعر المعروض يحسب الخصم والضريبة من منطق بيان؛ يعاد احتسابه عند الشراء ولا يثبت السعر للعميل بمجرد إرسال عرض.

## المصادقة ومنع تكرار الأثر

- بيان يحتفظ باتصال مركزي لكل أكاديمية وبسر مشفّر مستقل. المفتاح العام للمنصة وحده لا يجيز قراءة أو تعديل بيانات الأكاديمية.
- رؤوس الطلب: `X-Tenant-Domain`, `X-Sari-Timestamp`, `X-Sari-Delivery-Id`, `X-Sari-Signature`، و`X-Sari-Signature-Version: 2` عند توقيع الاستعلامات. يضيف بيان `X-Platform-Key` عند استدعاء منصة ساري.
- التوقيع: `sha256=` متبوعًا بـ HMAC-SHA256 على `v2.timestamp.deliveryId.method.requestTarget.domain.sha256(rawBody)`. يُوقّع جسم UTF-8 كما يُرسل، ويشمل `requestTarget` الاستعلام كاملًا وترتيبه وترميزه.
- السماحية الزمنية خمس دقائق. لا يقبل الإصدار الأول استعلامًا غير مشمول بالتوقيع. لا يقبل إصدارًا مجهولًا أو timestamp بصيغة أسية.
- بيان يعيد استجابة الطلب المكتمل نفسه إذا تكرر UUID والجسم؛ تغيير المحتوى أو إعادة طلب مجهول النتيجة ينتج `409`. ساري يحفظ إيصال الاستلام حتى عند 5xx، لأن الفشل قد يقع بعد حفظ الأثر.
- صف أحداث ساري يحافظ على ترتيب التفعيل والإلغاء لكل تاجر. تجاوز الحد الأقصى للمحاولات يوقف الأحداث التالية حتى المراجعة. الإقرار يجب أن يطابق نوع الحدث، ولا يكفي HTTP 200.
- لا تتكرر عمليات التسجيل/الدفع المجهولة تلقائيًا. لا تُحوَّل استجابة رابط شراء إلى حقيقة دفع أو إيراد.

## الربط والتشغيل

هذا تغيير بروتوكول يحتاج تحديث الطرفين وربط الأكاديميات؛ نشر بيان منفردًا يوقف العملاء الذين يرسلون المصادقة القديمة. لا تفعّل مفتاحًا عامًا بديلًا لتجاوز الربط.

1. راجع فرق الإصدارين ونسخة الاستعادة. طبّق migration بيان الجديد ضمن إجراء النشر المعتاد؛ لم يُطبَّق على الإنتاج في هذه المراجعة.
2. انشر طرفَي العقد بتنسيق واحد. ساري لا يحتاج migration جديدًا لهذا العقد، لكنه يحتاج migrations السابقة الخاصة بالاتصالات والإيصالات وصف الإرسال.
3. على بيان: `php artisan sari:connect TENANT_ID SARI_MERCHANT_ID`. الأمر يسأل عن مفتاح API للتاجر بصلاحية إدارة التكاملات، بإدخال مخفي؛ لا يكتب المفتاح في التقرير أو سجل الأوامر. لا يعيد إسناد اتصال مختلف تلقائيًا.
4. تحقق من الصحة الموقّعة وهوية التاجر، ثم نفّذ `php artisan sari:sync TENANT_ID --dry-run` لفحص الإعداد فقط، وبعده `php artisan sari:sync TENANT_ID` للمزامنة الفعلية.
5. شغّل عامل بيان لصف `default` على اتصال `database`؛ اضبط `retry_after` أطول من timeout المهمة (600 ثانية) ولا تعتمد على إعادة تلقائية للمهمة غير المكتملة. طلب إعادة المزامنة المقبول لا يعني اكتمالها. راجع نتائج الأمر وfailed_jobs.
6. تحقّق من المحتوى والنتائج بحساب مخصص، ومن ظهور أسماء الدورات وأسعارها ومواعيدها كما في بيان. تحقق من الإلغاء وإعادة الربط وفشل الاتصال دون إعلان نجاح وهمي.
7. أي تغيير نطاق/تاجر/سر يحتاج إعادة توثيق مدروسة ومراجعة العمليات المعلّقة. لا تحذف إيصالات منع التكرار عند الرجوع إلى إصدار سابق.

## فجوات تمنع تسمية التكامل كاملًا

1. **الشراء بعد المحادثة:** أصبح مسار واتساب يستهلك `checkout_invitation` فعليًا، ويختبر اختيار الموعد والموافقة وإرسال الرابط عبر قاعدة SQL ومسار إرسال واتساب الحقيقي بنقل مزوّد محاكى. المتبقي هو إسناد عملية الشراء اللاحقة إلى الاتفاق وتسوية نتيجتها. تفاصيل هذه الدفعة في `SARI_BYAAN_CHECKOUT_VERIFICATION_2026-09-28.json`.
2. **التسجيل اليدوي مختلف:** `/enroll` الموجود في بيان يتطلب `trainee_id` و`payment_type` صريحًا، وقد ينشئ دفعة يدوية. مسار المحادثة النشط يستخدم دعوة الشراء، ويحوّل الموافقة على عرض تسجيل قديم إلى المراجعة. تبقى وظائف التسجيل القديمة وسجلاتها للمراجعة والتوافق التاريخي، ولا تمثل عقد تنفيذ جديد مع بيان. لا نملأ `cash` تلقائيًا. قدرة التسجيل الذاتي في `/health` تبقى false.
3. **الفاتورة والتحصيل والاسترداد:** `/create-payment-link` المتوقع سابقًا ليس واجهة موجودة في بيان. يلزم إسناد موثق للـ checkout/order/payment إلى اتفاق ساري، وإشعارات دائمة للنتائج مع API قراءة وتسوية، وصلاحيات العميل، ومراجع منع التكرار. المطابقة بالهاتف والدورة فقط لا تكفي. refunds ليست مجرد تعديل حالة محلي.
4. **الحضور:** مسار ساري القديم ينتظر `/attendance`؛ لا تُعلن هذه القدرة حتى توفير عقد حضور موثق بسياسة نشر وصلاحية الطالب. capability الحالية false.
5. **اللقطات الكبيرة:** فوق 500 منتج/متدرب أو 50 FAQ تُرسل الدفعات append مع حالة partial، دون حذف دفعات سابقة أو ادعاء اكتمال replacement. يلزم staging/finalize ذري بإصدار لقطة وحراسة التزامن وترحيل معدل الطلبات. المعرفة تُحجب عند المزامنة الجزئية. تجاوز 10,000 متدرب أو حدود المحتوى يحتاج امتدادًا معلنًا للعقد.
6. **حالة المهمة والمراجعة:** صحة الاتصال، وقت آخر جزء متزامن، قبول المهمة، واكتمال جميع المصادر حالات مختلفة. يلزم سجل تشغيل كامل للمزامنة وتسوية خارجية لحالة unknown، وواجهة مراجعة تربط إيصال بيان باتفاق ساري.
7. **اعتماد الإنتاج:** لم نختبر DNS/TLS والعامل والمفاتيح والتكامل المالي على حساب حي مخصص. الاختبارات المحلية لا تغلق هذه البوابة.

## قواعد دعوة الشراء في واتساب

- السعر من بيان، مع الضريبة والموعد والمنطقة الزمنية؛ لا يستخرج النموذج سعرًا أو هوية متدرب أو موافقة. الاسم والهاتف يُستكملان في صفحة بيان عند الحاجة.
- يُعرض حتى 20 موعدًا متاحًا في الرسالة من الاستجابة المحدودة بـ500 موعد. الموعد يختاره العميل برقم صريح، بما في ذلك الأرقام العربية. الرد غير الصالح يعيد قائمة حديثة دون حجز.
- صلاحية العرض خمس دقائق. عند الموافقة يعاد الاستعلام دون إبقاء معاملات SQL مفتوحة أثناء الشبكة. تغيّر السعر أو الضريبة أو الموعد أو التوقيت أو التوفر يبطل العرض ويحتاج مراجعة جديدة.
- الاتفاق يحفظ مصدر اختيار الدورة والموعد ودليل وصول العرض والموافقة. حراسة الإرسال تمنع تغيير النص أو الرابط أو المستلم، وتمنع الرد بعد تسلّم الموظف أو حذف الذاكرة أو وصول رسالة أحدث أو تبديل اتصال الأكاديمية.
- تكرار الموافقة نفسها يعيد الدعوة المحفوظة. الطلبان المتزامنان قد يجريان قراءتين للسعر؛ ينتجان اتفاقًا واحدًا بلا تسجيل أو دفعة. فشل قراءة السعر قابل للمحاولة مجددًا، ولا يسجَّل كأثر مالي مجهول.
- `execution_state=succeeded` مع `external_provider=byaan_checkout` يعني تجهيز دعوة فقط. تبقى `order_id` و`external_order_key` فارغتين، ولا ينشئ هذا المسار `sari_conversions` أو حقائق دفع أو تسجيلات.
- نشر هذا الامتداد يحتاج طرفَي العقد: عميل ساري يشترط `schedule` ويفشل بأمان إن لم يحدّث بيان بعد. الرجوع إلى مسار التسجيل القديم ليس بديلًا صالحًا؛ عند الرجوع احتفظ بالاتفاقات وأوقف أتمتة الشراء حتى توافق الإصدارين.

## إعادة التحقق

في بيان: `php scripts/testing/verify-sari-contract.php` يستخدم `byaan_v2_test` المحلي فقط، ويحترم قفل الاختبار، ويمنع HTTP غير المزوّر والبريد الحقيقي. لا تشغّله على قاعدة الإنتاج.

في ساري: استخدم `scripts/testing/run-isolated.mjs --with-database byaan platform-read-model-pentest api-instance-lifecycle-pentest auth.platformProvision --no-file-parallelism` مع `SARI_TEST_DATABASE_URL` محلي اصطناعي، ثم الأنواع والترجمات والبناء.

`scripts/testing/verify-byaan-wire-contract.ts <byaan-root> <php-executable>` يقارن موقّع PHP الحقيقي بموقّع TypeScript على سبعة طلبات في الاتجاهين دون شبكة أو قاعدة بيانات.

سجل نتائج التحقق النهائي وأسماء الملفات موجود في `SARI_BYAAN_CONTRACT_VERIFICATION_2026-09-28.json`. تظل مصفوفة الخطة 4 مكتملة / 62 جزئية / 5 مفتوحة؛ لا تُغلق بوابة مالية باختبار توقيع أو mock ناجح.
