# أدلة الاتفاق وإنشاء الطلب وإسنادها للتجربة البيعية

استكمال على `main` بعد `b6defe9e`. أضيف سجل ثابت للطلبات الناتجة عن اتفاق محلي أو نتيجة زد موثوقة، مع إسناده إلى تخصيص العميل في التجربة. تبقى حالة الخطة **4 مكتملة / 59 جزئية / 8 مفتوحة**؛ إنشاء الطلب لا يثبت قبض المال أو تحسن المبيعات.

## التنفيذ

- ينشئ `ai_sales_order_facts` دليلًا جديدًا فقط عند إنشاء الطلب المحلي من موافقة العميل، أو تثبيت نتيجة إنشاء زد، أو إثبات نتيجة مجهولة عبر GET مربوط بمحاولة التنفيذ. يحفظ مرجع العرض والموافقة والمحادثة وبصمة تفاصيل الاتفاق وهوية العميل المستعارة وقيمة الطلب بالوحدة الصغرى ووقت التحقق المحلي. لا ينسخ الاسم أو الهاتف أو العنوان أو النص أو رابط الدفع أو مفاتيح المزوّد.
- تثبت هوية الطلب النشاط والمزوّد وحساب المتجر ومعرّف الطلب. تشمل هوية زد بصمة متجره، فتظل أرقام الطلبات المتساوية في متجرين مختلفة. تتفرد الأدلة بالاتفاق وبالهوية وبالطلب المحلي. لا يربط رقم زد بإسقاط محلي بناءً على تشابه الرقم أو الهاتف؛ يبقى `localOrderId=null` لزد حتى يوجد مسار ربط معتمد بين المصدرين.
- حفظ الطلب المحلي والموافقة والدليل معاملة واحدة؛ إخفاق الدليل يلغيها محليًا. في زد تُحفظ النتيجة الموثوقة والدليل معًا بعد POST، وقبل إسقاط الطلب إلى الجداول الأخرى. فشل الإسقاط لا يعيد POST ولا ينشئ دليلًا آخر.
- عند غموض حفظ نتيجة زد لا يُعاد إنشاء الطلب. تظل محاولة التنفيذ محفوظة، وتُثبت النتيجة بواسطة GET يحمل مرجع `SARY-CHECKOUT` نفسه مع تطابق المتجر والعميل والمنتجات والكميات. فقد إقرار commit بعد الحفظ يعاد قراءته دون تكرار الأثر الخارجي.
- `quotedAmountMinor` قيمة طلب، وليست إيرادًا. أساس المبلغ المحلي كتالوج يحتاج اعتماد الفاتورة، وأساس مبلغ زد فاتورة أبلغ عنها المزوّد. `paymentEvidence=not_measured` و`revenueMinor=null`؛ لا تُستبدل المعلومة الغائبة بصفر أو خسارة، ولا يُنتج السجل فائزًا أو سياسة تعلم.
- ينفذ عامل SQL عشر حالات كحد أقصى كل دقيقة، دون تداخل، ويغلق بعد تصريف العمل الجاري. يسلسل التخصيص بقفل النشاط ثم الدليل، ويطابق بصمات البروتوكول والمجموعة والقطاع والنافذة. التعارض يتحول إلى مراجعة، والفشل التشغيلي يعاد بتأخير متزايد حتى ثماني محاولات. هذه الأخطاء لا تلغي الطلب ولا تعيد الاتصال بالمزوّد.
- الإسناد إلى التخصيص الذي يحتوي وقت التحقق المحلي داخل `[assignedAt, observationEndsAt)`. يبقى العميل محسوبًا في المقام دون اشتراط إيصال رد، ولا يعاد توزيعه بعد سحب الإذن. الدليل لا يقرر أن رسالة بعينها سببت إنشاء الطلب.
- يقرأ السوبر أدمن النشط أعداد حالات العامل عبر `inboundOperations.salesOrderAttributionHealth`. يُراجع دوره وحالة حسابه في SQL لكل قراءة؛ لا تفاصيل عملاء ضمن الاستجابة.

## إصلاح سباق هوية اتفاق زد

قبل هذه الدفعة كانت كتابة نتيجة POST تتحقق من رقم المحاولة وحالة التنفيذ، وكانت مراجعة GET تقارن رقم المحاولة وبصمة مخزنة داخل snapshot. لا يكفي ذلك إذا تغير هاتف العميل أو مرجع الموافقة أو تفاصيل الاتفاق أثناء انتظار الشبكة.

أصبحت كتابة نتيجة POST تقفل الاتفاق وتعيد مطابقة العميل والمحادثة ومصدر العرض والموافقة والمزوّد وحالة الاتفاق وبصمة **تفاصيل snapshot كاملة** مع النسخة التي نُفذت. تفعل تسوية GET الشيء نفسه قبل تثبيت النتيجة. الاختبارات تغيّر هذه الحقول أثناء الطلب وتثبت رفض الإسناد دون POST آخر أو دليل لعميل خاطئ.

الجولة المركزة الأولى كشفت نقصًا في محاكاة `getPool` لدى اختبار زد بعد إضافة فحص جاهزية الجدول. صُححت المحاكاة لتصل إلى قاعدة الاختبار الفعلية، دون تعطيل فحص الجاهزية أو تخفيف شروط القبول. نجحت 224 حالة بعدها، ثم 234 بعد إضافة حالات اختلاف المتجر وغموض commit وتغير الاتفاق أثناء الشبكة. لا تدخل نتائج الجولة المخفقة في القبول النهائي.

اختبارات المزوّدين وواتساب محاكاة، وMySQL محلي ببيانات اصطناعية مع حجب الشبكة الخارجية. فحص الأمان عدائي محلي، وليس اختبار اختراق مستقلًا على الإنتاج أو إثباتًا لقدرة نموذج حي على الإقناع. اختبار التعافي يغطي إعادة الاتصال وفقد الإقرار ودورة تشغيل العامل؛ لا يُدّعى قتل عملية إنتاجية أو قياس بيع فعلي.

## الترحيل والتراجع والاحتفاظ

الترحيل `0126_sales_order_facts` إضافي، ويجب تطبيقه قبل تشغيل الكود الجديد. يفحص مسار الاتفاق والعامل جاهزية الجدول وفهارسه وقيوده. يظل الطلب القديم والاتفاق القديم كما هما؛ لا تُمنح إعادة قراءة اتفاق ناجح تاريخيًا ساعة إنشاء جديدة. إعادة المحدّث وإعادة SQL آمنتان.

يحفظ الدليل المراجع دون حذف متتابع من الطلب أو الاتفاق أو المحادثة، فيظل صالحًا للتدقيق بعد تنقية المصدر. حذف النشاط يحذف أدلته. بصمة العميل قابلة للربط داخل النشاط وليست إخفاء هوية كاملًا؛ سياسة الاحتفاظ والحذف التفصيلية ما زالت ضمن العمل المتبقي.

يمكن التراجع بالكود مع إبقاء الجدول والأدلة. العامل القديم لا يسجل هذه الوقائع، لذلك يجب اعتبار فترات التفعيل المختلط أو التراجع فجوات قياس، وعدم تسميتها عدم إنشاء طلب أو خسائر. يبدأ اعتماد نافذة قياس بعد التحقق من إصدار الويب والعمال معًا. لم يحدث push أو نشر، ولا تعديلات على سقف المنصة 100 دولار يوميًا أو اختيار OpenAI/ZahyPi.

## حدود هذه الدفعة والمتبقي

1. السجل يغطي الطلب المحلي الناتج عن الاتفاق ونتيجة اتفاق زد الجديدة فقط. لا يغطي كل الطلبات المستوردة أو اليدوية، ولا إشارات سلة وبيان، ولا يعتبر إنشاء رابط دفع أو إتمام تسجيل تدريبي قبضًا ماليًا.
2. هوية طلب زد مثبتة داخل دليله. ما زال اعتماد الروابط بين هذا الدليل و`zid_orders` وإسقاط `orders` وTap وسلة وبيان مطلوبًا قبل جمع إيرادات المصادر؛ لم يُغيّر هذا الإصلاح هوية الإسقاط القديمة `zid:<id>` أو يملأ حساب متجر مفقودًا بتخمين.
3. نتيجة `order_created_only` تاريخية؛ لا تصف حالة الطلب الحالية. يلزم تسجيل الإلغاء والتعديل والانتهاء والمبلغ النهائي وربطها بالدفع والاسترجاع، مع تغطية الاسترجاع الجزئي والمساعدة البشرية والطلبات المعلقة قبل التقرير الجامع.
4. يُسند إنشاء زد إلى وقت التحقق المحلي من النتيجة، لا ساعة إنشاء الطلب عند المزوّد؛ التسوية المتأخرة بعد النافذة لا تُرجع الحدث إلى الماضي. الطلب القديم الناجح بلا دليل يبقى خارج القياس الجديد، وليس خسارة.
5. بقي إثبات تسليم/قراءة الرسائل وتغطية المصادر، وواجهة التقرير وحكم تجاري محفوظ بمقام وقطاع وعملة ونافذة ثابتة، والتعلم المعتمد والتقييم الفعلي والمراجعة المستقلة، وبقية الحصص والاحتفاظ والتفعيل المحدود.
