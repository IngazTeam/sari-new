# توحيد حجز السعة ومنع التداخل داخل سجل الحجوزات

التاريخ: 24 سبتمبر 2026. امتداد لخطة مخ ساري بعد `12e6c7a`. النطاق هو سجل `bookings` المستخدم في إدارة الحجوزات والدفع؛ لا يعني دمجه بجدول التقويم القديم `appointments` أو إثبات جاهزية بيع 10/10.

## ما أُصلح

كان الإنشاء يفحص التعارض ثم يُدخل الحجز في عمليتين منفصلتين، فيستطيع عاملان اجتياز الفحص قبل أن يحفظ أحدهما. وكان فحص الإنشاء يربط الموظف بالخدمة نفسها، فلا يرى شغله في خدمة أخرى. أما إعادة الجدولة فكانت تستخدم قفل الخدمة، وهو لا يسلسل عمليتين على خدمتين تشتركان في الموظف.

أصبح الإنشاء والتعديل والحذف يستخدمون معاملة `READ COMMITTED` وقفلًا دائمًا خاصًا بالتاجر في `booking_capacity_locks`. يأتي هذا القفل قبل أقفال الحجز والخدمة. يُفحص التعارض بعد اكتساب القفل وتبقى المعاملة مفتوحة حتى الحفظ؛ لا اتصالات بمزوّد أو رسائل داخل المعاملة. لا يوجد قفل JavaScript محلي يمكن تجاوزه بتشغيل عامل آخر.

القفل مستقل عن صف إعدادات التاجر. وهو يسلسل هذه الكتابات داخل التاجر كله، حتى للأيام المختلفة، مقابل بروتوكول أبسط يمكن اختباره. التجار الآخرون يستمرون بصورة مستقلة. هذا ليس معيار أداء تحت حمل إنتاجي؛ تقسيم القفل حسب الموارد والأيام يحتاج اختبارًا لاحقًا إذا استدعى الحمل ذلك.

## قواعد التداخل والسلوك

| الحالة | النتيجة |
|---|---|
| موظف واحد وخدمتان مختلفتان في الفترة نفسها | يُرفض التداخل. |
| موظفان مختلفان في الخدمة نفسها | يسمح بالتوازي؛ لا تُغلق الخدمة كلها بسبب موظف واحد. |
| حجز بلا موظف محدد | يحتجز سعة الخدمة خلال فترته، ويتعارض مع حجز الخدمة بموظف أو بدونه. |
| نهاية حجز تساوي بداية التالي | لا يوجد تداخل؛ الفترات نصف مفتوحة. |
| حجز معلق أو مؤكد أو قيد التنفيذ | يحتجز السعة. الإلغاء والإكمال وعدم الحضور يحررونها دون حذف التاريخ. |
| إعادة جدولة أو تغيير موظف | يستخدم نفس قاعدة الإنشاء ونفس القفل؛ لا يتجاوز الحجز الموجود في خدمة أخرى. |
| خدمة أو موظف من تاجر آخر، أو مورد معطل | يُرفض الإنشاء؛ تُفحص قائمة موظفي الخدمة عندما توجد. |
| تاريخ أو وقت غير صالح، عبور منتصف الليل، مدة لا تساوي الفرق بين البداية والنهاية | يُرفض الإدخال؛ لا حفظ بمدة كسرية أو مبلغ غير صحيح كعدد هللات. |
| فشل الحفظ أو موت العامل قبل commit | تتراجع المعاملة وتتحرر السعة؛ اختُبر ذلك بعملية مستقلة جرى إيقافها. |
| فقد تأكيد commit | يُتلف الاتصال المشكوك فيه، والحجز المحفوظ يحجب تكرار الفترة. إنشاء الطلب لا يملك بعد معرفًا دائمًا لاسترجاع نتيجته؛ يراجع الموظف القائمة. |

إنشاء الحجز لا يغير حالة الدفع ولا ينشئ دفعة أو نتيجة شراء للتعلّم. تبقى إدخالات المدة والسعر اليدوية لصاحب الصلاحية؛ لم تُضف هذه الدفعة سياسة اعتماد سعر أو خصم مالي جديدة.

مسارا الإنشاء، المركب والمستقل، يستخدمان `orders.manage` وهوية التاجر من العضوية. لا يقبلان حقن `merchantId` أو `status` أو `paymentStatus` أو هوية التقويم. يمران بمساعد إنشاء ذري واحد دون فحص منفصل يُعامل كحجز مضمون. المساعد القديم `db.createBooking` أصبح يمر بالبروتوكول نفسه.

## التوافر والمحادثة

فحص التوافر يستخدم القاعدة نفسها، ولكنه يظل قراءة إرشادية؛ نتيجة «متاح» ليست حجزًا. الحفظ يعيد التحقق داخل المعاملة.

قائمة الفترات المسجلة تستبعد التداخل الفعلي حتى إذا كان عداد `currentBookings` قديمًا، وتستبعد الفترات المعطلة وموظفي التجار الآخرين والموظفين المعطلين أو غير المسندين للخدمة. العداد القديم يبقى مرشحًا محافظًا، ولا يعاد بناؤه تلقائيًا في هذه الدفعة.

مساعد المحادثة لم يعد يولد أوقاتًا افتراضية من 9 إلى 5؛ يعرض الفترات المسجلة بعد تصفية السعة. وعند إنشاء طلب يصفه بأنه **بانتظار التأكيد**، مطابقًا لحالة SQL، ولا يعد برابط دفع لم يُنشأ أو بتذكير لم يُرسل. أزيلت كتلة دفع قديمة غير منفذة واستيرادها غير الصحيح. اختيار المزوّد وسقف المنصة 100 دولار يوميًا لم يتغيرا.

لم تتغير ملفات الواجهة. أُعيدت مقارنة حزمة مكوّنات اختبار الواجهة، وأداة التحقق، وجميع ملفات CSS المحملة مع النسخة التي اجتازت **291 سيناريو و34 لقطة**؛ مطابقة البايتات تسمح بإعادة استخدام الدليل السابق. هذه الدفعة لا تدعي تشغيل السيناريوهات مرة أخرى أو اختبار جهاز iPhone/Safari فعلي. الفحص الأمني محلي، وليس اختبار اختراق إنتاجي مستقلًا.

## الترحيل وحدود الإغلاق

أضيف الترحيل `0085_booking_capacity_locks` بعد 0084، وطُبق على قاعدتي MySQL محليتين. طوبقت بصمته وسجل الترحيل والمفتاح الأولي للتاجر والرابط الأجنبي. لا يعدل الترحيل الحجوزات القديمة أو مبالغها أو حالات دفعها. يفشل المسار مغلقًا إذا لم يتوفر المخطط المطلوب.

يجب تطبيق الترحيل وتحديث جميع نسخ الويب والعمال معًا قبل التشغيل الإنتاجي؛ بقاء كاتب قديم لا يستخدم القفل يُبطل ضمان البروتوكول. لم يُنفذ نشر أو ترحيل إنتاجي.

المتبقي الذي لا تغلقه هذه الدفعة:

- جدول `appointments` ومسارات التقويم القديمة وGoogle/Calendly منفصلة؛ لم يُضمن منع التعارض بين تلك الجداول وسجل `bookings` بعد.
- اتفاق الحجز داخل محادثة البيع، وهوية مصدر الطلب وموافقة العميل وإعادة استرجاع نتيجة الإنشاء بالمعرف نفسه.
- سياسة الدوام والعطل وفواصل الخدمة والسعة الجماعية والحد اليومي. الفترات المسجلة هي قائمة عرض؛ الإصلاح لا يفرض أن يكون الإدخال اليدوي داخلها ولا يعيد بناء عداداتها القديمة.
- استكمال قراءة صفحة الحجوزات للفريق، وسياسات السعر والخصم ومراجعة الموعد مع العميل، والاعتماد الحي للتكاملات والجودة التجارية.

حالة الخطة تبقى **4 مكتملة، 55 جزئية، و12 غير مغلقة**؛ تحسنت أدلة B035 وB037 وB057 وB064 وB065 دون ترقية البنود المركبة إلى اكتمال غير مثبت.
