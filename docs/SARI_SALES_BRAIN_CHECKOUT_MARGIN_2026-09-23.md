# حماية هامش الفاتورة المحلية ومراجعة تكاليفها

التاريخ: 23 سبتمبر 2026. أساس هذه الدفعة: `aaec9ad`.

أضيفت حماية قابلة للتفعيل تمنع اعتماد فاتورة محلية سجّلها مخ ساري إذا لم يحقق هامشها الحد الذي اعتمده التاجر. يعتمد الحساب على تكلفة المنتج أو الخيار في قاعدة البيانات، والضريبة والتوصيل والتكاليف الأخرى التي يراجعها الموظف صراحة. هذه خطوة في B028 وB034 وB057؛ لا تعني اكتمال سياسة الخصم أو جاهزية المخ بدرجة 10/10.

## السلوك الناتج

1. يحدد صاحب صلاحية إدارة إعدادات البوت التفعيل والحد الأدنى من 0 إلى 100% داخل مخ ساري أو إعدادات البوت. يحتاج الحفظ مراجعة صريحة وإصدارًا وبصمة حاليين؛ يسجل قبل التغيير وبعده وهوية صاحبه داخل المعاملة نفسها.
2. عند مراجعة فاتورة محلية، يدخل الموظف الضريبة المشمولة في المبلغ وتكلفة التوصيل عليه والتكاليف الأخرى بالريال. الخانات فارغة ابتداءً؛ غياب التكلفة ليس صفرًا. تقبل الأرقام العربية والفارسية والفاصل العشري العربي دون تقريب مبالغ ذات أكثر من منزلتين.
3. تقرأ المعاينة تكلفة المنتجات والخيارات من SQL، وتعرض الإيراد بعد الضريبة والتكاليف والفرق ونسبة الهامش. لا يحدد المتصفح تكلفة المنتج، ولا يقدرها النموذج. تكلفة خيار مفقودة لا تُستبدل بتكلفة المنتج الأب.
4. لا يصبح زر الاعتماد متاحًا إلا بعد نتيجة تحقق ناجحة ومراجعة الموظف. تغيير المدخلات أو السياسة يلغي المراجعة السابقة. فشل تحميل السياسة يمنع الاعتماد.
5. يعيد الخادم فحص ملكية الطلب واتفاق العميل وحالته ومبلغه وبنوده والكتالوج والسياسة والتكاليف تحت الأقفال. لا تكفي نتيجة قديمة ظاهرة في المتصفح. يحفظ إثبات الحساب والمراجعة مع الاتفاق، ويرفع حظر الفاتورة في المعاملة نفسها.
6. المعاينة لا تصدر رابطًا. مسار الاعتماد القائم يستطيع إصدار رابط الدفع بعد نجاح الاعتماد؛ رفض الاعتماد لا يصل إلى إنشاء الرابط. لا يغير الحساب مبلغ العميل ولا يخصم كوبونًا ولا يرسل رسالة.

الحماية **متوقفة افتراضيًا** حتى يعتمد صاحب الصلاحية إعدادها. لا يُفرض حد تجاري مخمّن، ولا تُسحب اعتمادات فواتير سابقة عند تفعيلها أو تغييرها. يظل اعتماد المبلغ النهائي مطلوبًا عندما تكون الحماية متوقفة.

## الحساب وحدوده

تجرى الحسابات بوحدات العملة الصغرى الصحيحة، بالريال السعودي:

```
الإيراد = المبلغ المتفق عليه − الضريبة المشمولة
التكاليف = مجموع (تكلفة المنتج أو الخيار × الكمية) + تكلفة التوصيل + التكاليف الأخرى
الفرق = الإيراد − التكاليف
قبول الحد: الفرق × 100 >= الإيراد × الحد الأدنى
```

يشترط إيراد موجب، ومبالغ موثقة ضمن الحدود الرقمية. المقارنة دون تقريب النسبة المعروضة: هامش أقل من الحد بقيمة صغيرة لا يمر بالتقريب. التكلفة الصفرية المخزنة صراحة مقبولة؛ التكلفة المفقودة أو السالبة أو ذات وحدة غير موثقة تمنع الاعتماد عند التفعيل.

هذا **هامش وفق البيانات المخزنة والتكاليف التي راجعها الموظف**، وليس تدقيقًا محاسبيًا أو ضمانًا لصافي ربح النشاط. صحة الضريبة والمصروفات المدخلة مسؤولية المراجع؛ لا يفترض النظام ضريبة أو تكلفة توصيل من عنده. لا يوجد استثناء منفرد للحد في شاشة الطلب؛ تغيير السياسة يحتاج صلاحية مستقلة وسجل تغيير.

## ضمانات المنطق والصلاحيات

| الحالة | السلوك المثبت |
|---|---|
| متجر أو طلب أو دليل يخص جهة أخرى | رفض؛ هوية التاجر والمستخدم تؤخذ من الجلسة |
| موظف مبيعات بلا صلاحية إدارة الإعدادات | يمكنه مراجعة الفاتورة حسب صلاحياته؛ لا يستطيع تغيير حد الهامش |
| تكلفة أو سياسة تغيرت بعد المعاينة، حتى دون تغيير الإصدار أو التاريخ | إعادة الحساب والبصمة تكشف التغيير، ويرفض الدليل القديم |
| فاتورة مدفوعة أو خارجية أو تغيرت بنودها أو مبلغها أو كتالوجها | رفض الاعتماد من هذا المسار |
| فشل حفظ مراجعة الفاتورة أو سجل تغيير السياسة | تراجع المعاملة؛ لا اعتماد جزئي أو تغيير سياسة بلا تدقيق |
| طلبان متزامنان أو إعادة طلب حفظ قديم | إصدار السياسة ينجح مرة واحدة؛ اعتماد الفاتورة يحفظ إثباته الأصلي |
| تكلفة منتج يرسلها المتصفح أو حقول صلاحية مزورة | عقد مدخلات صارم يرفضها |
| أسماء منتجات تتضمن HTML | عرض كنص داخل React؛ لا تنفيذ للمحتوى |

ترتيب قفل التاجر يسبق السياسة ثم الطلب والمنتجات؛ تحديث السياسة يقفل التاجر حصريًا، والقراءة تستخدم القفل المشترك. لا اتصال بمزوّد خارج الشبكة داخل المعاملة. إثبات التكلفة يبقى للمراجعة الداخلية؛ لا يدخل نص العرض المرسل للعميل أو تعليمات النموذج.

أُغلق كذلك المساعد القديم `applyDiscountCode`: كان يزيد استخدام الكوبون ويعلن النجاح دون تعديل الطلب. يعيد الآن رفضًا واضحًا دون قراءة أو تعديل أو استهلاك. لم يُعثر على مستدعٍ إنتاجي له في المصدر الحالي. إصدار الأكواد والتحقق منها ومشاركتها لم تتغير بهذه الخطوة. تطبيق خصم فعلي يحتاج اتفاقًا محدثًا وموافقة العميل وتنفيذًا ماليًا مترابطًا؛ لا يُستعاض عنه برسالة نجاح.

## الترحيل والتشغيل

أضيف `0075_checkout_margin.sql` لجدولي السياسة والتدقيق، وطُبق على قاعدتي الاختبار المحليتين `sari_brain_test` و`sari_brain_migration_test`. طابقت قراءة سجل الترحيل في كلتيهما توقيته وبصمة SHA-256 للملف `80ba252c94a83426aa11aebe026759e528217f103af9401274e2f6a8afeb4b93`، وثبت وجود الجدولين. إثبات مراجعة الفاتورة يحفظ داخل لقطة الاتفاق القائمة. لا تعديل تلقائي للأسعار أو التكاليف أو الأكواد أو اعتمادات سابقة.

قبل استخدام الحماية في الإنتاج يلزم تطبيق الترحيل وتحديث الويب والعمال معًا، ومراجعة وحدات تكلفة المنتجات والخيارات، ثم تفعيل حد مناسب من صاحب الصلاحية. غياب الجدول الجديد يوقف قراءة السياسة والاعتماد بدل تجاهل الحماية. لم ينفذ نشر أو ترحيل إنتاجي أو اتصال بعميل أو مزوّد حقيقي في هذه الدفعة.
