# صلاحيات واجهات التقارير القديمة — 2026-09-29

أُزيل الراوتر المكرر داخل `server/routers.ts` ووُصل بالراوتر الموحد. قراءة قائمة التقارير والتفاصيل تستخدم عضوية التيننت المحدد وصلاحية `analytics.read`، والتوليد يستخدم `bot_settings.manage`؛ لا يستطيع المشاهد أو مشرف المبيعات بدء توليد بمزود. تُطبق هوية التيننت ومعرف التقرير معًا داخل استعلام التفاصيل، ويعود الرد نفسه للسجل المفقود وسجل تيننت آخر.

القائمة تقبل 1–52 تقريرًا و1–100000 صفحة مع ترتيب ثابت بنهاية التقرير ثم معرفه. ترفض المدخلات غير الصحيحة والحقول الزائدة ومعرفات التيننت من الحمولة، ولا تتحول أخطاء القراءة إلى قائمة فارغة أو نجاح. أُبقيت الحقول الخام القديمة في الاستجابة للتوافق، وأضيفت عينة محسوبة وحدود الدليل وغياب قياس الرضا واحتراف المبيعات. لا تستعمل الواجهة الجديدة هذه الحقول التاريخية كنسب موثوقة.

نجحت **76 حالة** لصلاحيات القراءة/التوليد والمدخلات والعزل وسلامة التوليد والواجهة المشتركة، و**3 حالات MySQL** للترقيم والترتيب والحدود والعزل والحقول الخام مقابل النسبة المحسوبة. النتائج في `tests.json` و`mysql-tests.json`. نجح بناء التطبيق مع تحذير أحجام Vite المعروف.

لا يوجد استدعاء حالي من العميل لهذه الواجهات القديمة حسب بحث المراجع؛ احتُفظ بأسماء العمليات وبنية السجل الأساسي. لم يُستدع مزود أو بريد فعلي. لا migration ولا مفاتيح ترجمة أو تعديل واجهة، ولا دفع أو نشر. تبقى مراجعة ملخصات `db-insights.ts`، وإثبات العينة الدائم، والتوليد المجزأ والجدولة والتكرار ومصالحة البريد. لا يعني فحص الصلاحيات اختبار اختراق شاملًا أو اكتمال بقية صفحات اللوحة.

التحقق النهائي: نجح فحص TypeScript الكامل.
