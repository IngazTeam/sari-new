# عقل ساري: النتائج والمعرفة والفجوات واحتراف المبيعات

تحديث تصميم الموك أب — 28 سبتمبر 2026.

[افتح عقل ساري](http://127.0.0.1:4329/#/page/merchant/sari-brain)

## ما تغيّر

أصبحت صفحة عقل ساري مساحة متابعة بأربعة أقسام بدل قائمة مصادر عامة:

1. **النتائج**: أهم فجوة وخطوة علاجها، ملخص الملفات المفعّلة والتي تحتاج مراجعة أو فشل استخراجها، ومعلومات مستخرجة مع اسم الملف وموضع النص.
2. **ملفات المعرفة**: البحث والتصفية، نوع الملف وحجمه وتاريخه، حالة الاستخراج والمراجعة والتفعيل بشكل منفصل، عرض النتائج، اعتماد المصدر أو إيقاف استخدامه. إضافة ملف في المعاينة تحفظ الاسم والحجم فقط، دون رفع المحتوى أو اختلاق نتائج استخراج.
3. **الفجوات**: نوع المشكلة، أولوية العلاج، مثال سؤال العميل، تكرار السؤال خلال الفترة، والأثر على قرار الشراء. العلاج يمر بمسودة إجابة ومصدر، ثم موافقة صريحة، ثم اختبار توضيحي ومراجعة نتيجته. إيقاف مصدر التصحيح يعيد الفجوة إلى انتظار الاختبار.
4. **احتراف المبيعات**: درجة مفهومة مع الفترة، حجم العينة، ست مهارات وأوزانها، دليل كل مهارة، وأولوية التحسين. الدرجة لا تزيد عند رفع ملف أو إغلاق فجوة، ولا تعرض عند نقص العينة.

جميع الأسماء والمحتويات والأسئلة والدرجات بيانات توضيحية. لم تُحلل ملفات المستخدم أو محادثات تيننت فعلي في هذا التحديث. لم تُعدّل واجهة React الإنتاجية أو محرك المعرفة أو عقود الخادم.

## ما كشفته مراجعة التطبيق الحالي

| الملاحظة من المصدر | أثرها على التصميم والتنفيذ الفعلي |
|---|---|
| `server/db/knowledge.ts:calculateHealthScore` يجمع أوزان وجود أقسام المعرفة، وبعض أعداد المنتجات والأسئلة والوثائق. يجلب الأقسام العامة، بينما الاسترجاع الفعلي يملك فلترة منفصلة للاعتماد والتفعيل والصلاحية. | النسبة الحالية مقياس اكتمال، وليست احتراف بيع أو ضمان صحة الإجابات. لا يجوز إعادة تسمية الرقم الحالي إلى احتراف المبيعات. يلزم توضيح اكتمال المعرفة مقابل جاهزيتها للاستخدام. |
| `server/routers-sari-brain.ts:getSources` يعرض الوثيقة التي تعيدها `getKnowledgeDocByMerchantId`، مع حالة الاستخراج ووجود النص. | قائمة الملفات المتعددة في المقترح تحتاج سجلًا موحدًا لكل مصدر وإصداراته، مع رابط للأقسام المشتقة منه. العقد الحالي لا يكفي لإثبات مراجعة كل ملف أو تعددها. |
| `server/routers-knowledge-docs.ts:reprocess` يستطيع إكمال استخراج النص مع فشل مرحلة التصنيف اللاحقة داخل catch غير حاجب. | اكتمال الاستخراج لا يعني أن المعرفة صارت جاهزة للاسترجاع. يجب عرض مراحل الاستخراج والتصنيف والمراجعة والفهرسة بأخطاء منفصلة قابلة للإعادة. |
| `getKnowledgeSections` و`getPendingReviews` يستطيعان إرجاع مصفوفة فارغة عند أخطاء داخلية. | واجهة الإنتاج تحتاج حالة «تعذّر جلب النتائج» مستقلة عن «لا توجد معرفة/فجوات». لا يجوز عرض مؤشر نجاح مع فشل قراءة الأدلة. |
| توجد أقسام `sales_intel` و`opportunities` ومقترحات تعلّم ومراجعات تجارب بيع. | هذه مصادر لإرشادات وأدلة، ولا تثبت بمفردها نسبة احتراف. يجب ربط كل محور بعينة محادثات محددة ونسخة معايير ومراجعة موثقة. |

هذه نتائج مراجعة مصدر محددة، وليست حكمًا على بيانات تيننت بعينه أو اختبار اختراق جديد.

## تعريف نسبة احتراف المبيعات المقترحة

الهدف قياس جودة سلوك البيع في محادثات قابلة للتقييم، بصورة منفصلة عن اكتمال المعرفة ومعدل التحويل التجاري.

| المهارة | الوزن | مثال المعاينة |
|---|---:|---:|
| فهم احتياج العميل | 20% | 32/40 = 80% |
| دقة المعلومة والمصدر | 20% | 34/40 = 85% |
| التعامل مع الاعتراض | 20% | 26/40 = 65% |
| ملاءمة الترشيح | 15% | 28/40 = 70% |
| وضوح الخطوة التالية | 15% | 30/40 = 75% |
| البيع دون ضغط أو وعود | 10% | 24/40 = 60% |

المتوسط الموزون في المثال = 73.75%، ويعرض مقربًا إلى **74%**. كل المحاور في بيانات المثال لها 40 حالة مؤهلة؛ لا تُنسخ هذه الفرضية إلى الإنتاج.

- عدد الحالات المؤهلة والاستبعادات يظهر لكل محور؛ لا يُحسب غياب الاعتراض فشلًا في معالجته، ولا تُعد الرسائل المتكررة عينات مستقلة.
- تعرض النتيجة مع الفترة وإصدار المعايير ومراجع الأدلة وتاريخ آخر تقييم. لا تقارن نسخ معايير أو شرائح غير متكافئة.
- عتبة 30 محادثة في المعاينة اختيار تصميم أولي، وليست ضمانًا إحصائيًا. يلزم معايرتها بحسب القطاع وتنوع السيناريوهات، وتحديد حد كفاية كل محور قبل الإطلاق.
- إذا نقصت الأدلة أو قدمت أو تعذر جلبها، تُعرض حالة غير كافية/قديمة/خطأ. لا يستبدل ذلك بصفر أو نسبة نجاح ثابتة، ولا تُعاد موازنة المهارات بصمت.
- لا يعتمد تقييم آلي على حكم النموذج عن نفسه فقط. يلزم معيار مراجعة محدد وأمثلة بشرية مرجعية، وتدقيق الأخطاء الحرجة مثل الأسعار والخصومات والشروط والوعود.
- نتيجة التحويل أو الإيراد لها لوحة قياس مستقلة؛ لا تعني نسبة 74% أن 74% من العملاء اشتروا أو أن المبيعات زادت.

## عقد البيانات اللازم للتنفيذ

| الجزء | البيانات المطلوبة |
|---|---|
| الملف | tenantId، sourceId، الإصدار وبصمة المحتوى، الاسم والنوع والحجم، تاريخ الرفع، حالة كل مرحلة ومعرّف محاولة المعالجة، خطأ آمن للمستخدم، الاعتماد والمراجع والتفعيل. |
| النتيجة | sourceId/version، sectionId، النص المستخرج والموضع المتاح فعليًا (صفحة/ورقة/صف أو مقطع)، تاريخ المراجعة، التعارضات، صلاحية الاستخدام. لا تُختلق إحالة صفحة إن لم يوفرها المستخرج. |
| الفجوة | النوع والأولوية وسببها، أسئلة منزوعة البيانات الشخصية، عدد الحالات المستقلة والفترة، المصادر المتعارضة، المالك، الحالة، التصحيح وسجل المراجعة وإعادة الاختبار. |
| تقييم المبيعات | assessmentId، rubricVersion، الفترة والشريحة، الحالات المؤهلة لكل مهارة، الاجتياز والفشل والاستبعاد، سبب الحكم ومراجع الأدلة، تاريخ المراجعة، حالة الكفاية والتقادم. |

يجب تطبيق عزل التيننت والصلاحيات على الخادم لكل قراءة واعتماد وتفعيل واختبار، وإبطال نتيجة الاختبار عند تغيير إصدار المصدر. لا يكفي إخفاء الزر أو الاعتماد على بيانات localStorage. عند التنفيذ ترتبط عمليات الاعتماد بسجل مراجعة ونسخة مصدر لمنع تطبيق مراجعة قديمة.
