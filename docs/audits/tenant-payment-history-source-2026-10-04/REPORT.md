# المرحلة 466 — مصدر سجل الدفع وتفاصيله

أضيفت payments.workspace.list/detail بعقد صارم ومصدر قراءة واحد. يحافظ المصدر على وصول المالك للسجلات المالية؛ أعضاء manager/viewer/sales_supervisor يتلقون حالة restricted دون قراءة صفوف الدفع. يعاد التحقق من المستخدم والمالك والعضوية وحالة المتجر داخل معاملة متسقة، ولا يكفي سياق جلسة قديم لتجاوز إلغاء العضوية.

القراءة تعرض25أو50سجلًا للصفحة، بترتيب التاريخ ثم المعرف، وتبحث في كامل بيانات التيننت بالاسم والرقم ومرجع Tap أو معرف السجل. البحث الحرفي يحمي % و_ ولا يفسر مدخل المستخدم كـSQL. مرشح الحالة والتاريخ والبحث نفسه يطبق على الإحصاء والصفحة؛ نهاية اليوم شاملة. لا يُحوّل تعذر قاعدة البيانات إلى أصفار.

الحالات السبع مستقلة، وauthorized لا يحتسب captured. كل عملة SAR/USD لها مجموع مبلغ المحاولات والمصرح والمحصّل والمسترجع مستقلة؛ لا تحويل صرف أو صافي ربح مفترض. القيم السالبة والعملة مجهولة الوحدة تستبعد من مبالغ الإجماليات مع عداد معلن وتظل سجلاتها قابلة للفحص. الأرقام غير الآمنة أو الإجماليات المتناقضة ترفض بدل تقريبها.

DTO صريح لا يحتوي metadata أو رابط تحويل الدفع أو نص خطأ المزود أو كوده. يوضح فقط وجود تشخيص مسجل. التواريخ غير الصالحة لا تُلف ليوم آخر؛ التوقيت المخزن دون منطقة يعامل كـUTC. روابط الطلب تتطلب ملكيته للتيننت، والحجز يتطلب ملكية الحجز والخدمة، والهدفان المتعارضان يُحجبان. لا تَظهر معرفات أهداف أجنبية في التفاصيل.

نجح تشغيل242حالة متداخلة، ثم41حالة للمصدر بعد إضافة فحوص التواريخ وتناقض الصفحات والمبالغ. نجحت12حالة MySQL تشمل51صفًا بترتيب ثابت، الفصل المالي، البحث الحرفي، حدود اليوم، الصلاحيات الحية، والسلاسل الأجنبية والمتعارضة. صححت عينات الاختبار لتتوافق مع اسم العميل الإلزامي وحالة الحساب deletion_pending، وأصلح فحص الأنواع استعمال MapIterator ليتوافق مع هدف المشروع. نجحت الأنواع والبناء النهائيان.

هذه بيانات سجلات محلية وليست استعلامًا مباشرًا من Tap أو إثبات تسوية بنكية. لا كتابة أو تحصيل أو ترحيل أو نشر في هذه المرحلة. الشاشات القديمة ومسارات list/getStats/getById ما زالت موجودة مؤقتًا إلى نقل الواجهة والموك أب ثم إغلاق القراءة القديمة. التالي تصميم السجل والتفاصيل وتصحيح تسمياتها وإزالة الأزرار الوهمية.
