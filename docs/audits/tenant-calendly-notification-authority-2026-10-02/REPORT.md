# المرحلة 344 — حراسة تأكيد Calendly عند واتساب

2026-10-02، main. المزوّد محاكى في الاختبارات؛ لا رسائل حقيقية أو رفع أو نشر.

## التنفيذ

أضيف حارس خاص بمفاتيح calendly: عند قناة واتساب. يُرفض المدخل القديم أو حذف الحارس أو طلب إعادة الإرسال التلقائي، وتُحفظ بيانات الحارس مع طلب القناة دون اعتماد المزوّد أو القناة.

قبل استدعاء المزوّد الفعلي، تُقفل موافقة واتساب الحالية وهوية الربط وحساب المالك ومحاولة الإيصال والموعد ونص التأكيد ورقم المستلم والقناة الأساسية. أي تغيير بعد قراءة القناة يمنع الإرسال. تستمر الأقفال خلال الاستدعاء وحفظ قبول القناة وعلامة قبول التأكيد على الموعد في معاملة واحدة. القبول لا يعني إثبات التسليم أو القراءة.

الموعد الملغى أو غياب الرقم أو سحب الموافقة يمنع إعداد رسالة. لا تُرسل علامة قبول سابقة مرة أخرى. النتيجة غير المحسومة أو المرفوضة لا تعاد تلقائيًا عبر نفس الإيصال، ولا يسمح حذف الحارس بتجاوز ذلك. مقارنة محتوى طلب سابق تمنع وصف نص أو رقم مختلفين بأنهما أُرسلا سابقًا.

أضيفت قدرة الإصدار calendly-notification-authority-v1 لوقف كاتب إشعارات قديم ومنع استعادته؛ أمر التحديث المعتمد محفوظ.

## التحقق

187 اختبارًا معزولًا و60 اختبار MySQL و123 اختبارًا للإصدار والتحديث ناجحة، مع نجاح الأنواع والبناء. تشمل الاختبارات opt-out والإلغاء وغياب الرقم، تغيير الرقم أو الموعد أو القناة أو الربط أو حالة المالك أو claim بعد قراءة القناة، العبث بالنص والحارس، نتيجة المزوّد غير المحسومة، عدم تكرار الإرسال، بقاء الأقفال أثناء الشبكة، وفشل حفظ القبول أو فقد تأكيد commit. شملت مجموعة MySQL تراجع إشعارات WooCommerce؛ الاختبارات المعزولة غطت القناة والحملات أيضًا.

عُدّل اختبار قراءة request_json ليدعم الكائن المفكوك تلقائيًا من mysql2، ثم أعيدت المجموعة كاملة. لم يتغير تحليل JSON في منطق القناة بسبب هذا التصحيح الاختباري.

## التالي والحدود

التحقق عند الإرسال يمنع تغييرات الصلاحية قبل خروج الطلب؛ تغيير الإعداد أثناء استدعاء مسموح ينتظر انتهاء المعاملة ولا يلغي رسالة خرجت للمزوّد بالفعل. النتيجة غير المحسومة تتطلب مراجعة ولا تعني فشلًا مؤكدًا. التالي واجهة Calendly الفعلية بكل أقسامها ثم الموك أب وفحص الريسبونسف وإغلاق مداخل الكتابة القديمة. لا Safari/iPhone فعلي أو نشر.
