# التفويض المحفوظ لإشعارات الطلبات

المرحلة414، 2026-10-03. أضيف الترحيل0199 لحفظ تفويض الإشعار ورمز حجز العامل. يحفظ تغيير حالة الطلب المراجع تفويضًا في المعاملة نفسها مع تغيير الطلب والإشعار وإيصال القرار. يرتبط التفويض بالتيننت والمالك والمراجع والطلب والمستلم والنص والحالة وإيصال الطلب وبصمة الطلب بعد التغيير والقناة الأساسية. لا تُستنتج تفويضات للسجلات القديمة.

تدخل هوية القناة وبصمة بياناتها في بصمة المراجعة. تغيير القناة أو بيانات اتصالها بعد المعاينة يرفض الحفظ قبل إنشاء الإشعار. لا تخزن وثيقة التفويض رمز اتصال القناة؛ تحفظ بصمته. يلزم تيننت نشط وقناة أساسية نشطة ومكتملة وإحدى القنوات الفعلية، وقالب صالح ومفعّل صراحةً. أضيف فحص حساب المالك مع حساب المراجع وصلاحيته الحالية؛ المشرف المسموح له بإدارة الطلبات يحتفظ بهويته كمراجع مستقل.

## التحقق

- نجحت84حالة وحدة: عقد التفويض، وبصمات القناة، والحقول غير الصالحة، ورفض القناة المفقودة أو المتعددة، وذرية تغيير الحالة وإيصالاتها، ومسارات الطلبات والعامل الحالي.
- نجحت47حالة MySQL، تشمل تدوير الرمز أو الحساب أو الوجهة، إيقاف القناة، قيود منع قناة أساسية ثانية، قالب قديم غير صالح، حساب مالك بانتظار الحذف، سحب عضوية المراجع، تزامن الطلبات المتطابقة، وعدم إنشاء إشعار عند عدم اختياره. أثبت اختبار تعارض قيد التفويض التراجع عن الطلب والإشعار والإيصال معًا.
- نجح فحص الأنواع وبناء التطبيق والخادم والعامل وميزانية الحزمة. نجحت39حالة لفحص الإصدار؛ أضيفت القدرة `order-notice-authorizations-0199` وتعليمات الترحيل في دليل التشغيل. بقي تحذير Vite المعتاد للحزم الكبيرة، مع نجاح الميزانية المحددة.
- طُبق0199 على قاعدة الاختبار المحلية المعزولة فقط. أنشأت الاختبارات تيننتات مؤقتة ونظفتها. لا إرسال خارجي أو نشر أو ترحيل لقاعدة الإنتاج.

هذه مرحلة تخزين التفويض والتحقق عند قبول قرار التاجر، وليست اكتمال حارس الإرسال. العامل القديم لا يقرأ التفويض بعد؛ التالي فرضه في خدمة واتساب والعامل، وربط استعادة الإرسال بإيصال مطابق، ومنع العامل المنتهي أو النتيجة المجهولة من إعادة الإرسال. رمز الحجز الجديد لا يستخدمه العامل القديم في هذه المرحلة.
