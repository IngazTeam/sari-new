# المرحلة491 — منع تطبيق ترقية على اشتراك تغير

أثبتت8حالات MySQL إخفاق السلوك السابق من10: كان التغيير ينجح رغم تغيير الباقة أو الدورة أو البداية أو النهاية أو الحالة، أو غياب نسخة المراجعة، وكذلك عند وصول تحصيل قديم أو تأكيد طلبين متزامنين.

أضيفت مقارنة لحقول الفوترة المراجعة داخل قفل صف الاشتراك وقبل تعديل الباقة. يشمل ذلك الباقة السابقة والدورة والحالة والبداية والنهاية مع تطبيع UTC والتحقق من صلاحية الفترة. يشترط أيضًا اشتراك نشط/تجريبي وحيد يطابق الهدف. لا تُقارن عدادات الاستخدام أو وقت تحديثها؛ تغيّرها العادي لا يعطّل الترقية.

يعيد مصدر مراجعة السعر نسخة حقول الاشتراك مع البصمة، ويستخدمها الراوتر كما هي في معاملة الدفع. يفحصها مرة ثانية قبل إنشاء المعاملة حتى لا يستبدل نسخة السعر القديمة ببيانات أحدث أثناء الطلب. الإقرار الفوري عند التعارض يعيد CONFLICT؛ التغيير والتحصيل المؤكد لا يسجلان مكتملين إن تعذر تطبيق النسخة.

## التحقق
160/160حالة وحدة وعقد وواجهة وأسعار وعزل. 21/21MySQL، منها11حالة تغيير باقة، مع تنافس طلبين وتعدد الاشتراكات الحالية وقراءة المصدر والإلغاء. 58/58فحص إصدار بعد إضافة capability تمنع مزج نسخة لا تحتوي الحماية. TypeScript وبناء الإنتاج والموك أب ناجحة. العينات مؤقتة ونظفت؛ لا تحصيل من مزود أو ترحيل قاعدة بيانات أو نشر.

## القيود والمتابعة
عند تأكيد المزود التحصيل ثم اكتشاف تعارض، تتراجع المعاملة المحلية وتبقى pending ولا يُعاد التحصيل تلقائيًا. هذا يمنع الكتابة فوق الحالة الجديدة، لكنه لا يسوي الأموال أو يردها؛ يلزم مسار واضح لاستعادة المحاولة وتسوية التحصيل وعرض التعارض. المعاملات القديمة الناقصة لنسخة الاشتراك ترفض التطبيق التلقائي وتحتاج مراجعة. الاشتراك الأول والتجديد والإضافات وتعويضات الاسترداد تحتاج مراجعات مستقلة. الرصيد ما زال مبنيًا على السعر الحالي للباقة، لا مبلغ السداد التاريخي. لا ادعاء اكتمال أمان الدفع أو النظام.
