# حماية نقل بانرات العروض — المرحلة 389

يحمل البانر الجديد هوية العرض وبصمة شروطه في خطة الرد وإيصال النقل. قبل الاتصال بالمزوّد تعاد قراءة صلاحية المتجر ومالكه، وأحدث رسالة وملكية المحادثة، وحجز الرد وحصته، والاشتراك والقناة والعرض. تبقى الأقفال حتى حفظ نتيجة المزوّد، فلا يمر تعديل متزامن لشروط العرض أثناء المحاولة.

يشترط النقل مطابقة البانر والنص الكامل والشروط والبصمة والخطة المحفوظة، وأن يكون العرض ساريًا على كل المتجر وقت النقل بحسب ساعة قاعدة البيانات. يمنع تغيير النطاق أو القيمة أو التاريخ أو إيقاف العرض بعد تجهيز الرد إرساله. عروض المنتجات والفئات تنتظر دليل أهلية طلب العميل. لا تُكتب عدادات مشاهدة أو نقر عند التجهيز أو الإرسال.

إعادة الطلب تطابق الجسم والحارسين المحفوظين، وحذف الحارس أو تغييره لا يتجاوز الحماية. نتيجة النقل المجهولة لا تعاد تلقائيًا. رفض أول أثر قبل الإرسال يعيد الحصة؛ وإذا سبق قبول النص ثم رفض البانر يحتفظ كل أثر بحقيقته دون ادعاء نجاح الرد كاملًا.

## التحقق

- نجحت 105 حالات وحدات وعقود نقل، و112 حالة MySQL تشمل العزل وتغير الشروط والرسائل المكررة والحصة والنتائج المجهولة وتزامن تعديل العرض مع النقل. لا فشل أو تخطٍ.
- فحص الأنواع ناجح، وبناء الإنتاج ناجح في 18.24 ثانية. نجحت فحوص الإصدار 28/28، وأضيف شرط `promotion-banner-transport-v1`.
- مزوّد الإرسال محاكى في الاختبارات؛ لم تُرسل رسائل خارجية ولم يحدث نشر.

## الحدود المتبقية

الحماية تثبت مصدر البانرات الجديدة ذات الحارس. لا يمكن نسبة وسائط الخطط القديمة غير الموسومة إلى عرض أو منتج بثقة؛ تحتاج سياسة مستقلة قبل استئنافها. فحص رابط الصورة هنا نحوي، ولا يثبت عنوان DNS أو محتوى كل تحويل أو ما سيجلبه المزوّد لاحقًا. لا تثبت هذه المرحلة نسبة تحويل مبيعات فعلية أو فحص Safari/iPhone أصلي.
