# المرحلة 79 — حفظ المنتج وإيصال العملية

## النتيجة

أضيفت واجهات `products.editor.read/write/receipt` لقراءة المنتج وإنشائه وتعديله بإيصال دائم، مع عقد حقول صالح للتصميم الجديد. واجهة المنتجات القديمة لم تتحول بعد؛ الحذف والمراجعة والواجهة والموك أب والاستيراد مراحل تالية، ولا يعني هذا إغلاق مخاطر الكتابات القديمة.

## الحماية وصحة البيانات

- معاملة واحدة لحفظ المنتج وإيصال الطلب، ومعرف UUID مرتبط بالتيننت والمنفذ والمدخلات. إعادة الطلب نفسه تعيد إيصال الحفظ الأصلي، وتغيير المحتوى أو المنفذ مع نفس المعرف مرفوض.
- قفل المتجر والمنتج وفحص الحساب والعضوية والصلاحية داخل المعاملة. العضوية المعطلة تمنع رجوع صلاحية المالك القديم. إيصال العملية يقرأه صاحبه داخل التيننت نفسه، حتى لو أصبح للقراءة فقط.
- بصمة تشمل صف المنتج كاملًا تمنع الكتابة فوق تعديل أحدث، بما فيه تعديل من API القديمة. اختلاف البصمة لا يمسح البيانات.
- قفل مصدر التكامل يُفحص في الخادم؛ قيمة مجهولة أو غير `none` تمنع الإنشاء والتعديل. المعرف الخارجي أو إسقاط WooCommerce/سلة/زد يمنع التحرير المحلي حتى لو مُسح إعداد المصدر العام. قواعد ظهور المتجر الحالي محفوظة.
- تحقق من طول النصوص والأعداد الصحيحة والحقول المعروفة وروابط HTTP/HTTPS والأسعار بلا تقريب. مرجع الفئة يجب أن يخص التيننت. يمكن تفريغ الحقول الاختيارية صراحة بـnull.
- الأسعار تدخل كنص عشري وتحفظ بالوحدة الصغرى. تعديل الاسم وحده لا يُجبر التاجر على إعادة تفسير سعر تاريخي. اعتماد سعر تاريخي جديد يمسح أسعار المقارنة والتكلفة غير المعتمدة إن لم تُقدم قيم جديدة. لا يُسمح بتبديل رمز عملة سعر محفوظ بلا مسار تحويل مستقل.
- عند حفظ الحالة يدويًا تُضبط `isActive` معها: المسودة والمؤرشف غير نشطين، والنشط مفعّل. هذا يمنع اختلاف عرض الحالة عن قراء المساعد التي تعتمد التفعيل.
- لا يُعاد اتصال قاعدة البيانات للمجمع عند غموض نتيجة commit أو فشل rollback؛ الاستعادة تستخدم الإيصال بدل إعادة إنشاء المنتج.
- استُعيد بحث التصنيف في مصدر المرحلة78 مع اختبار فعلي، بعد مقارنة سلوك القارئ السابق، إضافة إلى الاسم والوصف وSKU والباركود والاسم العربي.

## الإثبات

88 اختبار وحدة وعقد ناجحًا، و34 اختبار MySQL ناجحًا تشمل المحرر والكتالوج والأسعار وHTTP والجلسات. فحص الأنواع وبناء الواجهة والخادم والعامل وميزانية الحزمة نجحت. اختبارات MySQL تستخدم تيننتات مؤقتة وتحذفها بعد كل حالة، ولا تتصل بأي مزود خارجي.

السيناريوهات المثبتة: إنشاء متزامن بنفس الطلب دون تكرار، فوز تعديل واحد ورفض الآخر، تغييرات API القديمة، تفريغ الحقول، السعر المجاني والتاريخي، فصل العملات، فئة وتيننت أجنبيان، مصدر تكامل مقفل، تبديل الدور وتعطيله، فشل تخزين الإيصال مع التراجع، وفقد رد commit مع استعادة المنتج دون تكراره.

أضيف الترحيل `0173_product_editor_receipts.sql` والسجل وتعريف Drizzle. طُبق على `sari_pages_test` المحلية فقط دون تقديم سجل ترحيل قاعدة الفحص الأقدم. خادم الإنتاج يحتاج الترحيل ضمن التحديث المعتاد قبل استخدام الواجهة الجديدة؛ لم يُنشر شيء.

## الحدود والمتابعة

لا تتحكم هذه المرحلة في متغيرات المنتج أو خياراته أو حقول الدورات غير المعروضة في المحرر؛ تبقى بياناتها محفوظة بلا استبدال. واجهات CRUD القديمة والاستيراد والفئات والمتغيرات ما زالت تحتاج النقل والمراجعة، والحالات التاريخية غير المتطابقة لم تُعدّل جماعيًا. بصمة التعديل ليست مراجعة آثار الحذف؛ يعالجها المسار التالي. الواجهة والموك أب وSafari/iPhone الحقيقي لم تُختبر بهذه المرحلة، والتغطية ثابتة:79 عامًا و30 جزئيًا و9 تفصيلية و8 تحويلات.
