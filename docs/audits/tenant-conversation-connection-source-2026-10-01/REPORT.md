# المرحلة 227 — فحص اتصال المحادثات وإصلاح الاستقبال

أُلغي افتراض أن تعذر فحص المزود يعني نجاح الاتصال. يميز المصدر بين الاتصال المؤكد والانقطاع وعدم وجود رقم رئيسي والتعذر والإعدادات الناقصة والمزود غير المدعوم. تُقرأ الهوية من الرقم الرئيسي النشط الذي يستخدمه الإرسال، ويُعاد التحقق منها بعد القراءة. يستخدم Meta فاحصه المخصص، ولا تُرسل بياناته إلى Green API.

استُبدل إصلاح الـWebhook الذي كان يرسل رمز تحقق فارغًا. تستخدم العملية وسيلة الاتصال المحمية الموجودة بالمشروع، وعنوان التطبيق الموثق، ورمز HMAC مشتق على الخادم. لا تغير حالة قراءة الرسائل أو تأخير الإرسال أو الظهور متصلًا. اختلاف رقم جلسة المزود عن الرقم المسجل يمنع التعديل. لا يُعلن الإصلاح لمجرد HTTP 200؛ يُشترط saveSettings=true ثم قراءة الإعدادات والاتصال والتحقق من الرقم الرئيسي مجددًا.

بقي الاسمان connectionStatus وdiagnoseWebhook، وأضيفت هوية المتجر والحساب والرقم الداخلي وتاريخ الفحص وصلاحية الإدارة. وُحد تسجيل الإجراءين في الراوتر الرئيسي والمنفصل. أخطاء المزود وإعدادات التفويض والروابط والرموز لا تعود للمتصفح. لا يُدعى أن الفحص يمنع تغير المزود بعد انتهائه، أو أن سلامة الإعدادات تثبت وصول رسالة فعلية.

- نجحت 107 حالات للخدمة والصلاحيات وتوافق صفحة المحادثات ووسيلة Green API المحمية، و136 حالة لحصر الميزات، وحالتا MySQL لدورة مساحة إدارة واتساب؛ المجموع 245 دون فشل أو تخطٍ.
- تتضمن الحالات القراءة الإدارية وقراءة المشاهد، رفض التيننت أو الرقم المحقون، أخطاء المزود والتخزين، تغير الرقم الرئيسي، اختلاف جلسة الهاتف، غياب مفتاح التحقق، إعداد تطبيق غير صالح، وعدم اتساق تأكيد الإصلاح.
- نجح TypeScript وبناء المشروع. لا واجهة جديدة أو مفاتيح ترجمة في هذه المرحلة، ولا فحص بصري لها.

تحققنا من أن getSettings يعيد webhookUrlToken حسب [توثيق Green API](https://green-api.com/docs/api/account/GetSettings/)، ومن صيغة التفويض حسب [توثيق استقبال Webhook](https://elk.p03.green-api.com/en/docs/api/receiving/technology-webhook-endpoint/). جميع اتصالات الاختبارات محاكاة؛ لا تغيير لمزود حي ولا نشر. التالي توصيل حالات الاتصال بالواجهة وفصل الإصلاح الصريح عن المزامنة، ثم معالجة مسار استيراد المحادثات القديم الذي بقي خارج هذه المرحلة.
