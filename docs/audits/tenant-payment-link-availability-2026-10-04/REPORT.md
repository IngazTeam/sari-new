# المرحلة 469 — حقيقة إتاحة روابط الدفع

كشف فحص روابط الدفع أن getPaymentLinkAvailability كان يسمح بحالة expired إذا لم يكن تاريخ الانتهاء ماضيًا، وبحالات وأعلام وعدادات وتواريخ تالفة. تستعمل الدالة القراءة العامة وcheckout وإعادة استخدام رابط الطلب، لذلك لم تكن المشكلة محصورة بشارة الواجهة.

نُقل الشرط إلى ملف مشترك مع إبقاء التصدير السابق متوافقًا. تُرفض expired صراحةً حتى دون تاريخ أو مع تاريخ مستقبلي. لا يقبل علم التشغيل إلا1/true، ولا الحالة إلاactive، وتُرفض العدادات السالبة أو الكسرية أو النصية أو خارج المجال، وحد استخدام صفر، والتاريخ التالف أو اليوم المستحيل. تُقرأ السلاسل المخزنة دون منطقة زمنية كتوقيتUTC؛ يشمل المنع لحظة الانتهاء نفسها. تبقى الحالاتdisabled/completed والاستنفاد الصحيحة مميزة. سبب invalid يمنع اختلاق إتاحة أو انتهاء عند تعذر تفسير البيانات.

أثبتت39حالة اختبار قبل الإصلاح33إخفاقًا. نجحت217حالة في التشغيل الموسع بعده، بما فيها استدعاء المسار العام ومحاولةcheckout بأمثلة اصطناعية وإثبات عدم الوصول للمزوّد أو قراءات تالية. نجحت137من138حالةMySQL في التشغيل الأول؛ الحالة المتبقية كانت عينة بتاريخ2099 خارج مجال عمودTIMESTAMP. صُححت إلى2030 ونجحت الحالاتالخمس في إعادة اختبار الملف. اختبارات الطلب والحجز الأخرى ناجحة، والنقل للمزوّد محاكى. لا تحصيل فعلي أو تغيير بيانات إنتاج.

نجحت53حالة توافق إصدار والأنواع والبناء. أضيفت قدرة payment-link-availability-validated-v1 ودليل النشر لمنع الرجوع لإصدار يعيد إتاحة السجلات التالفة. لا ترحيل أو تعديل تلقائي للبيانات القديمة.

التالي مصدر وإدارة وواجهة روابط الدفع والموك أب. لم تختبر Safari/iPhone أو صلاحية بوابة حقيقية أو اختراق شامل، ولم يحدث نشر.
