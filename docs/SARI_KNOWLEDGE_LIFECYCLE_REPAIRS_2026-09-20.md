## ما نُفذ

1. **حذف لا يعلن نجاحًا جزئيًا:** deleteSource وresetBrain وحذف المستند من knowledgeDocs تستخدم خدمة واحدة ومعاملة واحدة. تشمل العملية صفوف المصدر والأقسام التابعة وسجل تغييراتها، وسجل العملية الجديد، وإبطال الردود والسياق الدائم. فشل آخر كتابة يرجعها جميعًا. أزيلت catch التي كانت تتجاهل فشل أجزاء الحذف ثم ترجع success.
2. **عزل صارم للمصدر:** معرف المصدر يتحقق من نوعه ونطاقه الرقمي وملكيته قبل الحذف. معرف منتج أو FAQ يطابق المتجر المختار، ومعرف موقع يجب أن يكون مملوكًا له. حذف المستند الحالي يحذف صفوف مستندات المتجر السابقة أيضًا، حتى لا يظهر مستند قديم بعد الحذف. ترتيب المستند الحالي حُسم بالتاريخ ثم المعرف عند تساوي التاريخ.
3. **حذف الأقسام التابعة كاملًا:** تحصر الخدمة الرسم البياني في أقسام المتجر، وتعبر جميع المستويات مع كشف الدوران، وتحذف على دفعات 500 معرف. لا يكفي parent_id أجنبي لإدخال صف من متجر آخر في الحذف. يعالج هذا خلل join القديم الذي قيّد متجر الأب دون متجر الابن، وكان يحذف مستوى أبناء واحدًا فقط.
4. **حماية بيانات الأعمال:** إعادة الضبط تحافظ على حساب المتجر والمحادثات والطلبات والمفاتيح. اختبارات MySQL أنشأت هذه البيانات وقارنتها بعد العملية، وكذلك كامل بيانات متجر آخر. حذف المنتجات والأسئلة الصريح يحتفظ بدلالته التدميرية السابقة؛ ليس أرشفة تلقائية.
5. **إبطال ضمن commit:** الكاتب الموحد للتحليل وخدمة حذف المعرفة يمسحان نصوص الردود المخبأة، ويضعان context_json بقيمة null نصية ويزيدان إصدار السياق وينهيان صلاحيته داخل المعاملة. تُمسح الذاكرة المحلية بعد نجاح commit فقط، والعمال يقرؤون الحالة الدائمة عند الرسالة التالية. invalidateCache يستخدم هذه العملية المشتركة أيضًا. حماية إصدار إعادة بناء جلسة موجودة لا تعني إلغاء كل عمل كان جاريًا قبل الحذف.
6. **تعامل محدد مع deadlock:** يعاد تنفيذ المعاملة كاملة مرتين كحد أقصى عند ER_LOCK_DEADLOCK الذي تعيد MySQL معه المعاملة، بما في ذلك الخطأ المغلف في Drizzle. لا تعاد محاولة انقطاع الاتصال أو فشل قيد أو lock timeout أو نتيجة commit غير معروفة. callback مخصص لكتابات قاعدة البيانات؛ لا اتصال خارجي داخله. اختبارات مستقلة تؤكد الحدود وعدم مسح الذاكرة بعد فشل المعاملة.
7. **حفظ التحليل الخلفي:** مسارا sariBrain وwebsiteAnalysis يحفظان الصفحات والأسئلة عبر محوّل واحد وكاتب التحليل الذري. أزيل حذف الصفحات/الأسئلة السابقة ثم إدخالها صفًا صفًا. الدمج تلقائي وإضافي: يحفظ الإجابات التي راجعها التاجر وقرارات التعطيل، ويضيف الجديد. يحتفظ بالمنصة وحالة التحليل بدل فرض unknown أو completed من هذه المرحلة الفرعية. يبقى تاريخ التحليلات السابقة بدل حذفه قبل حفظ التحليل الجديد.
8. **رفع HTTP واعٍ بالمتجر والصلاحية:** /api/knowledge-docs/upload يقرأ x-merchant-id ويثبت العضوية وصلاحية bot_settings.manage قبل حجز الحصة وMulter والتخزين والذكاء الاصطناعي. المالك والمدير مسموحان؛ المشاهد ومشرف المبيعات مرفوضان. الاختيار المشوّه 400، والمتاجر المتعددة بلا اختيار 409، والعضوية غير الصالحة أو المتجر الموقوف 403؛ تعطل التحقق 503. صفحة الإعدادات ترسل المتجر المختار وتعرض PDF/DOCX/XLSX المطابقة للأنواع التي يقبلها الخادم أصلًا.
9. **إعادة معالجة مستند محمية:** استُبدل fetch غير المحدود بتنزيل HTTPS عام يثبت DNS لكل اتصال ويعيد التحقق لكل تحويل. الحد 5MB، ووقت الطلب 10 ثوانٍ، وحد أقصى تحويلان، دون proxy تلقائي. يتحقق من توقيع PDF أو بنية Office وحدود الحزمة قبل استخراج النص، ويمرر XLSX إلى نوع المعالج الصحيح. الأنواع التاريخية غير المدعومة ترفض قبل التنزيل؛ لا تستبدل بيانات النص عند رفض التنزيل. أزيل تسجيل الاستثناء الخام في مسار إعادة المعالجة حتى لا يسرب رابط تخزين موقّعًا.
10. **بوابات دائمة:** أضيف ملف دورة الحياة إلى وظيفة MySQL في CI، وثلاثة ملفات للصلاحيات وإعادة المعالجة ومعاملة الإبطال إلى test:remediation. اختبار الحراسة القديم لإبطال الذاكرة يتتبع الخدمة الجديدة؛ الاختبار السلوكي الفعلي والتراجع في MySQL هما دليل صحة العملية.

## حدود الإصلاح والمتبقي

- الذرية تخص المصادر والمسارات المذكورة. مسارات API لإعادة ضبط مصدر تكامل، وبعض الكتابات اليدوية وتحديث المستندات وByaan وغيرها، لا تنضم تلقائيًا إلى معاملة حذف المصدر الجديدة.
- إبطال cache/context يزيل الموجود عند commit. يمكن لعمل بدأ سابقًا أن يولد نصًا أو قسمًا جديدًا لاحقًا، أو يعيد بناء أول جلسة أو كتابة رد مخبأ. يلزم knowledge generation دائم وفحصه في جميع الكتابات، مع إلغاء/تسييج المهام الجارية وoutbox دائم للتضمين. لم يُقدّم الإبطال هنا كحل كامل لهذا السباق.
- حذف المصدر ليس محوًا شاملًا: لا يحذف ملفات object storage أو النسخ الاحتياطية أو المحادثات القديمة أو البيانات السلوكية المستقلة أو نصًا نُسخ إلى مصدر آخر. مواقع وأسئلة ومنتجات مصادر منفصلة؛ غياب provenance تفصيلي يمنع نسبة كل معلومة مشتقة إلى المصدر المحذوف.
- حفظ الصفحات والأسئلة الخلفي أصبح موحدًا، لكن صف التحليل وبيانات الاتصال والمنتجات والمراحل اللاحقة منفصلة. بعض مراحل pipeline ما زالت best-effort؛ لا يوجد ضمان استئناف كامل بعد سقوط العملية، ولا ضمان أن كل فشل جزئي يمنع حالة completed النهائية.
- الدمج الخلفي لا يحدّث إجابة موجودة أو يعيد تفعيل صفحة معطلة تلقائيًا. تحديث المحتوى الذي راجعه التاجر يحتاج قرارًا صريحًا؛ توثيق هذه الدلالة جزء من الإصلاح.
- إعادة معالجة المستند أكثر أمانًا في حدود التنزيل، لكن الرفع والتخزين والتحليل والتضمين ومنافسة إعادة الرفع/الحذف لا تزال بحاجة إلى دورة دائمة واحدة. ضمان ذرية الحذف لا يعني أن رفعًا جاريًا لن يضيف معرفة بعده.
- لا migration جديد ولا اعتماديات جديدة. متطلبات ترحيل 0054 ومراجعة الأسعار التاريخية الواردة في الجولة السابقة تبقى قبل النشر. سقف الذكاء الاصطناعي 100 دولار للمنصة يوميًا، واختيار OpenAI/ZahyPi من السوبر أدمن، محفوظان.
- لم تُنفذ في هذه الجولة تجارب متصفح كاملة أو قبول حقيقي لـTap/Byaan/زد/سلة أو اختبار حمل أو استعادة إنتاج معزولة أو canary. كذلك تسعير الصوت ومطابقة الفواتير وجودة النماذج ودليل تجديد العملاء والهامش التجاري لا تثبتها اختبارات الكود.

3. حجز المخزون وتسوية الطلبات والآثار التجارية ومراجعة الأسعار السابقة، ثم قبول مزودي Tap/Byaan/زد/سلة على حسابات اختبار.
4. E2E واقعي وحمل ومراقبة واستعادة معزولة وpentest مستقل ونشر تدريجي موثق بالـSHA.
5. بطاقات أسعار وتكلفة صوت ومطابقة الفواتير، تقييم جودة الردود، وبيانات التجديد والهامش والقطاع الأول للعملاء الـ12.

لإعادة التحقق: `pnpm test:remediation`، وقائمة MySQL في `.github/workflows/ci.yml` بعد الهجرات على قاعدة اختبار محلية، و`pnpm check` و`pnpm audit:locales` و`pnpm test:tooling` و`pnpm build`. المقارنة الشاملة استعملت Vitest مع بيئة فارغة وحجب الاتصالات الخارجية. لا تُشغّل اختبارات حقن الفشل على الإنتاج.
