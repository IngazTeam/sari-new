# ربط تجربة البيع بقبول واتساب وتسلسل أول دفعة

استكمال بعد `9568fd55` على `main`. يربط التقرير `/admin/sales-experiments` تخصيصات التجربة بقبول النقل المسجل وأول قبض محفوظ لكل عميل. تبقى الخطة **4 مكتملة / 59 جزئية / 8 مفتوحة**؛ لا تمنح هذه الدفعة درجة 10/10 أو تثبت تحسن الإقناع والمبيعات.

## ما نُفذ

- يقرأ API البروتوكول والانسحاب والتخصيصات ووقائع الدفع والقبول وتفويضات الرد ضمن لقطة MySQL واحدة بمستوى `REPEATABLE READ`. يحجز صلاحية المشرف النشط أثناء القراءة فقط؛ لا تستخدم قراءات السجل التاريخي أقفالًا تجلب نسخة أحدث من بقية اللقطة.
- يتحقق من بصمات سجل القبول وتفويض الرد، وهوية التاجر والخطة والتخصيص والعميل والمجموعة والسياسة والقطاع والنافذة. يربط القبول بالرد والمحادثة والرسالة الواردة والمراجعة والمزوّد ورقم التفويض ومحتوى طلب الإرسال المحفوظ وتوقيت بدء الإرسال. لا يقرأ حساب واتساب الحالي أو يرسل طلبًا للمزوّد.
- يرفض السجل الناقص أو المتكرر أو المتعارض أو الملاحظة المستقبلية. الحد 20,000 سجل قبول للتجربة، و10,000 تخصيص و20,000 واقعة دفع للتاجر كما سبق؛ تجاوز أي حد يرفض القراءة كلها، ولا ينتقي عينة أو يعرض مقامًا مبتورًا.
- يحافظ على العملاء غير المشترين ومن لا يملكون سجل قبول ضمن مقام التجربة. يُعدّ العميل مرة واحدة مهما تكررت الردود، وتفصل أعداد السجلات عن أعداد العملاء.
- يفصل قبول النقل الفعلي بتوقيت متسق عن النقل التجريبي `mock` وعن القبول الفعلي الذي تراجع فيه توقيت الساعة. لا يُحسب الرد الذي يحترم رفض العميل أو يتابع طلبًا قائمًا كتطبيق لأسلوب السياسة المرشحة.
- يقارن جميع الردود بأول واقعة قبض محفوظة داخل نافذة كل عميل، عبر العملات والطلبات والحجوزات؛ لا يعيد بدء التسلسل عند دفعة ثانية أو استرجاع. تستخدم المقارنة الزمنية القاعدة نفسها في تشخيص الدفعة المفردة.
- الفئات الخمس حصرية للعملاء: قبول سابق للقبض؛ أو قبول لحظة القبض بعد بدء إرسال سابق؛ أو إرسال بدأ قبل القبض وقُبل بعده؛ أو إرسال بدأ لحظة القبض أو بعدها؛ أو عدم وجود قبول فعلي ذي توقيت متسق. تُطبّق هذه الأولوية عند تعدد الردود. عدد العملاء الذين لديهم أسلوب مرشح قبل القبض مجموعة فرعية من الفئة الأولى.
- تحجب مقارنة الدفع عند وجود إسناد معلق أو يحتاج مراجعة أو غير مسند داخل نطاق التقرير، حتى لو كان التعليق لاسترجاع. تبقى أعداد القبول ومقام العملاء متاحين. غياب قبض مسجل حالة غير مقاسة، وليس معدل تحويل صفريًا.
- تربط بصمة مجموعة الأدلة سجلات القبول وتفويضاتها؛ يتغير التقرير عند استعادة دليل متأخر دون تأريخ القبول بأثر رجعي. لا تعاد معالجة الدفع أو الاسترجاع أو إرسال الرد أثناء القراءة.

## الواجهة والعقد

أصبح إصدار التقرير `sales-experiment-readout.v2`. ترفض الواجهة الإصدار القديم أو غياب بيانات القبول أو تناقض المجاميع والمقامات وتسلسل القبض مع المال، بدل عرض تقرير ناقص يوحي بإكمال القياس.

تعرض بطاقتان للمجموعتين تغطية القبول، مع تفاصيل السجلات والتوقيت في أقسام قابلة للفتح بلوحة المفاتيح. تستخدم العربية والإنجليزية صياغة تفرق بين القبول والتسليم والقراءة والسببية. تبقى أعداد المال والعملات منفصلة، ويظل مقام التجربة مستقلًا عن وجود رد مسجل. يشمل فحص الجوال الأقسام الجديدة لا رأس الصفحة وحده.

## التحقق

نجحت **1,147 حالة دون فشل أو تخطٍ**: 584 للعقود والأمان والعرض والمسارات، و563 على MySQL. تتضمن هذه الدفعة 97 حالة جديدة: 59 لعقد التعرض، و23 للعقد المرئي وبياناته، و15 لربط السلسلة في SQL. أُعيد ملف التوليد والإرسال والتعافي بكامل حالاته الـ386، وليس الحالات الجديدة وحدها. التشغيل السريع الأولي الذي اختار 15 حالة فقط دليل تطوير؛ أرقام القبول هنا من التشغيل النهائي غير المقتطع.

نجحت **121 رحلة متصفح حديثة**: 73 لصفحة التجربة و48 لصفحة أدلة الطلبات. تشمل 16 رحلة إضافية لفئات توقيت التعرض بالعربية والإنجليزية، وفتح التفاصيل بلوحة المفاتيح واللمس بعروض 320–1440 بكسل، وفحص المفاتيح الخام والتمرير الأفقي، وإلغاء القراءات المتأخرة وفقد الصلاحية والاتصال. راجعت صورة تفاصيل التعرض العربية على الجوال والواجهة الإنجليزية على سطح المكتب بصريًا.

نجحت الأنواع و7,378 استدعاء ترجمة و244 مفتاحًا ديناميكيًا بلا نقص أو خطأ استيفاء، وسجل الترحيلات والبناء. ظل سجل الترحيلات عند 130 ترحيلًا. ثبّت المشغّل بصمات **1,923 ملف مصدر** قبل التشغيل وبعده وقبل حفظ الأدلة؛ لم تتغير المصادر بعد القبول.

هذا قبول محدد النطاق، لا إعادة للبوابة الشاملة السابقة ذات 10,004 حالات. الاختبارات الأمنية محلية والشبكة الخارجية محظورة، وليست بنتريشن إنتاج مستقلًا أو إرسالًا فعليًا لعميل. المتصفح Chromium ببيانات ونقل API محاكاة؛ ليس اختبار iPhone/Safari فعليًا أو رحلة إنتاج مسجلة الدخول.

تشمل حالات الأمان تبديل هوية التاجر والتخصيص والعميل، وإعادة حساب بصمة سجل متلاعب به، وتبديل تفويض الإرسال والمراجعة والمزوّد ومحتوى الطلب وتوقيت الإرسال، والسجلات المكررة أو الناقصة والمستقبلية وتجاوز الحدود. تشمل حالات المنطق حدود الملي ثانية، وغياب القبول، والنقل التجريبي وتراجع الساعة، ورفض العميل، وتعدد الردود والدفعات والعملات والاسترجاع، وعدم تسرب الهاتف أو نص الرد.

تستخدم اختبارات SQL سلسلة التسجيل والتخصيص وتوليد الرد ومراجعته وتفويض نقله وحفظ واقعة الدفع الفعلية في قاعدة مؤقتة، مع نواقل خارجية محاكاة. تختبر إضافة القبول أثناء القراءة، وحذف التفويض مع الحذف المتتالي للسجل، وإفساد التفويض بين قراءة القبول وقراءة تفويضه: تستمر اللقطة السابقة متسقة، وتظهر نتيجة التغيير في القراءة التالية فقط. تختبر أيضًا الاستعادة المتأخرة وعدم زيادة الإرسال أو استهلاك الحصة بسبب التقرير.

## الحدود والمتبقي

القبول هنا ملاحظة محلية محفوظة؛ لا يثبت وصول الرسالة أو قراءتها قبل الدفع. حذف السجل بسبب الاحتفاظ أو فقد الإسقاط قد ينقص تغطية الأدلة؛ لذلك اكتمال النقل غير مثبت، ولا يوصف العميل بلا سجل بأنه غير متعرض يقينًا. الاعتماد على أول قبض محفوظ لا يثبت أنه أول دفع في حياة العميل أو في كل مصادر التاجر.

يبقى قياس اكتمال مصادر الدفع والاسترجاع الجزئي، وتدخل الموظف، والمقياس الأساسي المسجل والاستدلال الإحصائي، واعتماد السياسة وتفعيلها والتراجع عنها. يبقى تقييم الإقناع بالنماذج والمزوّدين وقياس أثر البيع في تجربة فعلية مستقلة. نجاح محاكاة OpenAI/ZahyPi وواتساب لا يثبت جودة ردود النماذج الحقيقية.

لا تغيير للترحيلات أو مسار إرسال واتساب أو اختيار المزوّد أو سقف المنصة 100 دولار يوميًا. لم يُدفع الكوميت أو يُنشر على الإنتاج.
