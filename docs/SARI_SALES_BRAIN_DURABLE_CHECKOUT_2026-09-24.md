# محاولة دفع محلية محفوظة قبل الاتصال بـ Tap

التاريخ: 24 سبتمبر 2026. أساس الدفعة: `e460be9`. النطاق هو جلسة Tap التي تبدأ من رابط مربوط بطلب محلي، بعد اتفاق العميل واعتماد الفاتورة. الكوميت النهائي في سجل Git؛ لم ينفذ نشر أو دفع أو اتصال بمزوّد حقيقي.

**الخطة مستمرة: 4 مكتملة، 55 جزئية، 12 غير مغلقة.** هذه الدفعة تحسن B035 وB037 وB064 وB065 ولا تمنح اعتماد 10/10. [الخطة](./SARI_SALES_BRAIN_10_OF_10_PLAN_2026-09-23.md)، [مصفوفة القبول](./audits/sales-brain-implementation-2026-09-23/acceptance-matrix.md)، [ملف الأدلة](./audits/sales-brain-implementation-2026-09-23/evidence.json).

## سبب أولوية الإصلاح

أظهرت مراجعة تحرير الكوبون بعد إلغاء الطلب أن الإلغاء وحده لا يكفي: مسار `checkoutLink` كان يستدعي Tap أولًا ثم يحفظ `order_payments`. وجود مرجع idempotency ثابت لنقرة المتصفح يحمي بعض الإعادات، لكنه لا يغلق نافذة تعطل العملية بعد إنشاء الجلسة وقبل حفظها، ولا يمنع محاولة جديدة بمعرّف متصفح آخر.

أُنجز سجل دائم يسبق POST وقيد لمحاولة نشطة واحدة لكل طلب محلي. إذا كانت النتيجة غامضة لا يسمح مرور الوقت أو تغيير UUID بمحاولة جديدة. **تحرير استخدام الكوبون لم ينفذ في هذه الدفعة**؛ يتطلب أولًا تسوية نتيجة الدفع، ثم سياسة تحرير مستقلة. لم يُخفَ هذا المتبقي بتخفيض عداد الاستخدام عند الإلغاء.

## التنفيذ

1. يُقرأ الطلب والرابط مجددًا تحت قفل الطلب أولًا، بترتيب متوافق مع تسوية دفع Tap. يجب أن يكون الطلب محليًا وبحالة قابلة للدفع، غير مدفوع، وفاتورته معتمدة، وبنفس مبلغ وعملة الرابط الثابت. تُقرأ ساعة قاعدة البيانات بعد انتظار الأقفال لفحص صلاحية الرابط.
2. تُحمّل إعدادات Tap دون الاحتفاظ باتصال قاعدة مشغول ينتظر اتصالًا آخر. تُربط المحاولة ببصمة هوية الرابط والطلب والمبلغ والدافع ووصف الرابط وسياقه وحساب Tap ونمط الاختبار. المفتاح السري لا يُحفظ في سجل المحاولة.
3. يُحفظ `dispatching` وتُعتمد معاملته قبل أي POST. قيد فريد على عمود مولد يمنع وجود `dispatching` أو `unknown` أو `created` آخر لنفس الطلب، حتى مع كتابة تتجاوز قفل التطبيق. يوجد أيضًا قيد لمعرّف طلب المتصفح مع الرابط ومرجع Tap.
4. تستخدم الشبكة المبلغ الذي أُعيد التحقق منه والمرجع المحفوظ. استجابة Tap يجب أن تستوفي العقد الموجود للمبلغ والعملة والنمط والحالة والرابط المستضاف لدى Tap.
5. تُحفظ معاملة الدفع وحالة `created` ومعرف الدفع في معاملة SQL واحدة. فشل حفظ أي منهما يتراجع عنهما معًا ويحتفظ بحاجز المحاولة الغامضة.
6. إعادة الطلب أو تغيير UUID يعيدان رابط الجلسة المحفوظة إذا كانت بيانات الدافع والحساب والرابط مطابقة وحالة الدفع تسمح بذلك. لا POST جديد. تغيير هذه البيانات يرفض الإعادة بدل ربط جلسة شخص أو حساب بآخر.

الحالة `created` تعني أن الجلسة حُفظت، وليست إثبات تحصيل. الطلب يظل غير مدفوع حتى مسار التسوية الموثق الموجود. اختبار تكاملي يبدأ بخصم موافق عليه واعتماد الفاتورة ثم يفتح الجلسة بالمبلغ نفسه، دون زيادة عداد الكوبون مرة أخرى.

## حالات الفشل والإعادة

| الحالة | السلوك |
|---|---|
| نقرات متزامنة أو UUID مختلف أثناء POST | المحاولة الثانية لا تتصل بالمزوّد |
| فقد تأكيد commit الخاص بالحجز | قد يبقى `dispatching`؛ لا POST من الاستدعاء الفاشل ولا استعادة تلقائية لصلاحيته |
| مهلة أو قطع شبكة أو استجابة غير صالحة أو HTTP غير ناجح | `unknown`، دون افتراض أن إنشاء الجلسة لم يحدث |
| فشل حفظ علامة `unknown` أيضًا | يبقى `dispatching` حاجزًا؛ لا إعادة إرسال بسبب عطل التخزين |
| فشل كتابة الدفع أو ربط النتيجة | لا نصف حفظ؛ تبقى المحاولة للمراجعة |
| commit نتيجة ناجح مع فقد التأكيد | الشرط لا يستبدل `created` بـ`unknown`؛ إعادة المحاولة تقرأ الدفع المحفوظ دون POST |
| إلغاء الطلب أثناء POST | إذا بقيت هوية الطلب والرابط مطابقة، تُحفظ نتيجة الجلسة للمتابعة، ويُمنع تسليم رابطها للعميل |
| إشعار نهائي موثّق FAILED/DECLINED/RESTRICTED أو CANCELLED/ABANDONED/VOID | تسمح محاولة بمعرّف جديد بعد فحص بقية الشروط؛ المحاولة القديمة لا يعاد تشغيلها |
| UNKNOWN أو TIMEDOUT أو انقضاء زمن الجلسة وحده | لا يعد دليلًا كافيًا لإنشاء جلسة أخرى |
| AUTHORIZED | يمكن استرجاع الجلسة نفسها؛ لا إنشاء بديل |
| دفع قديم غير محسوم بلا سجل محاولة | يحجب إنشاء جلسة جديدة بدل افتراض غيابه |

لو تغيرت الهوية المالية أثناء الاتصال وتعذر حفظ النتيجة ضمن عقدها، يبقى الحاجز غامضًا للمراجعة. لا يعيد هذا المسار إنشاء أثر خارجي مفقود أو يحوله إلى نجاح تخميني.

## سجل التاجر والصلاحيات

تعرض تفاصيل الطلب المحلي آخر 10 محاولات: الحالة والمبلغ ووقت التحديث ومرجع Tap. القراءة تتطلب `orders.manage` وتستمد التاجر من العضوية الفعلية؛ لا يقبل العميل merchantId أو حقول توسيع خفية. السجل لا يعرض اسم الدافع أو هاتفه أو بريده أو المفتاح أو بصمة الطلب أو رابط الجلسة، ولا يملك زر إرسال أو تحرير أو اعتماد نتيجة.

الواجهة مترجمة للعربية والإنجليزية، مع حالات التحميل والخطأ وإعادة التحميل والسجل الفارغ. المرجع الطويل يلتف داخل عرض الهاتف، والنص يُعرض كنص لا HTML. الحالات الغامضة توضح وجوب مطابقة المرجع بسجل Tap قبل أي محاولة بديلة أو تحرير للكوبون.

## المخطط والنشر

الترحيل `0078_order_checkout_attempts.sql` مطبق على قاعدتي MySQL المحليتين `sari_brain_test` و`sari_brain_migration_test` فقط. تم التحقق من بصمة الترحيل، والعمود المولد الافتراضي، والقيود الفريدة الثلاثة. يستخدم العمود `VIRTUAL` حتى يعمل مع مرجع الطلب الخارجي والحذف المتسلسل في MySQL. أصلح الاختبار أيضًا استخدام دالة Drizzle غير مدعومة مع datetime قبل اعتماد النسخة النهائية.

فحص جاهزية المخطط في مسار الدفع يمنع تشغيله دون الجدول والعمود والقيود المطلوبة. يجب ترحيل الإنتاج وتحديث الويب والعمال وإيقاف النسخ القديمة قبل التشغيل. لا توجد إعادة بناء تخمينية لمحاولات قديمة خرجت إلى المزوّد ولم تُسجل محليًا؛ يجب مراجعة النتائج القديمة الغامضة لدى المزوّد عند النشر. لا تكفي إضافة الجدول وحدها لحماية عامل قديم ما زال ينفذ المسار السابق.

## المتبقي بعد هذه الدفعة

- استرجاع وتسوية نتيجة Tap الغامضة من المزوّد بمرجع مطابق، ثم إجراء مراجعة محفوظ يسمح بإغلاقها دون إعادة POST.
- سياسة تحرير استخدام الكوبون بعد إلغاء/استرداد مثبتين. عداد الخصم يبقى كما اعتمدته الفاتورة حاليًا.
- تعميم سجل المحاولات على الحجوزات والروابط العامة غير المرتبطة بطلب؛ مساراتها السابقة باقية ولا يشملها ضمان هذه الدفعة.
- توافق المزود الحي، ومعالجة وصول webhook قبل حفظ الدفع محليًا، والتسوية عند تغيّر الهوية أثناء الشبكة. لا تُعلن هذه الحالات مغلقة بمجرد نجاح المحاكاة.
- اتفاقات سلة وبيان، الرسوم الآلية وحجز المخزون، وجودة الإقناع والتعلم المقاس وبوابات النشر والقياس التجاري في الخطة.
