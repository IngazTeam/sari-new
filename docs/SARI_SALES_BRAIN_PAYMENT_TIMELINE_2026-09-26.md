# التسلسل الزمني للرد والدفع في التجربة البيعية

استكمال الخطة على `main` بعد `727fe1b0`. تضيف هذه الدفعة فحصًا تشخيصيًا لتوقيت الرد بالنسبة إلى قبض Tap المحلي. حالة الخطة **4 مكتملة / 59 جزئية / 8 مفتوحة**؛ البند B042 يحتاج أيضًا إثبات التسليم وتغطية الطلبات المعلقة والمصادر الخارجية قبل إغلاقه.

## ما أصبح متاحًا

يستطيع السوبر أدمن النشط قراءة `inboundOperations.salesPaymentTimeline` بإدخال `{merchantId, factId}`. تتحقق الخدمة من دوره وحالته في SQL لكل طلب، ومن ملكية النشاط والدليل، ثم من سلسلة الدفع والقبض الأصلي والتخصيص والبروتوكول وإيصالات الرد وإذن الإرسال. لا يختار المتصفح الممثل أو المجموعة أو العميل أو زمن القبض. تتطلب القراءة إسنادًا مكتملًا؛ لا تُشغّل إصلاحًا ضمنيًا للحالات المعلقة.

| النتيجة | معناها وحدودها |
|---|---|
| قبول النقل قبل القبض | بدأ الإرسال ورُصد قبول المزوّد قبل وقت التحقق المحلي من القبض؛ لا يثبت وصول الرسالة أو قراءتها أو تسببها في الدفع |
| قبول عند القبض | رُصد القبول والقبض عند المللي ثانية نفسها؛ لا أسبقية مفترضة |
| إرسال جارٍ عند القبض | بدأ الإرسال قبل القبض لكن رُصد قبوله بعده؛ لا يُعاد تأريخ القبول إلى وقت بدء الإرسال |
| بدء عند القبض أو بعده | لا يُصنّف الرد دليلًا سابقًا على القبض |
| تراجع الساعة | رُصد القبول قبل وقت بدء الإرسال المسجل؛ يُعزل من عدّ القبول السابق |
| نقل اصطناعي | `mock` محفوظ بصورة منفصلة ولا يدخل عدّ النقل إلى مزوّد حقيقي |

يفصل الفحص تطبيق أسلوب المرشح عن الردود التي لم تطبقه، مثل رفض العميل أو وجود طلب سابق، ويعرض توقيت كل إيصال وبصمته. ترجع قراءة الاسترجاع إلى ساعة القبض الأصلي، حتى إن وصلت رسائل أخرى بين الدفع والاسترجاع. يبقى صافي الحدث والعملة والموعد المثبت كما هما في إسناد الدفع؛ لا يجمع التقرير إيرادات مصادر متعددة.

لا يوجد اختيار لآخر رد بوصفه سبب البيع، ولا نسب نجاح أو اختيار فائز. تبقى `deliveryBeforeCapture` و`readingBeforeCapture` غير مقاستين، ومساهمة الموظف غير مقاسة، واكتمالية المصدر والسببية غير مثبتتين. لا تتغير مجموعة العميل أو مقام جميع العملاء المؤهلين المخصصين عند غياب إيصال الرد. القراءة لا تمنح الإرسال أو التعلّم أو جمع الإيرادات.

## سلامة القراءة والتعافي

- قفل مشاركة للنشاط ثم الأدلة، بالترتيب المستخدم في الكتابات، يمنع مزج حالة تخصيص قديمة بإسقاط رد أحدث أثناء الفحص. تختبر رحلة SQL انتظار الإرسال المتنافس حتى تنتهي القراءة، ثم ظهوره في القراءة التالية.
- يُقرأ 101 صفًا كحد أعلى لاكتشاف تجاوز سقف المئة؛ عند التجاوز لا تُعاد عينة جزئية على أنها التاريخ الكامل. الترقيم أو التصدير الشامل يحتاج مسارًا مستقلًا قبل الاعتماد التجاري.
- تتحقق البصمات والهوية والمبلغ والعملة والنافذة والمجموعة في الطرفين. حتى إعادة بصم إذن مختلف أو تغيير ساعة بدء الرد لا يجتاز ربطه بإذن الإرسال المحفوظ. التعارض يمنع التقرير ولا يغير الدفع المؤكد.
- الفحص لا يُنشئ سجلات، ولا يُعيد إرسال رسالة، ولا يتصل بالمزوّد أو AI، ولا يسوي ميزانية أو حصصًا، ولا يعيد محاولة إسناد. عند تعذر إنهاء معاملة القراءة تُتلف الوصلة غير السليمة، وتنجح محاولة جديدة بوصلة نظيفة.
- الاستجابة تحتوي معرفات أدلة وبصمات وأوقاتًا ومبالغ ونتائج تشخيصية؛ لا تحتوي الهاتف أو اسم العميل أو نصه أو الرد أو مفاتيح المزوّد أو معرّف رسالته الخام. أخطاء API منقاة ولا تعرض SQL أو البيانات الداخلية.
- `basisDigest` ثابت لنفس الأدلة، ويتغير إذا ظهر إيصال أثناء استرجاع لاحق. هذه قراءة حية قابلة للتحديث وليست حكمًا تجاريًا نهائيًا محفوظًا. حذف سجل التسليم الذي تتبعه إيصالات التعرض قد يخفض العدد؛ لذلك **صفر إيصالات لا يعني عدم تعرض العميل**، و`completeness` تظل `not_established`.

## التحقق على النسخة المجمدة

نجح **9464 اختبارًا باسم فريد** دون إخفاق أو تخطٍ في القبول النهائي، بإجمالي 13187 تنفيذ في مجموعات متداخلة. أضيفت **88 حالة اختبار**: 61 للعقد الزمني، و12 لصلاحية API، و15 لرحلات MySQL من التوليد والإرسال إلى الدفع. تمثل 85 اسمًا فريدًا لأن أربع حالات لتنقية أخطاء API لها الاسم المعروض نفسه؛ الأربع ناجحة وتُعد مرة واحدة في اتحاد الأسماء المحافظ. لم تُحذف حالة من القبول السابق.

| الفحص | النتيجة |
|---|---|
| unit | 3646 ناجحة |
| database | 3026 ناجحة |
| regression | 1073 ناجحة |
| legacy-sales | 229 ناجحة |
| budget | 11 ناجحة |
| security | 5202 ناجحة |
| TypeScript / build / Drizzle | ناجحة؛ الحزمة الرئيسية 102316 بايت gzip |
| الترجمة | 7196 استدعاء / 244 مفتاح ديناميكي؛ لا أخطاء |
| قاعدة جديدة | 126 ترحيلًا قائمًا من 0000 إلى 0125؛ لا ترحيل جديد |

طابقت بصمات **621 ملف مصدر** النسخة المجهزة للكوميت. تُحفظ مجموعات القبول وبصماتها في [ملف الأدلة](./audits/sales-brain-implementation-2026-09-23/evidence.json)، وسجل التشغيل في [دليل التحقق](./audits/sales-brain-implementation-2026-09-23/payment-timeline/verification.json).

لم تتغير مصادر الواجهة أو مفاتيح الترجمة؛ تحققت مطابقة 565 ملفًا من client/shared وfixtures وفاحصات المتصفح مع الكوميت السابق. أعيد استخدام 82 رحلة مكونات سابقة كدليل تاريخي فقط. **لا رحلات متصفح جديدة** ولا ادعاء اختبار Safari أو آيفون فعلي أو كامل 1166 رحلة. [دليل المطابقة](./audits/sales-brain-implementation-2026-09-23/ui/final-input-equivalence.json).

الاختبارات المركزة الأولى نجحت في 86 حالة، ثم 88 بعد إضافة تزامن القراءة والإرسال وفشل rollback. استُخدم ترشيح الحالات في التشغيل المركّز؛ الحالات غير المختارة ليست من دليل القبول النهائي. التشغيل النهائي يشمل جميع حالات مجموعاته دون ترشيح. رحلات المزوّدين وواتساب وTap تستخدم محاكاة وبيانات اصطناعية وشبكة خارجية محجوبة؛ لا قياس لإقناع نموذج حي أو اختبار اختراق مستقل على الإنتاج.

## أثر هذه الدفعة وما بقي

لا تعديل على المدفوعات أو الاشتراكات أو سقف المنصة اليومي البالغ 100 دولار، ولا جداول أو ترحيلات جديدة. الترحيلات القائمة حتى 0125 لازمة كما في الدفعة السابقة. لا توجد صفحة واجهة جديدة لهذا الفحص؛ المتاح الآن API تشخيصي محكوم بالصلاحية. لم يحدث push أو نشر.

مراجعة مصادر التجارة أكدت أن إسقاط زد المحلي يستخدم `orders.sallaOrderId = zid:<id>` ومرجع `sari_order_id`، بينما نتيجة الاتفاق الموثقة تحمل أيضًا هوية متجر زد. بيانات بيان الخاصة بإنشاء رابط الدفع أو إتمام التسجيل لا تثبت قبضًا ماليًا من بوابة المعهد. لم تُدمج هذه الإشارات مع Tap بالتخمين؛ لا تغيير على مسارات سلة وزد وبيان ضمن هذه الدفعة.

المتبقي المتصل بهذه المرحلة:

1. توحيد هوية الطلب ومصدره وحساب المزوّد عبر سلة وزد وبيان وTap، وربط الاتفاقات والطلبات غير المدفوعة، ثم منع التكرار عبر المصادر.
2. إيصالات تسليم/قراءة موثوقة بأوقاتها، وفحص اكتمال التغطية وفجوات العمال والاحتفاظ؛ ترتيب الملاحظات المحلية هنا لا يثبت زمن عملية الدفع الأصلية عند المزوّد.
3. الاسترجاع الجزئي والمساعدة البشرية، وتقرير على مستوى التجربة بمقام ثابت وقطاع وعملة ونافذة قرار، مع معالجة البيانات الناقصة بدل حذفها.
4. واجهة التقرير، وتثبيت حكم قابل للمراجعة والتعلم المعتمد، والتقييم الفعلي متعدد الأدوار والمراجعة المستقلة والأثر التجاري.
5. بقية التشغيل: حصص الإشعارات الأخرى، وتسوية الحالات الغامضة، والاحتفاظ والتفعيل المحدود والتراجع.
