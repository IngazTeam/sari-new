# حدود عمليات التسجيل وروابط الدفع في بيان

استكمال البنود B033 وB036 وB037 وB041، فوق `65161cd4`، بتاريخ 28 سبتمبر 2026.

## الخلل والإصلاح

كان عميل بيان يعيد `success: true` لأي استجابة HTTP ناجحة، ولو كانت تحمل `success: false` أو لا تحتوي على معرّف تسجيل أو فاتورة صالح. وكانت روابط الدفع تعاد دون تحقق، وأخطاء التتبع المحلي تختفي داخل catch. قد يؤدي ذلك إلى تأكيد نجاح لم تثبت نتيجته أو الخلط بين إنشاء رابط والتحصيل.

أضيف عقد لمدخلات التسجيل وإنشاء رابط الدفع: هوية نشاط محددة، رقم هاتف موحد، مرجع دورة، اسم وعنوان محدودان، ومبلغ موجب بدقة منزلتين. لا يرسل المدخل غير الصالح إلى المزوّد. بقيت مسارات الطلبات وأسماء حقولها القائمة؛ يحفظ نوع معرّف الدورة النصي أو الرقمي في الطلب الموقّع.

تقبل الاستجابة أسماء المعرّفات والروابط القائمة بصيغتي snake_case وcamelCase. يلزم مرجع تسجيل للتسجيل، ومرجع فاتورة ورابط لعملية الدفع. تعارض الصيغتين أو الرفض الصريح أو بيانات ناقصة/غير صالحة لا يتحول إلى نجاح. تقبل المعرّفات الرقمية الصحيحة وتحفظ نصيًا بدل ضياع تتبعها بسبب اشتراط سجل التحويلات لنص.

روابط الدفع محدودة الطول، تستخدم HTTPS بلا بيانات دخول أو منفذ مخصص أو جزء fragment أو محارف تحكم. لا تُتبع الروابط أثناء التحقق ولا ترسل إليها أسرار. هذا تحقق في بنية الرابط، وليس اعتمادًا لبوابة الدفع أو إثباتًا لتحصيل المبلغ.

## صلاحيات الإرسال والنتيجة

يُفحص اتصال بيان الموثق والنشط، والنشاط ومالكه، ثم يعاد الفحص بعد حل DNS وقبل الإرسال. تغيير الاتصال أو السر أو التوثيق أو حالة الحساب في تلك الفترة يمنع الطلب. لا يقفل هذا الفحص حساب المزوّد طوال اتصال الشبكة؛ يبقى ضبط الاتفاق والموافقة وسجل محاولات التنفيذ الدائم مطلوبًا.

| النتيجة | معناها |
| --- | --- |
| `not_sent` | لم يرسل الطلب بسبب المدخلات أو الجاهزية أو الصلاحية |
| `unknown` | بدأ الإرسال دون الحصول على نتيجة مكتملة قابلة للقراءة؛ يحتاج تسوية |
| `reported` | أعاد المزوّد مرجعًا وبيانات تستوفي عقد القراءة المحلي |
| `tracking: recorded` | حفظ البلاغ وتاريخه محليًا وأعيد معرّفه |
| `tracking: unavailable` | النتيجة الخارجية مقروءة، لكن حفظ التتبع تعذر؛ لا تعاد عملية المزوّد بسبب ذلك |

لا تُعاد محاولة POST تلقائيًا. إرجاع `retryable: false` للحالات غير الناجحة يمنع تقديمها كمحاولة آمنة؛ لا يساوي ذلك منعًا دائمًا للتكرار عبر استدعاءات جديدة من خارج الدالة.

يبقى التسجيل `enrollment/completed` بلاغ تسجيل، والرابط `payment/pending`. المصدر في التاريخ `internal_unverified`، وتظهر `paymentEvidence: not_verified`. لا ينشأ حدث قبض أو شراء مثبت أو تعلم من النتيجة. فشل حفظ التتبع لا يغيّر استجابة المزوّد إلى رفض مزعوم ولا يسبب طلبًا ثانيًا.

أصبحت أخطاء النقل عامة، دون إعادة أو تسجيل رسائل المزوّد التي قد تحتوي على بيانات عميل أو ترويسات توقيع. يمنع النقل التحويلات التلقائية ووكيل البيئة، ويحد حجم الطلب والرد ويشترط JSON قابلاً للقراءة.

## التحقق

نجح **268 اختبارًا**: 212 للوحدات والأمن في 14 ملفًا، و56 على MySQL في ملفين، دون فشل أو تخطٍّ. منها 63 حالة جديدة لحدود بيان و18 حالة جديدة على SQL. نجح فحص الأنواع والبناء وفحص 7996 استدعاء ترجمة و311 مفتاحًا ديناميكيًا دون نقص أو خطأ. [نتائج التحقق وبصمات المصدر](./audits/sales-brain-implementation-2026-09-23/byaan-sales-boundary-verification.json). لم يُعد فحص المتصفح لهذه الدفعة التي لا تغيّر الواجهات.

الاختبارات تحاكي HTTP وDNS للمزوّد وتحجب الشبكة الخارجية. تستخدم حالات SQL قاعدة محلية مصطنعة وتنفذ فعلًا قراءة الاتصال والصلاحيات وحفظ التحويل وتاريخه. تشمل تغيّر الصلاحيات أثناء حل DNS، وتعليق النشاط بعد استجابة المزوّد، والنتائج الخاطئة، وعزل الأنشطة، وعدم إنشاء حقائق مالية.

لم تتغير واجهة مستخدم أو مفتاح ترجمة أو مخطط قاعدة بيانات. لا ترحيل جديد في هذه الدفعة. لا اختبار لحساب بيان حي أو عملاء أو دفع حقيقي.

## حدود الإنجاز والمتبقي

هذا تقوية للدالتين القائمتين `enrollTrainee` و`createPaymentLink`، وليست إضافة ربط تلقائي جديد بمحادثات واتساب. لا توجد في النسخة المفحوصة استدعاءات إنتاجية لهاتين الدالتين خارج تعريفهما؛ يلزم وصلهما لاحقًا بعقد الاتفاق والموافقة بعد اعتماد مزوّد التشغيل.

ما زال يلزم عقد بيان الحي، وإثبات علاقة العميل والدورة والتسجيل والفاتورة والدفع والعملة، ومفتاح عملية دائم مع تسوية الأثر المجهول، ومنع الازدواج مع Tap، ثم ربط النتائج المالية المثبتة بالتعلم. لا تدّعي الاختبارات المصطنعة إثبات هذه الأمور. تبقى المصفوفة **4 مكتملة / 62 جزئية / 5 مفتوحة**، ولا اعتماد 10/10 أو نشر للإنتاج.
