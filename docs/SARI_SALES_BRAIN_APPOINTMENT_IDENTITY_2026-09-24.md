# هوية دائمة لطلب إنشاء موعد واسترداد نتيجته

التاريخ: 24 سبتمبر 2026. استكمال بعد `c32bb4d7`. النطاق هو إنشاء المواعيد من مساري Calendar API المركب والمستقل. لا نشر إنتاجي أو اتصال Google حي في هذه الدفعة.

## المشكلة والنتيجة

كان قفل السعة يمنع تكرار الحجز، لكن ضياع رد HTTP أو تأكيد commit يجعل إعادة الطلب تبدو كتعارض جديد، دون طريقة لاسترداد نتيجة العملية الأصلية. وبعد إلغاء الموعد أو حذفه، كان الطلب المعاد يستطيع إنشاء موعد آخر لأن السعة أصبحت متاحة.

أصبح الإنشاء يحتاج UUID يحتفظ به المستدعي منذ المحاولة الأولى. تحفظ هوية الطلب، وهوية الموظف، وبصمة المحتوى، ومرجع الموعد في المعاملة نفسها التي تحجز السعة. إعادة الطلب نفسه تسترد الموعد القائم وحالته الحالية؛ لا تنشئ موعدًا أو حدث Google آخر. يظل سجل الطلب موجودًا عند حذف الموعد أو حذف خدمته، ويمنع إعادة إنشائه بهوية قديمة.

| الحالة | السلوك |
|---|---|
| طلب جديد صحيح | فحص الملكية والسعة، ثم حفظ الموعد وهوية الطلب معًا، ثم إرسال Google عند توفر الربط. |
| الطلب نفسه والمحتوى والموظف نفسيهما | استرداد المرجع والحالة الحالية، حتى بعد تعطيل الخدمة أو تغير سعرها أو مدتها. لا تطبيق للأسعار الجديدة على الموعد القديم. |
| عدة طلبات متزامنة أو عمال مستقلون | فائز واحد بإنشاء السجل، والبقية تسترد المرجع نفسه تحت قفل السعة المشترك. |
| UUID نفسه مع محتوى أو موظف مختلف | رفض دون إعادة إنشاء أو إرسال؛ UUID وحده ليس تفويضًا. |
| UUID نفسه لدى تاجر آخر | نطاق مستقل؛ لا يستطيع قراءة موعد التاجر الأول. |
| الطلب الأصلي لا يزال ينتظر Google | الاسترداد يعرض `creating` ولا يرسل POST آخر. |
| مهلة، خطأ اعتماد، أو تأكيد Google غير مطابق | حفظ `create_unknown` واستردادها دون إعادة إرسال تلقائي. |
| فقد تأكيد commit قبل POST | استرداد الموعد المحجوز؛ لا يفترض أن إرسال Google بدأ أو لم يبدأ. تبقى `creating` بحاجة إلى تحقق. |
| فقد تأكيد commit بعد نجاح POST | استرداد الحالة المحفوظة دون POST إضافي. |
| إلغاء أو اكتمال أو عدم حضور لاحق | تعرض حالة الموعد الحالية؛ لا يعود إلى `confirmed` ولا يحجز السعة مرة أخرى. |
| حذف الموعد أو حذفه تبعًا لحذف الخدمة | تبقى هوية الطلب؛ القراءة ترجع `appointment_unavailable`، وإعادة الإنشاء بهويته ترفض. |
| فشل كتابة هوية الطلب | تتراجع مع الموعد في المعاملة نفسها؛ لا ينفذ Google. |
| رفض السعة قبل الحفظ | لا يحفظ طلب ناجح وهمي؛ يمكن إعادة المحاولة بالهوية نفسها بعد معالجة السبب. |

## عقد API والصلاحيات

`calendar.bookAppointment` يحتاج `requestId` بصيغة UUID بالإضافة إلى الحقول السابقة. الحقل إلزامي؛ لا ينشئ الخادم UUID عشوائيًا بديلًا لكل محاولة لأن ذلك يفقد منع التكرار. تُوحّد حالة الأحرف في UUID. البصمة تبنى من حقول صريحة بعد التحقق والتطبيع، وتشمل التاجر والموظف والخدمة والعميل والموعد والملاحظات؛ لا تعتمد على ترتيب مفاتيح JSON.

يرجع الإنشاء `requestId` و`appointmentId` و`appointmentStatus` و`calendarSyncState` و`replayed` و`state: recorded`. الحقل السابق `success: true` يعني أن طلب الإنشاء محفوظ؛ يجب قراءة حالة الموعد والمزامنة لمعرفة وضعه الحالي، فقد أصبح الموعد ملغيًا أو مكتملًا عند الاسترداد.

`calendar.getBookingRequest({ requestId })` قراءة منفصلة لا تتصل بـGoogle. ترجع واحدة من:

- `not_found`: لا يوجد طلب محفوظ بهذه الهوية ضمن التاجر عند القراءة. إن كانت المحاولة الأصلية متأخرة، يبقى استعمال UUID نفسه شرطًا لمنع التكرار.
- `recorded`: مرجع الموعد وحالته التشغيلية وحالة مزامنته الحالية.
- `appointment_unavailable`: الطلب محفوظ، لكن الموعد لم يعد متاحًا. لا يعاد إنشاؤه تلقائيًا.

الإنشاء والقراءة يحتاجان `orders.manage`، والتاجر والفاعل من العضوية والجلسة. قراءة هوية الطلب مقيدة بالفاعل الذي أنشأها؛ إدارة المواعيد الأخرى تبقى عبر قائمة التقويم وصلاحياتها. لا تقبل هوية موظف أو تاجر أو موعد من حقول lookup، ولا تسرب القراءة هاتفًا أو اسمًا أو ملاحظات أو بصمة اعتماد أو مرجع Google.

على المستدعي الاحتفاظ بـUUID والمحتوى الأصليين حتى يحصل على نتيجة موثوقة. عند timeout يقرأ النتيجة أو يعيد الطلب نفسه؛ لا يولّد UUID جديدًا أو يغير العميل/الوقت في محاولة استرداد. طلب جديد بهوية جديدة يمثل نية حجز جديدة، ويظل خاضعًا للسعة والصلاحيات.

لم يظهر مستدعٍ لـ`bookAppointment` داخل واجهة العميل الحالية عند مراجعة الشفرة. أي مستدعين خارجيين أو نسخ قديمة يجب تحديثهم لإرسال `requestId` قبل تفعيل العقد الجديد. مسارات واتساب القديمة و`db.createAppointment` ما زالت تستخدم فحص السعة نفسه، لكنها لم تُنقل إلى عقد الموظف هذا؛ لا ندعي أن إصلاح API يغلق موافقة العميل أو هوية رسالة واتساب.

## الترحيل والتحقق

الترحيل `0088_appointment_creation_requests` يضيف جدولًا جديدًا فقط، بقيد فريد للتاجر وUUID وآخر للتاجر ومرجع الموعد. لا FK من الطلب إلى الموعد أو الخدمة؛ FK التاجر يحذف السجل مع حذف بيانات التاجر. لا يخمن هوية للطلبات القديمة ولا يخزن نص محتوى الطلب؛ يحتفظ ببصمته ومرجعه. يلزم تحديث المخطط والمستدعين والويب والعمال معًا قبل الاستخدام الإنتاجي.

طُبق الترحيل على قاعدتي MySQL محليتين. [دليل المخطط](./audits/sales-brain-implementation-2026-09-23/appointment-request-migration.json) يتضمن بصمة SQL وسجل الترحيل والفهارس وعلاقات الحذف. بصمة SQL الخام: `d4443365d7460b468de52d728c2189e1bc461f5622e8851eb814b3b8411d6399`.

اختبارات الإصلاح المباشرة: **37 اختبار MySQL**، بما فيها عمليات مستقلة وإعادة تشغيل عامل، و**76 اختبارًا لمساري API** بعد إضافة حالات هوية الطلب والقراءة. فحوص السعة والمزامنة والمراجعة السابقة بقيت ضمن الانحدار. الاتصال الخارجي محجوب؛ Google مصطنع في الاختبارات.

نجح **4951 اختبارًا فريدًا** دون إخفاق أو تخطي، بإجمالي 6197 تنفيذ اختبار يشمل التكرار بين المجموعات. جميع التقارير من نسخة مستقلة للملفات المحضرة للكوميت، مع مطابقة بصمات 286 ملف مصدر.

## المتبقي

- اتفاق الحجز وموافقة العميل داخل محادثة المبيعات، وربط الهوية برسالة واتساب أو جلسة الاتفاق بدل هوية إجراء الموظف فقط.
- معالجة مؤكدة لفشل العامل قبل إرسال Google. إعادة الطلب الحالية لا تعيد POST، وقد تبقى السعة محجوزة عند غياب حدث يمكن التحقق منه.
- سياسة الدوام والعطل والفواصل والسعة الجماعية وCalendly، والتحقق المستمر من تغييرات Google الخارجية.
- اعتماد التكاملات الحية والنشر المرحلي وقياس أثر البيع. لا تغييرات على اختيار OpenAI/ZahyPi من السوبر أدمن أو سقف المنصة 100 دولار يوميًا.

تتقدم أدلة B035 وB037 وB064 وB065، وتبقى حالة الخطة **4 مكتملة / 55 جزئية / 12 غير مغلقة**؛ لا اعتماد 10/10 بهذه الدفعة.
