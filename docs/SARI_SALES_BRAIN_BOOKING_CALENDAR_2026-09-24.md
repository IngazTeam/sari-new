# مزامنة الحجز مع Google واستعادة نتيجة الإرسال

24 سبتمبر 2026، بعد `90c558c4`. تنفيذ واختبارات وترحيل محلي ببيانات مصطنعة، دون إنشاء أحداث فعلية أو إرسال رسائل للعملاء أو نشر على الإنتاج.

## الفجوة المعالجة

مسار المحادثة يحفظ اتفاق العميل والحجز محليًا، لكن التأكيد المحلي لا يثبت وجود موعد في Google. أضيف مسار صريح داخل إدارة الحجز لإرسال الموعد المؤكد إلى الحساب المتصل، ثم التحقق من نتيجته وربطه بالاتفاق الحالي. لا ينشئ صفًا ثانيًا في سجل appointments.

كذلك أُصلح عطل فعلي في المزوّد: `validateAndRefreshCredentials` كان يستخدم ناتج إنشاء OAuth غير المنتظر كما لو كان عميلًا جاهزًا، مما يفشل الاتصال قبل التحقق من الرمز. ينتظر الآن إعداد العميل، ويتحقق من صلاحية الرمز أو يجدده مع حفظ هوية التفويض الأصلية، ويعيد أخطاء عامة دون أسرار. لا يفسر انقطاع الشبكة أو 429/5xx كدليل انتهاء صلاحية يستدعي تجديدًا إضافيًا. مهلة طلب النقل 15 ثانية وإعادة المحاولة التلقائية معطلة للنقل ولطلبات كتابة الأحداث.

## الرحلة والعقد

1. موظف لديه `orders.manage` يفتح حجزًا مؤكدًا محليًا، ذا اتفاق عميل صحيح وفترة متاحة، وحساب تقويم واحد صالح.
2. يرى الحساب والحالة، ويكتب سببًا ويصدق على مراجعة الموافقة والموعد. لا يستطيع إرسال معرف حساب أو حدث أو نشاط أو فاعل بديل.
3. يقرأ الخادم توفر الفترة من Google، ويرفض الرد الناقص أو المشغول أو المتعذر قبل حجز محاولة إرسال. يعيد بعدها فحص الدليل والملكية والسعة في معاملة النشاط، ويمنع تداخل إرسالات هذا المسار إلى التقويم نفسه حتى للخدمات المختلفة.
4. يحفظ مرجع حدث عشوائيًا صالحًا وصلة بالحجز والاتفاق والفاعل والطلب والحساب وبصمته، وسبب المراجعة ودليلها، قبل أي إنشاء خارجي.
5. يرسل إنشاء الحدث مرة واحدة. مطابقة المعرف والخاصية الخاصة للاتفاق والتوقيت الصريح وحالة الحدث تثبت الربط؛ مجرد HTTP ناجح أو وجود `id` لا يكفي.
6. إذا انقطع الرد أو اختل الدليل، تبقى الفترة محفوظة ويظهر احتياج للتحقق. إعادة الطلب لا تعيد إنشاء الحدث. يستخدم الموظف إجراء التحقق الذي يقرأ المرجع نفسه من الحساب الأصلي.

| الحالة | السلوك المثبت |
|---|---|
| حجز pending أو موافقة ناقصة أو رفض لاحق أو فترة غير متاحة | يرفض إرسال الحدث. |
| أكثر من حساب تقويم نشط أو اعتماد غير صالح | يرفض بدل اختيار حساب عشوائي. |
| تغيّر الدليل أثناء فحص التوفر الخارجي | يرفض قبل تسجيل الإرسال أو كتابة الحدث. |
| تغيّر الموافقة أو الحساب أثناء كتابة الحدث | يحفظ الغموض؛ لا يقرر أن الربط الصحيح قد اكتمل. |
| طلبان متزامنان لإنشاء الحدث | سجل إرسال واحد واستدعاء إنشاء واحد؛ الآخر يسترد النتيجة المسجلة. |
| فقد تأكيد حفظ سجل الإرسال | لا تعاد الكتابة إلى Google؛ يلزم التحقق من المرجع بعد انقضاء مهلة العامل. |
| فشل حفظ التدقيق بعد رد Google | يتراجع الربط المحلي مع التدقيق وتبقى المحاولة قابلة للتحقق بالقراءة، دون إعادة الإنشاء. |
| فقد تأكيد الحفظ النهائي | يعيد الطلب النتيجة المحفوظة دون استدعاء إنشاء ثانٍ. |
| مرجع أو اتفاق أو تاريخ/وقت مختلف، حدث متكرر أو غير نشط | لا يثبت الربط. |
| GET يعيد 404 أو 410 أو خطأ مصادقة/نقل | لا يعتبره إلغاءً أو مبررًا لإعادة الإنشاء. |
| تغيير حساب التقويم أو تفاصيل الحجز المرتبط | يمنع التحقق من هدف بديل؛ يحتاج مراجعة الارتباط الأصلي. |
| محاولة creating لم يتجاوز آخر تحديثها دقيقتين | يحجب إجراء التحقق حتى لا يتسابق مع عامل ما زال نشطًا. |
| إلغاء أو حذف أو تغيير موعد محلي لارتباط محفوظ | يحجب تحرير الفترة؛ يلزم مسار خارجي منسق لم يُضف في هذه الدفعة. |
| إكمال/عدم حضور قبل نهاية فترة مرتبطة | يرفض التحرير المبكر. يسمح بالتقدم إلى in_progress بعد تحقق المزامنة؛ الإنهاء يتطلب مرور نهاية الفترة. |

النتيجة `synced` تصف آخر تحقق من وجود حدث مطابق، وليست مراقبة مستمرة للتغييرات الخارجية أو إثبات تحصيل مالي. فحص FreeBusy وإنشاء الحدث طلبان منفصلان؛ لا توفر هذه الدفعة قفلًا على تغييرات Google المباشرة أو التكاملات الأخرى أثناء الفاصل بينهما. التغييرات الخارجية اللاحقة تحتاج تحققًا صريحًا، والتاريخ القديم والسجل الآخر ليسا موحّدين بهذا المسار.

## الواجهة والأمان

لوحة بالعربية والإنجليزية، مع حالات تحميل وفشل وغموض وانشغال وتغير الحساب، وسبب وتصديق يتجددان عند تغير الدليل أو الحجز. تمنع النقرة المكررة وإعادة الإرسال العمياء بعد فشل غير محسوم. تعرض مرجع الحدث وآخر تحقق والتاريخ، ولا تعرض الرموز أو أخطاء المزوّد الخام.

قائمة عمليات الحجز تراعي حالة التقويم أيضًا: لا تقترح إلغاء حجز مرتبط أو تحرير فترة مستقبلية، وتحجب انتقالات الحالة عند غموض المزامنة. يتكرر التحقق في الخادم؛ تعطيل الزر وحده ليس آلية الحماية.

هوية النشاط والفاعل من الجلسة والعضوية في مساري API المركب والمستقل. فحص Schema صارم يرفض الحقول الزائدة وتزوير الحساب والحدث والمبلغ والحالة والتصديق. React يعرض نصوص الحساب والأسباب كنص مع التفاف، دون تفسير HTML.

## الترحيل والتشغيل

`0092_booking_calendar_dispatch.sql` يضيف جدول ارتباط/إرسال وجدول مراجعات. يحتفظ بتفرد الحجز والطلب ومرجع الحدث وتفرد طلب المراجعة. المراجع لا تُحذف تلقائيًا عند حذف الحجز؛ حذف النشاط نفسه يتبع سياسة الحذف الحالية. لا backfill أو تخمين لهوية حساب الروابط القديمة؛ تبقى في حالة legacy.

فُحصت القيود والبصمة وسلوك منع التكرار على قاعدتي MySQL محليتين؛ [تقرير الترحيل](./audits/sales-brain-implementation-2026-09-23/booking-calendar-migration.json). عند النشر المنفصل يلزم الترحيل وتحديث الويب والعمال معًا؛ الحماية الجديدة تعتمد على سجل الإرسال. لا تشغّل كودًا قديمًا يستطيع تعديل الحجز دون قراءة هذا السجل.

## المتبقي

- تعديل وإلغاء الأحداث الموجودة بتوثيق موافقة العميل وحجز الفترتين عند غموض النقل؛ يظل المسار محجوبًا بدل تغيير المحلي وحده.
- معالجة الحجز المدفوع وفروق السعر والاسترداد وتبديل الخدمة والإلغاء التجاري.
- دمج الحجوزات القديمة وسجل appointments وسياسات الموظفين والفواصل والسعة المتعددة ومراقبة تغير الحدث الخارجي.
- التحقق الفعلي من الحسابات والمزوّدين على عينة مصرح بها، وقياس جودة الإقناع والتحويل التجاري.
