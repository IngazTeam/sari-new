# مراجعة الموظف لموافقة العميل قبل تأكيد الحجز

التاريخ: 24 سبتمبر 2026. استكمال خطة المخ والمبيعات بعد `bdb518a8`. التنفيذ والاختبارات والترحيل محلية؛ لم يُنشر شيء على الإنتاج أو تُستخدم حسابات العملاء ومزوّداتهم.

## المشكلة التي أُغلقت في هذه الدفعة

كان اتفاق العميل يُحفظ عند إنشاء طلب الحجز، لكن واجهة الموظف لا تعرض الاتفاق، ومسار التعديل العام يستطيع تغيير الموعد أو تأكيده دون ربط القرار بالتفاصيل الموافق عليها. كذلك كان حذف المحادثة يحذف الاتفاق، فيصبح غياب الاتفاق قابلًا للالتباس مع حجز قديم لا يملك اتفاق محادثة.

أضيف مرجع دائم `bookings.customer_agreement_id`، وعرض للموافقة داخل إدارة الحجز. تأكيد الحجز المرتبط باتفاق يحتاج الآن مراجعة صريحة من موظف لديه `orders.manage`، مرتبطة ببصمة البيانات التي عُرضت له. يعيد الخادم فحص هذه البيانات داخل معاملة السعة قبل تغيير الحالة.

**التأكيد هنا محلي في bookings فقط.** لا ينشئ أو يثبت حدث Google ولا يغيّر حالة الدفع. نص الواجهة والتصديق يوضحان هذا، وتظل المراجعة الفعلية للتقويم والرسوم مسؤولية الموظف وفق إجراءات النشاط إلى حين إكمال الربط الخارجي.

## ما يراه الموظف

- مرجع الاتفاق والخدمة والموظف والتاريخ والوقت بتوقيت الرياض وسعر الخدمة الذي وافق عليه العميل.
- نص الملخص الذي أُرسل، ورسالة طلب العميل، ورسالة موافقته، وآخر رسالة واردة.
- رسالة الرفض اللاحقة عند وجودها، حتى لو أعقبها سؤال آخر من العميل.
- سبب حجب التأكيد: نقص المرجع، أو تلف السجل، أو نقص دليل الإرسال، أو اختلاف التفاصيل، أو الرفض، أو عدم التوفر، أو تجاوز حدود العرض الآمن.
- تصديق صريح قبل التأكيد المحلي، وسجل تدقيق يبيّن الموظف وموافقة العميل التي راجعها.

العرض يخص الاتفاقات المرتبطة بحجز فعلي. لا يضيف لوحة عامة للعروض التي انتهت صلاحيتها قبل الموافقة أو لم ينتج عنها حجز.

## عقد المراجعة والأثر

| الحالة | السلوك |
|---|---|
| حجز مرتبط باتفاق صحيح، دون تصديق | زر التأكيد محجوب؛ API يرفض التأكيد المباشر أيضًا. |
| تصديق على أحدث دليل مطابق | يُغيّر حالة الحجز ويحفظ التصديق في سجل العملية نفسه. |
| رسالة جديدة بعد فتح المراجعة | تتغير البصمة؛ التصديق القديم يرفض. إن لم تتضمن الرسائل رفضًا، يمكن مراجعة الدليل الجديد والتصديق عليه. |
| رفض بعد الموافقة ثم سؤال آخر | يبقى التأكيد محجوبًا؛ السؤال لا يمحو الرفض. |
| تغير الوقت أو الموظف الموافق عليه عبر التعديل العام | يرفض التعديل؛ يلزم اتفاق جديد ومسار مخصص للتغيير. |
| تغير السعر أو مدة الحجز أو تفاصيله المخزنة عن الاتفاق | يرفض التأكيد. |
| تحديث سعر الكتالوج بعد قبول العميل دون تغيير سعر حجزه | تبقى مقارنة السعر مع الاتفاق والحجز؛ يمكن للنشاط احترام السعر الموافق عليه بعد مراجعة الدليل الجديد. |
| غلق الفترة أو إشغال عدادها أو تعارض السعة أو تعطيل الخدمة/الموظف | يرفض التأكيد. |
| حذف المحادثة أو الاتفاق | يبقى المرجع داخل الحجز، وتظهر حاجة للمراجعة؛ لا يعامل كحجز قديم بلا موافقة. |
| نقص الأدلة | يظل الإلغاء متاحًا وفق ضوابط الحالة والدفع السابقة. |
| حجز قديم لا يملك مرجعًا أو اتفاقًا | يحتفظ بمسار إدارته السابق، مع تنبيه واضح لعدم وجود اتفاق محادثة. |
| طلبان متزامنان للتأكيد | تغيير واحد وسجل تدقيق واحد. |
| فشل حفظ التدقيق | تتراجع الحالة معه في المعاملة نفسها. |
| فقد تأكيد commit | إعادة طلب العملية نفسه تسترد النتيجة المحفوظة دون أثر أو تدقيق مكرر. |
| معرف العملية نفسه مع فاعل أو محتوى مختلف | يرفض وفق عقد هوية العملية القائم. |

التصديق يتضمن معرف الاتفاق وبصمة الأدلة و`reviewed: true`. لا يملك المستدعي إرسال تاجر أو فاعل أو سعر أو حالة دفع بديلة. البصمة تربط الحجز والاتفاق والرسائل ودليل النقل والخدمة والفترة. تواريخ SQL تدخل فيها بصيغة ثابتة بدل إسقاطها أثناء تطبيع JSON.

المراجعة لا تتصل بالموديل ولا بـ Google أو Tap. اختيار OpenAI/ZahyPi وميزانية المنصة اليومية لا يتغيران.

## العزل والصلاحيات

أضيف `bookings.getConsentReview` إلى مساري API المركب والمستقل عبر إجراءات الحجز المشتركة. يحدد الخادم النشاط من عضوية المستخدم، ويشترط `orders.manage` للقراءة كما يشترطها للتعديل. المستخدم غير المصادق، والقارئ غير المخول، وتزوير نطاق النشاط، والحقول الزائدة، تُرفض قبل الوصول لبيانات الموافقة.

القراءة تبدأ بحجز مملوك للنشاط، ثم اتفاق ضمن النشاط نفسه. تعاد الأخطاء العامة دون SQL أو رسائل عملاء آخرين. نصوص العميل والخدمة تعرضها React كنص، مع التفاف داخل الحاوية؛ لا تُفسر HTML أو أوامر JavaScript.

تُقرأ حتى 100 رسالة واردة بعد الموافقة للتحقق من رفض لاحق. تجاوز العدد، أو طول رسالة مصدر معروضة عن 8000 حرف، أو ملخص عن 16000 حرف، يحجب التأكيد من هذه الواجهة بدل الاعتماد على دليل ناقص. يلزم حينها مسار مراجعة كامل خارج هذا الجزء؛ لم يُضف زر تجاوز لهذه الحماية.

## الترحيل والتوافق

ترحيل `0090_booking_consent_binding.sql`:

1. يضيف مرجع موافقة قابلًا لأن يكون فارغًا، دون علاقة تحذف المرجع عند حذف المحادثة أو الاتفاق.
2. يربط الحجز فقط باتفاق موجود يشير إلى الحجز نفسه والنشاط نفسه.
3. يترك الحجوزات القديمة غير المرتبطة دون تخمين، ولا ينسخ مرجعًا بين نشاطين.

اختُبر الترحيل على قاعدتي MySQL محليتين ببيانات مصطنعة تشمل ارتباطًا صحيحًا وحجزًا قديمًا ومرجعًا من نشاط آخر. تحقق [تقرير الترحيل](./audits/sales-brain-implementation-2026-09-23/booking-consent-review-migration.json) من البصمة والسجل والعمود ونتائج الربط.

يحفظ مسار قبول العميل المرجع الجديد في معاملة إنشاء الحجز نفسها. تُفحص جاهزية العمود قبل تشغيل المسار والعمليات. **عند النشر يلزم إيقاف الكتابات القديمة، وتطبيق الترحيل، وتحديث الويب والعمال معًا**؛ العامل القديم الذي لا يحفظ المرجع لا يجب أن يستمر في الكتابة بعد الربط الأولي.

## حالة الخطة والمتبقي

تقدمت B035 وB037 وB057 وB064 وB065 مع إبقائها جزئية. الحالة الإجمالية **4 مكتملة / 55 جزئية / 12 لم تُغلق**.

المتبقي الأقرب:

1. مسار اتفاق جديد لتعديل الوقت أو الموظف في الحجز القائم، مع نقل الموافقة والسعة دون طلب مكرر.
2. دمج التأكيد المحلي مع التقويم الخارجي ومعالجة حالات Google غير المحسومة، دون سجلين متعارضين.
3. واجهة عامة لمراجعة العروض المنتهية والمرفوضة وغير المكتملة قبل إنشاء الحجز.
4. توسيع سياسات الجدولة والرسوم والخدمات المتغيرة والسعة الجماعية والوقت الفاصل.
5. تجربة مزوّد AI وواتساب وتقويم بحساب اختبار مخصص، وقياس جودة الحوار والإقناع والتحويل.
