# استعادة الحفظ بعد أعطال قاعدة البيانات المؤقتة — 24 سبتمبر 2026

استكمال بعد الكوميت e492facd. كان حفظ الرد يسبق تسوية الميزانية، لكنه يُجرّب مرة واحدة؛ فشل SQL مؤقت قد يفقد ردًا موجودًا بالفعل في ذاكرة العامل. كما أن إعادة الحفظ بعد نجاح commit وفقد إقراره كانت تُرفض، ولو كانت النتيجة والهوية متطابقتين.

## التنفيذ

- أضيف مسار لحفظ رد المزوّد المستلم، بثلاث محاولات SQL كحد أقصى، وفاصل 100 ثم 300 مللي ثانية. لا إعادة استدعاء النموذج، ولا تبديل مزوّد، ولا حجز تكلفة جديد. تنتهي المعاملة ويُحرّر الاتصال قبل انتظار المحاولة التالية.
- إعادة المحاولة محصورة في تسعة رموز معروفة لأعطال الاتصال والأقفال، من Error فعلي؛ لا استنتاج من نص الخطأ أو بيانات النموذج. الأخطاء الدائمة ونقص المخطط وتعارض الهوية والنتيجة تتوقف فورًا. استُخدمت ثوابت mysql2 المثبتة للتحقق من رموز أخطاء الأقفال والاتصال.
- تثبت نسخة هوية المهمة ومحاولة الميزانية طوال إعادة الحفظ. في كل محاولة تُفحص ملكية النشاط، وحجز التكلفة، ومعرف الطلب، والنموذج، والمهمة، وبصمة المصدر كما في المسار الأصلي.
- الرد المطابق في حالة responded يُستعاد بعد التحقق من النص المخزن والبصمة والمصدر، دون كتابة جديدة أو تحريك جدول الاستعادة أو حجز العامل. اختلاف تنسيق JSON وحده لا يغيّر هوية النتيجة.
- إذا سبق عامل الاستعادة إلى إسقاط النتيجة، تسمح حالة applied بإقرار الرد نفسه وفق البصمة المحفوظة. معاملة الإسقاط تكتشف الإنجاز السابق فلا تكرر المقترحات أو الأدلة أو الإشعارات. لا إعادة إنشاء response_json الذي مُسح بعد الإنجاز.
- الرد المختلف أو غير الصالح لا يستبدل الرد المقبول ولا يفسد حالته. تغير مصدر نتيجة لم تُسقط يوقفها؛ تغير هوية المهمة لا يسمح للعامل القديم بالكتابة عليها.
- استنفاد المحاولات يترك النتيجة غير محسومة والمبلغ محجوزًا وفق المسار السابق. أخطاء SQL ونص الرد وتفاصيل الاتصال لا تظهر في رسالة فشل الحفظ.
