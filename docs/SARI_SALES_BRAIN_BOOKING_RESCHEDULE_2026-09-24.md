# نقل موعد Google بموافقة جديدة واحتجاز الفترتين

24 سبتمبر 2026، بعد **3df236ea**. تنفيذ واختبارات وترحيل محلي ببيانات مصطنعة، دون نقل حدث Google حقيقي أو مراسلة عميل أو نشر إنتاجي.

## ما أصبح ممكنًا

الحجز المؤكد المرتبط بالتقويم عبر المسار الموثق يستطيع الانتقال إلى وقت جديد، بعد ملخص واضح وموافقة جديدة محفوظة من العميل ومراجعة موظف لديه orders.manage. يحتفظ النظام بالحجز نفسه ورقم مرجعه؛ لا ينشئ موعدًا إضافيًا، ولا يدّعي اكتمال النقل بمجرد موافقة العميل أو إرسال PATCH.

يشمل المسار حجزًا بلا أي سجل مالي، بخدمة وموظف وسعر ومدة ثابتة، وفترة جديدة معدة مسبقًا لا تتداخل مع الأصل. هذا النطاق مقصود حتى لا يغيّر النقل التزامًا ماليًا أو موردًا لم يجر التحقق منه. تغيير الخدمة أو الموظف أو المدة أو السعر، والمواعيد المدفوعة/القديمة غير الموثقة والتداخل الجزئي مع الموعد السابق، تحتاج مسارًا مساعدًا لاحقًا.

## رحلة العميل والموظف

1. تستخرج المحادثة اختيار الموعد فقط. رقم الحجز وملكية العميل والمحادثة ومرجع Google تأتي من السجلات، ولا يختارها الموديل ولا يكتبها مباشرة.
2. يظهر للعميل ملخص يشمل الموعد الحالي والجديد والخدمة والموظف والسعر والمدة وتوقيت الرياض. العرض صالح 15 دقيقة. تقديم العرض لا يحجز الفترة الجديدة، والرفض أو غياب دليل إرسال العرض أو انتهاء صلاحيته لا يغيران الحجز.
3. قبول العرض يعيد التحقق من الأصل والوقت والتوافر والشروط. يحفظ الاتفاق المقبول وطلب النقل واحتجاز الفترة الجديدة، ويغير ارتباط التقويم إلى reschedule_pending في معاملة واحدة. الموعد الأصلي ومرجع اتفاقه وحالته confirmed تبقى كما هي.
4. يعرض الموظف الفترتين والملخص ورسالة الموافقة وتاريخها، ثم يكتب سببًا ويصدق على المراجعة. دليل متغير يلغي التصديق؛ لا يمكن اختيار حساب أو حدث أو رسالة أو etag من المتصفح.
5. اعتماد النقل يقرأ الحدث من الحساب الأصلي ويطابق الهوية والاتفاق والوقت وعدم التكرار، ويتحقق من FreeBusy للفترة الجديدة. يعاد بعدها فحص الدليل والتعارضات المحلية وتداخل التقويم المشترك تحت قفل السعة.
6. تحفظ محاولة moving الدائمة مع UUID وhash والفاعل والسبب وetag قبل PATCH واحد مشروط بـIf-Match. لا حذف/إعادة إنشاء للحدث، ولا تحديث للاسم أو الوصف أو الحضور. تتغير الفترة ومرجعية الاتفاق في الخصائص الخاصة.
7. يلزم رد 200 بحدث مطابق للموعد الجديد والاتفاق الجديد والمرجع الأصلي. يُراجع الالتزام والموافقة والتوافر والحالة المالية ثانية، ثم يحدّث الحجز وارتباط التقويم وسجل النقل وسجلي التدقيق في معاملة واحدة. عندها فقط تتحرر الفترة السابقة وتصبح الجديدة هي الحجز الفعلي.
8. قبل الإرسال يمكن إغلاق الطلب مع سبب ومراجعة؛ تتحرر الفترة المقترحة ويبقى الموعد الأصلي. بعد الإرسال لا يتاح هذا الإجراء حتى عند فقد الاستجابة. يستطيع الحجز أن يمر بنقل جديد مستقل بعد اكتمال النقل السابق، مع اتفاق وتاريخ منفصلين.

## الفشل والتزامن والتعافي

| الحالة | السلوك المثبت محليًا |
|---|---|
| سؤال/رفض، عرض غير مسجل الإرسال، أو موافقة متأخرة | لا نقل ولا احتجاز جديد؛ الأصل محفوظ. |
| موافقة مكررة | الطلب نفسه، بلا صف احتجاز إضافي وبلا اتصال Google. |
| موظفان يعتمدان النقل معًا | معاملة السعة تسمح بإرسال PATCH واحد فقط. |
| تغير الموافقة أو الحساب أو التوافر أثناء الفحص السابق للإرسال | رفض قبل PATCH؛ يبقى طلب المراجعة قابلًا للإغلاق قبل الأثر. |
| timeout أو 412 أو رد بوقت/اتفاق/مرجع خاطئ أو حدث ملغى/متكرر | move_unknown؛ الحجز الأصلي والفترة الجديدة محفوظان. |
| فشل حفظ محاولة الإرسال أو فقد تأكيد commit | لا تكرار تلقائي؛ عند وجود محاولة محفوظة تعاد حالتها بالـUUID. |
| فشل التدقيق أو الإسقاط بعد نجاح Google | يتراجع الإسقاط المحلي بالكامل وتبقى moving قابلة للتحقق؛ لا تحرير منفرد للفترة ولا إعادة PATCH. |
| انقطاع العامل في moving | بعد دقيقتين يمكن قراءة الحدث الأصلي للتحقق؛ المهلة ليست إثبات نجاح أو إذنًا بتحرير السعة. |
| GET يعيد 404/410/403 أو الحدث القديم | لا يثبت النقل ولا يحرر أي فترة. |
| GET يثبت الحدث الجديد مع بقاء المرجع والاتفاق والموافقة والشروط صحيحة | إسقاط محلي موثق، دون إعادة PATCH. |
| رد PATCH قديم أو GET قديم بعد اكتمال تحقق آخر | مراجعة السجل وبصمة الدليل تمنع الكتابة القديمة فوق النتيجة الأحدث. |
| رسالة جديدة/تراجع العميل أو تغير الالتزام خلال PATCH | يحتفظ بالغموض حتى لو لوحظ نجاح النقل الخارجي؛ يلزم تدخل النشاط، ولا يعيد الموعد الخارجي تلقائيًا. |

الفترات المستقبلية محفوظة عبر دفتري bookings وappointments، وبصرف النظر عن عملية/عامل التنفيذ. احتجاز يوم جديد يدخل سقف الخدمة اليومي، دون عد الحجز مرتين في اليوم نفسه. حجز خدمة أخرى في حساب Google نفسه لا يتجاوز فترة نقل محفوظة؛ وكذلك النقل لا يتجاوز موعدًا آخر ذا إنشاء خارجي غير محسوم.

إصدار دفع جديد أو تجديده والتعديل المحلي والإلغاء لا تتجاوز طلب نقل نشطًا. لإلغاء حجز لديه طلب نقل لم يُرسل، يغلق الموظف طلب النقل أولًا ثم يراجع طلب الإلغاء نفسه. الطلب الذي أُرسل لا يُغلق لإسقاط احتجاز غير محسوم.

## ما يراه العميل

الرد عقب الموافقة يقول إن طلب النقل مسجل وإن الموعد الجديد لم يثبت بعد. إعادة الرسالة لا تنشئ حجزًا أو أثرًا خارجيًا. حالة الحجز المؤكد بعد النجاح تُقرأ من SQL. الاختبار يمر عبر معالج المحادثة بالرسائل المحفوظة وبمخرجات AI مصطنعة؛ الموديل لم ينفذ النقل.

لم تُضف رسالة واتساب تلقائية جديدة عند اعتماد الموظف للنقل. تأكيد النتيجة وإبلاغ العميل يبقيان مسؤولية رحلة النشاط القائمة؛ إصدار إشعار تلقائي موثق ومراقبة تسليمه جزء من الإغلاق التشغيلي اللاحق. لا تثبت هذه الاختبارات جودة إقناع نموذج حي أو زيادة التحويل.

## المخطط والنشر

ترحيل **0094_booking_calendar_reschedules** يضيف سجل الطلب واحتجاز الفترة المقترحة والتدقيق السابق للأثر. يفرد الاتفاق وUUID داخل التاجر؛ يسمح بطلبات تاريخية متعددة للحجز، ويمنع التطبيق طلبين نشطين عبر معاملة السعة المشتركة. لا FK إلى الحجز أو الاتفاق يمحو تاريخ العملية عند حذفهما؛ ملكية التاجر لها FK. لا تخمين أو تحويل تلقائي لسجلات قديمة.

طُبق الترحيل على قاعدتي MySQL المحليتين فقط، وفُحصت بصمة SQL والفهارس والتكرار وحفظ التاريخ. البصمة: dd2d89aa5e15bde20b6086001d07fd80eb0566fc0e0700c0e22d702ec915e5ea. الدليل في [تقرير الترحيل](./audits/sales-brain-implementation-2026-09-23/booking-reschedule-migration.json).

عند نشر منفصل، يجب تحديث جميع كتاب الحجز والمواعيد والدفع والويب والعمال مع الترحيل؛ العامل القديم لا يفهم احتجاز الفترة الجديدة. لا تُحذف سجلات النقل ولا يعاد تشغيل كاتب قديم يتجاهلها مع وجود طلبات نشطة. عند التراجع عن نشر، أوقف كتابة المواعيد مؤقتًا أو أبق مسار الكتابة الذي يفهم الاحتجاز إلى أن تُراجع الطلبات النشطة. لم يُنفذ أي نشر أو تراجع إنتاجي هنا.
