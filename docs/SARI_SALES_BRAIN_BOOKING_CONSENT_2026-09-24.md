# اتفاق الحجز داخل محادثة المبيعات وموافقة العميل

التاريخ: 24 سبتمبر 2026. استكمال خطة المخ والمبيعات على أساس `4112cba1`، بعد إصلاح هوية طلب التقويم في `e89d25ff`. التنفيذ والتحقق محليان؛ لم يُنشر كود أو ترحيل ولم تُستخدم حسابات العملاء أو مزوّدات حية.

## النتيجة وحدودها

أصبح طلب الموعد داخل المحادثة ينتج ملخصًا محفوظًا، ثم ينتظر موافقة العميل الصريحة على التفاصيل المعروضة. الموافقة الصحيحة تنشئ **طلب حجز محليًا في bookings بحالة pending ودفع unpaid**. لا تنشئ موعدًا مؤكدًا في appointments أو حدث Google، ولا رابط دفع أو تحصيل. هذا التفريق ظاهر في نص الملخص ونتيجة الموافقة.

المسار متصل بـ chatWithSari للرسائل الخاصة ذات رسالة واردة محفوظة. أزيل تجاوز الحجز القديم من معالج GreenAPI، بحيث يمر طلب الموعد والرد اللاحق «نعم» في المسار نفسه. مساعدات الحجز القديمة الموجودة لأغراض التوافق لم تُحذف، ولا تعني هذه الدفعة توحيد جميع أدوات الحجز في المشروع.

## عقد المحادثة

1. يقرأ الخادم نص الرسالة المحفوظ وملكية المحادثة ورقم العميل؛ النص الممرر إلى الدالة ليس سلطة للموافقة.
2. يرسل للموديل كتالوج الخدمات والموظفين المملوك للنشاط وسياقًا محدودًا. مهمته استخراج serviceId وstaffId وbookingDate وstartTime فقط؛ يُرفض أي حقل إضافي مثل السعر.
3. عند نقص التفاصيل، يطلب استكمالها. يستطيع الرد التالي استكمال الوقت أو الخدمة دون تكرار كلمة «حجز»، إذا كان آخر رد توضيحي قد قُبل في النقل.
4. يشتق الخادم الاسم والسعر والمدة والوقت النهائي من البيانات الفعلية، ويتحقق من فترة متاحة مهيأة. يحفظ لقطة وبصمة وملخصًا صالحًا لمدة 15 دقيقة. الملخص وحده لا يحجز السعة.
5. «نعم» لا تُفسّر بالموديل. يلزم عرض محفوظ سابق مطابق للنص الذي قُبل في النقل، وموافقة قصيرة غير مشروطة من المصدر الصحيح. قبول النقل ليس إثبات قراءة العميل.
6. قبل الأثر، يعاد فحص التفاصيل والسعة وأحدث رسالة والتولي البشري وملكية العامل. تُحفظ الموافقة ومرجع الحجز في معاملة واحدة.
7. التكرار يسترد المرجع والحالة الحالية. فقدان تأكيد commit لا يؤدي إلى إنشاء جديد؛ حذف الحجز لا يحذف مرجعه من الاتفاق.

يبقى اختيار OpenAI أو ZahyPi في مسار المزوّد الحالي وإعدادات السوبر أدمن؛ لم يُنشأ اتصال مستقل يتجاوز اختيار المزوّد أو ميزانية المنصة اليومية البالغة 100 دولار.

## ضوابط الأثر

| الحالة | النتيجة |
|---|---|
| لا موافقة، أو رفض، أو سؤال/تعديل مثل «نعم لكن…» | لا ينشأ حجز. |
| العرض لم يُرسل، أو تغيّر نصه، أو تبعه رد بشري أو عرض أحدث | لا تُقبل الموافقة على العرض القديم. |
| تغير السعر أو المدة أو الاسم أو الموظف أو الفترة | يطلب ملخصًا جديدًا وموافقة جديدة. |
| انتهاء صلاحية العرض أو استبداله | لا ينشأ الحجز منه. |
| الموعد محجوز في bookings أو appointments | يرفض التعارض تحت قفل السعة المشترك. |
| عميلان يوافقان على الفترة نفسها | ينشأ حجز واحد فقط. |
| ثلاث عمليات مستقلة توافق على الرسالة نفسها | مرجع حجز واحد. |
| تعطل قراءة قاعدة البيانات | تتراجع المعاملة دون تحويل العطل إلى انتهاء صلاحية؛ تبقى الموافقة قابلة للاسترداد. |
| فشل حفظ ارتباط الموافقة بعد إدخال الحجز | يتراجع الحجز والارتباط معًا. |
| فقد تأكيد الحفظ | تسترد إعادة الطلب النتيجة المحفوظة. |
| حجز ألغي أو اكتمل أو حُذف لاحقًا | لا يعاد إنشاؤه أو تأكيده؛ تعرض حالته الحالية أو الحاجة إلى المراجعة. |
| رفض بعد إنشاء الحجز | لا يدّعي الإلغاء؛ يطلب مراجعة النشاط. |
| فقد ملكية العامل قبل الأثر | لا يكتب الحجز. |
| اسم خدمة أو موظف يحتوي رموز SEND_IMAGE أو SEND_DISCOUNT | يُعرض كنص؛ لا يتحول إلى أمر وسائط أو خصم. |

بصمة اللقطة تُحسب بعد ترتيب المفاتيح بصورة ثابتة. كشفت الاختبارات أن MySQL يعيد ترتيب مفاتيح JSON؛ الاعتماد على ترتيب الإدخال كان يرفض موافقات صحيحة، وأُصلح ذلك. لا تتغير حقائق السعر أو الوقت بناءً على ترتيب JSON.

أسماء الخدمات والموظفين تُعرض في سطر واحد مع تحييد الأقواس المستخدمة لأوامر الرد وإزالة محارف التحكم واتجاه النص. اختبار يمر عبر parseAICommands الفعلي أثبت بقاء نص العرض كما هو، وعدم إرفاق وسائط أو استخراج خصم، ثم نجاح الموافقة بالسعر الفعلي.

## النطاق المدعوم الآن

- خدمة نشطة تتطلب موعدًا، بسعر ثابت صحيح بوحدته الصغرى، دون وقت فاصل.
- فترة محلية مهيأة ومفتوحة، مطابقة للتاريخ والوقت والموظف، بسعة واحدة وعدّاد إشغال صفر.
- تاريخ مستقبلي ضمن advance_booking_days، ووقت نهائي لا يعبر منتصف الليل.
- الموظف نشط ومملوك للنشاط ومسموح له بالخدمة عند تعيينه.
- الحد اليومي للخدمة، عند ضبطه، يحتسب الحالات النشطة عبر السجلين.
- حساب التاريخ والوقت بتوقيت الرياض في هذا العقد.

الخدمات ذات السعر المتغير أو المخصص، والوقت الفاصل، والسعة الجماعية، والموعد غير المهيأ، تحتاج مراجعة النشاط. هذه قيود معلنة لهذا التنفيذ، وليست دعمًا مكتملًا لمحرك جدولة عام.

## قاعدة البيانات والتشغيل

ترحيل `0089_conversation_booking_agreements.sql` يضيف جدول الاتفاقات وقيودًا فريدة على مصدر العرض والموافقة ومرجع الحجز داخل كل نشاط. يحتفظ بالمرجع إذا حُذف الحجز؛ حذف المحادثة أو النشاط يحذف الاتفاق وفق علاقتهما. لا يعيد بناء الحجوزات السابقة ولا يخمّن موافقات قديمة.

طُبق الترحيل على قاعدتي الاختبار المحليتين، وتحقق تقرير [الترحيل](./audits/sales-brain-implementation-2026-09-23/booking-agreement-migration.json) من بصمة SQL وسجل الترحيل والقيود. جاهزية الجدول مطلوبة قبل تشغيل عامل التفاعل وقبل تسجيل الاتفاق أو الموافقة. **يلزم تطبيق الترحيل وتحديث الويب والعمال معًا قبل التفعيل الإنتاجي.**

## تحديث الخطة وما لم يُغلق

تقدمت البنود B035 وB037 وB064 وB065 مع إبقائها جزئية. إجمالي المصفوفة **4 مكتملة / 55 جزئية / 12 لم تُغلق**؛ نجاح الاختبارات المحلية لا يرفع التقييم تلقائيًا إلى 10/10.

الأعمال التالية المحددة:

1. توحيد طلب الحجز المحلي وموافقته مع إجراء التأكيد النهائي لدى النشاط والتقويم، دون إنشاء سجلين متعارضين أو تجاوز السعة.
2. استكمال مراجعة حالات Google العالقة في creating، والتأكد الخارجي من عدم وجود أثر قبل السماح بإعادة المحاولة.
3. إظهار اتفاق العميل ورسالة مصدره وسبب انتهاء صلاحيته في واجهة الموظف مع الصلاحيات المناسبة؛ لم تُضف واجهة لهذا الجدول بعد.
4. توسيع سياسات الجدولة والتسعير والرسوم والإلغاء والسعة الجماعية والوقت الفاصل، ثم اختبارات قبول لكل نوع خدمة مدعوم.
5. اختبار رحلة واتساب ومزوّد AI وتقويم حقيقية بحساب اختبار مخصص، ثم قياس جودة التفاوض والاعتراضات والتحويل على بيانات مراجعة معتمدة.
6. إكمال بقية البنود المفتوحة في مصفوفة المخ والتعلم والمبيعات، لا اعتبار تحسين الحجز إغلاقًا لها.
