# تعديل الموعد بموافقة العميل مع حفظ سجل الاتفاقات

24 سبتمبر 2026؛ استكمال خطة المخ والمبيعات بعد `a108dc06`. التنفيذ والترحيل والفحص محلية بعملاء مصطنعين. لم يُنشر على الإنتاج ولم تُرسل رسائل للعملاء أو طلبات إلى المزوّدين.

## النتيجة

أصبح سالي يعالج طلب تغيير موعد قائم عبر المحادثة: يحدد الحجز المملوك للعميل، ويعرض الموعد الحالي والتاريخ والوقت والموظف والمدة والسعر الجديدين، ثم ينتظر موافقة واضحة على الملخص الذي ثبت إرساله. عند الموافقة يحدّث **الحجز نفسه** داخل معاملة السعة، ويبقي جميع الاتفاقات السابقة محفوظة.

هذا يسد فجوة بين البيع والمتابعة بعد الاتفاق: طلب التعديل لا يتحول إلى حجز إضافي، ولا يفقد العميل موعده الأصلي لمجرد طلب تغيير. الموعد المعدل يعود إلى `pending` ويحتاج مراجعة جديدة من النشاط، حتى لو كان الموعد السابق مؤكدًا محليًا.

## العقد المنفذ

| الحالة | النتيجة |

| الموافقة الصريحة على آخر ملخص صالح ومُرسل | فحص ملكية الرسالة والمحادثة والعامل، وبصمة حالة الحجز السابقة والتفاصيل الجديدة والسعة، ثم التعديل الذري. |
| تغيّر الموعد أو السعر أو الحالة أو الملاحظات أو شروط الفترة | ينتهي العرض؛ لا تطبق تفاصيل تغيرت دون عرض وموافقة جديدين. |
| تغير سعر الكتالوج قبل إعداد العرض | يعرض السعر الجديد صراحة، ويحفظه فقط بعد موافقة العميل؛ تبقى الخدمة نفسها. |
| تاريخ مالي بأي حالة أو حدث Google قائم | يرفض التعديل التلقائي؛ يحتاج مسار مراجعة النشاط. لا يلغي دفعة أو حدثًا خارجيًا. |
| تعديل حجز مؤكد محليًا | يعود pending ويُمسح confirmed_at؛ الاتفاق القديم لا يجيز تأكيد الموعد الجديد. |
| مراجعة الموظف | تعرض الاتفاق الفعّال ورسائله؛ يرفض التصديق القديم ويحتاج تصديقًا جديدًا ببصمة حديثة. |
| التزامن | قفل سعة النشاط ينسق السجلين، ويستثني الحجز الجاري نقله من فحص تعارضه مع نفسه وعد اليوم. |
| فشل حفظ الموافقة بعد تحديث الحجز | تتراجع كل التغييرات معًا. |
| فقد تأكيد commit | إعادة الرسالة نفسها تسترد النتيجة؛ لا تنشئ حجزًا أو اتفاقًا إضافيًا. |
| إعادة تشغيل اتفاق قديم | يعيد الحالة الحالية، ولا يعيد الموعد القديم. |
| حذف الحجز بعد نجاح التعديل | يبقى مرجع النتيجة؛ لا يُعاد إنشاء الحجز. |

الهوية من رسائل قاعدة البيانات وملكية المحادثة، لا من نص يمرره المستدعي. خدمة التعديل تعيد فحص سياق طلب التعديل داخل المعاملة؛ حتى استدعاء دالة إنشاء حجز جديد مباشرة بطلب تعديل مملوك يرفض. يقبل المسار الحجوزات المستقبلية pending/confirmed غير المدفوعة فقط، ذات اتفاق محادثة صحيح وخدمة موعد بسعر ثابت وفترة صريحة بسعة واحدة، دون buffer. لا يوجد أثر خارجي داخل المعاملة.

## التخزين والترحيل

ترحيل `0091_booking_agreement_amendments.sql` يضيف `target_booking_id` و`prior_agreement_id` و`before_snapshot` و`before_hash`. تستبدل فريدة مرجع النتيجة بفهرس عادي يسمح بعدة مراجعات للحجز نفسه. تبقى فريدتا رسالة المصدر والموافقة؛ ويظل `bookings.customer_agreement_id` مرجع الاتفاق الفعّال.

لقطة ما قبل التعديل تحفظ بيانات الالتزام اللازمة للتحقق والتدقيق، مع بصمة الملاحظات عوض نسخها. موافقة التعديل والموعد الجديد وتبديل المرجع تحفظ في معاملة واحدة. لا تعدّل موافقة سابقة أو تستبدل محتواها.

أثبت [فحص الترحيل](./audits/sales-brain-implementation-2026-09-23/booking-amendments-migration.json) على قاعدتي اختبار محليتين بقاء سجل سابق دون تغيير، وقبول مراجعة ثانية للنتيجة نفسها، ورفض تكرار المصدر أو الموافقة، وتطابق الفهرس وبصمة SQL المسجلة.

عند النشر يلزم إيقاف الكتابات القديمة وتطبيق الترحيل وتحديث الويب والعمال معًا. النسخة السابقة تشترط الفهرس الفريد القديم؛ لا تصلح لإعادة التشغيل فوق المخطط الجديد. التراجع يحتاج نسخة متوافقة مع سجل المراجعات، وليس حذف المراجعات لإعادة الفريدة. لم ينفذ هذا الترحيل على الإنتاج.
