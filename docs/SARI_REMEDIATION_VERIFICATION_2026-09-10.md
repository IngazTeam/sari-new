## المرحلة الرابعة — تعافي البوابة وحدود استجابات التفعيل

المرجع عند بدء المتابعة: `ba65b2b`. الإصلاح محلي في عميل ZahyPi وفاحص التفعيل، دون تغيير schemas أو أسماء المهام أو قاعدة البيانات أو مفاتيح المزود.

### العيوب المثبتة والإصلاح

1. **تعطل إعادة المحاولة عند أخطاء البوابة غير JSON:** كان عميل الوظائف يحلل الجسم قبل فحص HTTP؛ رد HTML من proxy بحالة 503/429 كان يتحول إلى خطأ validation لا يُعاد. صار يفحص الحالة أولًا، ويلغي الجسم دون قراءته، ويعيد فقط الحالات المؤقتة المسموح بها (408، 429، 5xx) ضمن سقف المحاولات والمهلة الأصليين.
2. **فشل تفعيل زائف أثناء `retry_wait`:** كان فاحص التفعيل يقبل الانتظار في queued/running فقط، بعكس عميل التشغيل. صار يتابع retry_wait على job_id نفسه، بلا POST إضافي، ويرفض تغير الهوية أو انتهاء المهلة أو الحالة الطرفية غير الناجحة.
3. **احتمال ظهور محتوى JSON المعطوب في رسالة الخطأ الداخلية:** كانت رسالة JSON.parse الخام تُمرر من فاحص التفعيل. استُبدلت برسالة ثابتة لا تتضمن محتوى الرد. لم يُثبت تسريب فعلي إلى مستخدم أو سجلات الإنتاج في هذه الجولة.
4. **حدود القراءة والموارد:** مطابقة MIME أصبحت لنوع application/json نفسه مع السماح بمعاملاته، لا substring يقبل jsonp أو text/plain. يُرفض الحجم المعلن فوق 64,000 bytes قبل القراءة، وتبقى رقابة الحجم الفعلي قائمة ولو كذب Content-Length. الإلغاء best-effort بلا انتظار قد يعلق أو يطمس الخطأ الأصلي، ويُحرر reader في finally. عميل التشغيل يحرر القارئ ويلغي الاستجابات المرفوضة أيضًا، مع بقاء حده 1 MiB.

لا يضيف فاحص التفعيل retries لطلب HTTP الفاشل؛ التغيير فيه انتظار حالات الوظيفة المعلقة فقط. إعادة إرسال POST في عميل التشغيل تستخدم الجسم وIdempotency-Key وtrace نفسها؛ عدم تكرار التنفيذ الفعلي يعتمد أيضًا على احترام Gateway لهذا المفتاح، وهو شرط اختبار حي.
