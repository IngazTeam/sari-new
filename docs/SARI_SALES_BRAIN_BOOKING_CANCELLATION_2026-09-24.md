# إلغاء الحجز المرتبط بالتقويم بموافقة محفوظة

24 سبتمبر 2026، بعد **08252e15**. تنفيذ وترحيل وفحص محلي ببيانات مصطنعة. لم تُحذف أحداث حقيقية، ولم تُرسل رسائل للعملاء، ولم يُنشر كود على الإنتاج.

## ما اكتمل في هذه الدفعة

أضيف إلغاء منسق للحجز الموافق عليه والمؤكد والمرتبط سابقًا بهذا المسار بتقويم Google، بشرط عدم وجود حالة دفع أو أي رابط دفع أو محاولة تحصيل أو سجل مالي. يقرأ الخادم طلب إلغاء صريحًا من العميل يحدد رقم الحجز، ويعرضه مع تفاصيل الموعد لموظف لديه orders.manage. الموديل لا يحدد صاحب الطلب أو مرجع الحدث، ولا يمنح صلاحية الإلغاء.

المحادثة تتعرف على صيغ الإلغاء الصريحة قبل اقتراح حجز أو قبول عرض قديم. تستخدم الرسالة المحفوظة وملكية العميل والمحادثة، وتجيب بأن الطلب يحتاج مراجعة، أو أن النتيجة غير محسومة، أو أن السجل أصبح ملغى. لا تنشئ موعدًا ولا تنفذ DELETE من المحادثة، ولا تدّعي اكتمال الإلغاء قبل تغير الحالة المحلية الموثقة.

## شروط القبول والتنفيذ

1. الطلب آخر رسالة واردة في محادثة الاتفاق الحالي، أحدث من الموافقة الأصلية، وعمره لا يتجاوز 24 ساعة؛ رقم الحجز صريح ومطابق. أمثلة مقبولة: «أريد إلغاء الحجز #123»، «ألغي حجزي رقم ١٢٣»، و«cancel my booking #123». السؤال أو النفي أو الشرط أو جمع أكثر من طلب أو رقم مفقود يحتاج مراجعة النشاط؛ لا تخمين من نعم أو رفض عام.
2. الموظف يرى طلب العميل ورقمه وتاريخه والخدمة والفترة بتوقيت الرياض، ويكتب سببًا ويصدق على المراجعة. الهوية والصلاحية من الجلسة؛ لا يقبل API معرف رسالة أو حساب أو حدث أو etag من العميل.
3. يقرأ الخادم حدث Google من الحساب الأصلي، ويطابق المرجع والاتفاق والفترة والحالة وعدم التكرار، ويحفظ نسخة etag صالحة. يعيد بعدها فحص الدليل والطلب والسجل المالي في معاملة الحجز.
4. يحفظ سجل إلغاء فريدًا للحجز والطلب، مع الفاعل والسبب وبصمة الدليل ولقطة الالتزام ورسالة العميل وetag، قبل الأثر الخارجي. يتحول الارتباط إلى cancelling ويمنع التعديل المحلي وإصدار رابط دفع جديد.
5. يجري DELETE واحدًا مشروطًا بـIf-Match، بمهلة 15 ثانية ودون إعادة نقل تلقائية. قبول 204 يسمح بإلغاء المحلي مع تحديث السجلين وتدقيق عمليات الحجز في معاملة واحدة، بعد إعادة فحص الدليل والطلب والهوية.
6. فقدان الرد أو رفض الشرط أو أي غموض يبقي الفترة محفوظة. إعادة UUID تسترد النتيجة المسجلة؛ UUID مختلف لا يتجاوز محاولة الإلغاء السابقة. التعافي يقرأ الحدث الأصلي فقط، ولا يعيد DELETE.

## الفشل والتزامن

| السيناريو | السلوك |
|---|---|
| تغير العميل أو الحساب أو إصدار رابط دفع خلال فحص الحدث الأول | يرفض قبل تسجيل محاولة الإلغاء أو حذف الحدث. |
| محاولة إصدار دفع أو تعديل الحجز بعد تسجيل الإلغاء | تُحجب تحت قفل الحجز؛ لا سباق يسمح بأثر مالي جديد. |
| timeout أو 412 أو استجابة حذف غير معتمدة | cancel_unknown؛ لا تحرير للموعد ولا إعادة DELETE. |
| GET يعيد 404/410/403 أو حدثًا نشطًا أو مرجعًا آخر أو تكرارًا | لا يثبت الإلغاء، ويبقى الحجز محفوظًا. |
| GET يثبت cancelled على المرجع الأصلي بعد تسجيل المحاولة | يلغي المحلي بشرط بقاء الالتزام وطلب العميل والهوية بلا تغيير. قد يقتصر سجل Google المحذوف على المعرف؛ الحساب والحدث مثبتان قبل الإرسال. |
| تراجع العميل أو تغير الطلب خلال التنفيذ | يحتفظ بالحالة غير المحسومة، حتى إذا لوحظ حذف الحدث. يحتاج تعارض الطلب مع الأثر الخارجي مراجعة النشاط؛ لا يعيد إنشاء الحدث تلقائيًا. |
| عامل توقف أو فُقد تأكيد حفظ محاولة الإلغاء | تبقى cancelling؛ بعد دقيقتين يتاح التحقق من المرجع بالقراءة فقط. |
| فشل أحد سجلي التدقيق بعد الحذف | يتراجع الإسقاط المحلي بالكامل، وتبقى المحاولة قابلة للتعافي بالقراءة. |
| فقد تأكيد الحفظ النهائي | يعيد الطلب النتيجة المحفوظة دون حذف أو تدقيق إضافي. |
| وصول رد قديم بعد تحقق أحدث أو تحققان متزامنان | إصدار السجل وبصمة الدليل يمنعان الكتابة القديمة من تجاوز النتيجة الأحدث. |

النتيجة تصف آخر أثر أو قراءة في التقويم الأصلي. لا تراقب هذه الدفعة نقل الحدث إلى تقويم آخر أو نسخه أو استعادته خارجيًا لاحقًا. لا تُعامل 404 أو 410 كدليل كافٍ لتحرير السعة.

## الواجهة والمخطط

لوحة AR/EN داخل إدارة الحجز تعرض المصدر والموعد وحالات المنع والتدقيق. التصديق والسبب يتجددان عند تغير الدليل، وتمنع النقرة المكررة وإعادة المحاولة العمياء بعد تعذر التحديث. تُعرض نصوص العميل والتدقيق كنصوص ملتفة دون تفسير HTML. لوحة المزامنة وقائمة الحالات تفهم حالات الإلغاء أيضًا.

ترحيل **0093_booking_calendar_cancellation.sql** يضيف سجل الإلغاء فقط؛ لا backfill أو تعديل للحجوزات القائمة. لا FK يمحو تاريخ الإلغاء عند حذف الحجز، مع بقاء سياسة حذف النشاط الحالية. فُحصت البصمة والفهارس ومنع تكرار الحجز والطلب على قاعدتي MySQL محليتين؛ [دليل الترحيل](./audits/sales-brain-implementation-2026-09-23/booking-cancellation-migration.json).

يلزم الترحيل وتحديث الويب والعمال ومسار الدفع معًا عند نشر منفصل. الكود القديم الذي لا يقرأ سجل الإلغاء لا يجوز أن يستمر بكتابة الحجوزات أو إصدار روابط دفع أثناء تفعيل المسار.

## المتبقي

- نقل موعد Google بموافقة جديدة وحفظ الفترتين عند الغموض.
- إلغاء الحجز المدفوع والرسوم والاسترداد وفروق السعر؛ جميعها تحتاج مسارًا ماليًا متكاملًا.
- تسوية طلب تغير أو انتهت حداثته بعد حذف خارجي، أو حدث ظل نشطًا/اختفى دون دليل كافٍ؛ لا مسار تلقائي لإعادة الإرسال أو تحرير الحجز بالقوة.
- طلبات الإلغاء العامة دون رقم أو بصيغ غير مدعومة، والروابط القديمة وسجل appointments والسياسات المتقدمة للموظفين والسعة.
- تجربة فعلية بالمزوّد، وقياس التحويل التجاري، وجهاز iPhone/Safari فعلي. الفحص الحالي محلي وChromium بواجهات API مصطنعة.

حالة الخطة **4 مكتملة / 55 جزئية / 12 لم تُغلق**؛ لا اعتماد 10/10. اختيار OpenAI/ZahyPi من السوبر أدمن وسقف 100 دولار يوميًا للمنصة كلها محفوظان.
