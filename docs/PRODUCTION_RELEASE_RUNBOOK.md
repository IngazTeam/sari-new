# Runbook نشر Sary إلى الإنتاج

لنشر `sary.live` استخدم مسار السيرفر الحالي أدناه، أو بوابة النشر العامة عند تجهيز بيئة جديدة. السكربتان القديمان مجرد wrappers إلى `scripts/deploy-production.sh`. كلا المسارين يبني إصدارًا منفصلًا ويستخدم migrations المسجلة، دون `git reset --hard` أو `db:push` أو بناء داخل النسخة التي تخدم المستخدمين.

## أمر واحد للسيرفر الحالي

بعد رفع التحديثات إلى `main`، نفّذ هذا السطر داخل جلسة root على `sary-app-droplet`:

```bash
cd /var/www/sari && test "$(git branch --show-current)" = main && git pull --ff-only origin main && bash scripts/update-sary.sh
```

هذا الأمر مخصص للإعداد الحالي: المصدر `/var/www/sari`، ملف البيئة `/var/www/.env`، مستخدم التطبيق `sari-deploy`، وNode `22.23.2` وPM2 داخل `/home/sari-deploy/.local/sari-runtime`. يظل المنفذ `3000` وإعداد Nginx الحالي كما هما. لا يُستخدم لتثبيت سيرفر جديد أو لتغيير إعدادات البنية التحتية.

يسحب الأمر `main` بطريقة fast-forward، ثم يتحقق أن الإصدار يطابق `origin/main`، وينشئ worktree منفصلة، ويثبت الحزم من lockfile، ويفحص TypeScript ويبني بحد ذاكرة Node قدره 4GB. يبقى التطبيق السابق يعمل أثناء التحضير. اختبارات البناء لا تتلقى أسرار الإنتاج. بعدها تؤخذ نسخة مشفرة حديثة لقاعدة البيانات وملف البيئة، وتُجرى فحوص النشر نفسها من `deploy-production.sh` قبل الترحيلات وبعدها. مفاتيح مزود الذكاء تُدار من لوحة السوبر أدمن ويستخدم النشر `preflight:ai-deployment`.

عند نجاح الترحيلات، يُفعّل `sari` و`sari-inbound` تحت `sari-deploy` مع التحقق من مجلد كل عملية وملف تشغيلها، ثم `/ready` وحفظ PM2. يفحص رمز إصدار فريدًا عبر الموقع العام والصفحتين العربية والإنجليزية، ولا يطبع `DEPLOY_OK` إلا بعد نجاحها. إذا فشل تفعيل التطبيق، يحاول إعادة الإصدار السابق؛ لا يعكس تغييرات قاعدة البيانات. فشل الفحص العام بعد نجاح الفحص المحلي يترك الإصدار الجديد عاملًا ويطبع `NEW_RELEASE_RUNNING_LOCALLY; PUBLIC_ROUTE_REQUIRES_ATTENTION`.

النسخ التلقائية في `/var/backups/sari-pre-migration-*`، ومفتاحها المستقل في `/var/lib/sari-backup/archive.key` بصلاحيات root فقط. يُنشأ المفتاح مرة واحدة ولا يتغير بين النشرات. لا يُطبع ولا تُطلب كلمة مرور في كل تحديث. احفظ نسخة منه خارج السيرفر منفصلة عن الأرشيفات؛ فقده يفقد القدرة على فك تشفيرها. يستخدم الأرشيف OpenSSL AES-256-CBC مع PBKDF2-SHA256 و200000 دورة، ويحتفظ بملف `SHA256SUMS`.

يتحقق المسار الحالي من فك تشفير الأرشيف وسلامة gzip وتطابق نسخة ملف البيئة؛ هذا **فحص أرشيف وليس اختبار استعادة قاعدة بيانات**. تظهر الحقيقة في `RESTORE_VERIFIED=NO`. نقل النسخ خارج السيرفر وتمارين الاستعادة مستقلان عن هذا الأمر؛ لا يُستعاد أي شيء فوق قاعدة الإنتاج أثناء التحديث. يتوقف الأمر إذا تعذر النسخ أو وجد جداول غير InnoDB أو مساحة قرص غير كافية. لا تُحذف نسخ أو إصدارات سابقة تلقائيًا.

كل تحديث جديد يحتاج مراجعة توافق migrations مع الإصدار السابق قبل رفعه إلى `main`؛ التراجع التلقائي للكود يفترض توافقها خلفيًا. نفّذ البوابات المطلوبة قبل الرفع، ولا تستخدم الأمر لنشر تغييرات غير مراجعة.

### الانتقال إلى هوية متجر زد — 0127

يتغير قيد هوية طلب زد في `0127`؛ لذلك لا يجوز أن يكتب إصدار قديم بالتزامن مع الإصدار الجديد، أو يعالج عامل تنبيهات قديم التنبيهات الجديدة. يوقف المُحدّث عمليتي `sari` و`sari-inbound` بعد البناء والنسخ الاحتياطي وقبل الترحيل عندما يفتقد الإصدار السابق علامة القدرة `zid-order-store-identity-0127`. ينتظر توقف العمليات وتصفير PID ويحفظ حالة PM2 المتوقفة. يتضمن هذا الانتقال انقطاع خدمة أثناء الترحيل والفحوص والتفعيل؛ النشرات التالية بين إصدارين متوافقين تحتفظ بمسار إعادة التحميل المعتاد. في بوابة النشر العامة تُفحص مجلدات عمليات PM2 الفعلية، لا رابط `current` وحده.

يفحص مسارا التفعيل والتراجع علامة القدرة قبل بدء أي إصدار. إذا فشل الترحيل أو التفعيل، لا يعيدان إصدارًا يجهل هوية المتجر. يُحتفظ بقاعدة البيانات والصفوف والمهام، ويُستكمل إلى إصدار متوافق باستخدام أمر المُحدّث نفسه؛ يقبل المُحدّث اكتشاف إصدار متوقف لإعادة المحاولة. لا تنفذ `pm2 resurrect` من نسخة محفوظة أقدم أو تعِد قيد التفرد السابق؛ بعد وجود الرقم نفسه في متجرين قد يفشل القيد أو يُفقد العزل. إذا أصبحت بيانات عمليات PM2 مختلطة أو تالفة، تُصلح هوية العمليات وفق سجل الإصدار قبل إعادة المحاولة. لا تطبع حالة التوقف أو نجاح البناء `DEPLOY_OK`.

العزل هنا يغطي زوج عمليات PM2 المُدارين على السيرفر الحالي. أي كاتب مستقل أو سيرفر إضافي خارج هذا الملف يجب إيقافه ضمن نافذة الانتقال أيضًا؛ لا توجد آلية توزيع متعددة الخوادم في المُحدّث الحالي.

### الانتقال إلى كتالوج زد بحسب المتجر — 0129

يتطلب `0129` أيضًا القدرة `zid-catalog-store-identity-0129` في علامة الإصدار، بجانب قدرة الطلبات السابقة. يطبق المُحدّث نفس إيقاف زوج PM2 القديم قبل الترحيل، ورفض تفعيل أو استعادة إصدار لا يملك القدرتين. تغيير هوية الكتالوج لا يصلح للتشغيل المختلط مع قارئ أو كاتب قديم؛ يشمل الانتقال انقطاعًا أثناء الترحيل والفحوص والتفعيل. لا تُعد قيد `merchant_id,zid_product_id` بعد تخزين منتجات تحمل المعرّف نفسه في متجرين.

تبقى منتجات زد التاريخية بهوية متجر فارغة دون حذف أو تغيير سعرها. القراءات الجديدة لا تعرضها للبيع، حتى لو تطابق اتصال اليوم مع اسم المتجر القديم؛ يلزم تشغيل مزامنة المنتجات للمتجر المتصل الموثق. تنشئ المزامنة مصدرًا وإسقاطًا جديدين بنطاق المتجر، وتحفظ الصفوف التاريخية. لا تُعد تلك الصفوف المخفية منتجات محذوفة، ولا تعِد تفعيلها بكتابة `store_id` يدويًا. إذا كانت إعدادات الاتصال لا تحفظ هوية متجر صحيحة، أعد ربط زد عبر المسار الموثق قبل المزامنة. عند فشل الانتقال احتفظ بالبيانات واستكمل إلى إصدار متوافق بأمر المُحدّث نفسه أعلاه.

### الانتقال إلى قبول الرد الصوتي — 0132

يتطلب `0132` القدرة `staff-voice-acceptance-0132` أيضًا في علامة الإصدار القائمة `scripts/zid-order-store-capability.json`. اتساع قيد مصادر القبول يغيّر عقد جاهزية عامل الرد النصي السابق؛ لا يصلح تشغيله مع المخطط الجديد أو استعادته تلقائيًا بعد الترحيل. تستخدم مسارات التحديث والنشر حارس القدرات القائم لإيقاف الويب والعامل القديمين قبل DDL، ورفض تفعيل أو استعادة إصدار بلا القدرات الثلاث. تبقى بيانات النص والتصعيد محفوظة. عند تعثر التفعيل يُصلح الإصدار المتوافق ويعاد تشغيل أمر التحديث المعتاد؛ لا تحذف سجلات الصوت ولا تُضيق القيد لإجبار rollback قديم. عقد طلب الصوت في الواجهة يحتاج تحديث الصفحة. هذا الانتقال يتضمن انقطاعًا أثناء الترحيل والتفعيل والتحقق.

### سجل مراجعات الفريق — 0133

يضيف `0133_staff_team_reviews.sql` جدول التدقيق `ai_sales_staff_reviews` فقط، دون تعديل بيانات المحاولات أو قيد قبول النقل. يتطلب المسار الإداري صلاحية `conversations.review` للمالك أو المدير، ويفشل إن غاب الجدول أو الفهرس الفريد. يطبق أمر التحديث المعتاد الترحيل قبل التفعيل. التغيير إضافي ومتوافق مع الإصدار السابق `de036bf2`؛ لا يحتاج انتقال قدرة جديدًا. عند التراجع احتفظ بجدول التدقيق وبياناته، ولا تحذف الإيصالات أو تعِد الإرسال لتجاوز مراجعة غير محسومة. اختبار القبول المحلي يشمل قاعدة جديدة حتى 134 ترحيلًا وترقية 0132 وإعادة DDL غير المسجل وحفظ البيانات، كما في [تقرير المراجعة الإدارية](./SARI_SALES_BRAIN_TEAM_REVIEW_2026-09-27.md).

### الانتقال إلى طلبات وكتالوج سلة — 0137–0139

تتطلب علامة الإصدار القائمة أيضًا `salla-order-store-identity-0137` و`salla-order-creation-0138` و`salla-catalog-store-identity-0139`. هذه عقود قراءة وكتابة، وليست مجرد وجود جداول: هوية الطلب والمنتج بحسب المتجر وسجل محاولة الإنشاء يجب أن تفهمها النسخة التي تستأنف العمل. الإصدار `68bc76b7` وما قبله لا يحمل العلامات الجديدة؛ يمنع الحارس الرجوع إليه تلقائيًا. لا تنقل العلامة يدويًا إلى كود قديم لتجاوز الفحص.

يفحص مسارا النشر المرشح أولًا ثم العمليات الفعلية لـPM2. وجود عامل قديم أو ملف تنفيذ لا يطابق مجلد إصداره يوجب إيقاف الزوج والتحقق من غياب PID حي وحفظ الحالة قبل الترحيل. فشل الإيقاف أو الفحص أو الحفظ يوقف النشر. التفعيل والتراجع يستخدمان حارس النسخة المعدّة للنشر، لا checkout متغيرًا ولا حارس الإصدار السابق. أول انتقال يتضمن انقطاعًا خلال الترحيل والفحوص والتفعيل؛ يبقى أمر السيرفر الكامل أعلاه صالحًا دون تغيير.

عند فشل الترحيل بعد الإيقاف استكمل إلى إصدار متوافق مع الاحتفاظ بالجداول والسجلات والعمليات المتوقفة. عند تعثر تفعيل جزئي افحص PM2؛ رفض الإصدار القديم لا يعني توقف كل عمليات الجديد. لا تُلغِ طلبًا أو تعِد POST لمجرد فشل النشر، ولا تحذف `salla_order_creations` أو إسقاطات الطلبات والمنتجات، ولا تختزل معرفاتها إلى أرقام غير مربوطة بمتجر. الحارس لا يسوّي محاولة `review` ولا يستعيد قاعدة بيانات. يلزم إيقاف أي كاتب مستقل خارج زوج PM2 ضمن النافذة نفسها.

بعد النشر شغّل «مزامنة كاملة» لكل اتصال سلة مستخدم لتوثيق المنتجات القديمة؛ مزامنة المخزون وحدها لا تنشئ الربط الأول. [تقرير الانتقال والاختبارات وحدودها](./SARI_SALES_BRAIN_SALLA_RELEASE_2026-09-27.md)، و[تفاصيل مزامنة الكتالوج](./SARI_SALES_BRAIN_SALLA_CATALOG_2026-09-27.md).

### آثار إنشاء طلب سلة — 0140

تضيف `0140_salla_creation_effects.sql` ثلاث مهام مستقلة مع حفظ الطلب: إشعار الإدارة وإشعار التاجر وSheets. لا تُولّد مهام للطلبات القديمة؛ لا يمكن معرفة ما أُرسل منها بأمان. يتطلب المخطط الجدول والفهرس والقيد قبل تشغيل التطبيق. القدرة الجديدة `salla-creation-effects-0140` تمنع تشغيل أو استعادة إصدار لا يفهم سجل الآثار، بما فيه `8052b440`. يوقف المُحدّث الزوج القديم قبل الترحيل ويتضمن الانتقال انقطاعًا أثناء الفحوص والتفعيل؛ يبقى أمر السيرفر الكامل أعلاه كما هو.

عند الفشل احتفظ بالمخطط والمهام واستكمل بإصدار متوافق؛ لا تعدّل العلامة أو تعِد مهمة `review` إلى `pending`. العامل يستأنف التحضير الآمن فقط؛ علامة الإرسال تعني احتمال وجود أثر خارجي ولو غاب إقراره. `accepted` قبول من الموصل وليس إثبات قراءة المستخدم أو نجاح كل قنواته. راقب الحالات المجمعة وافحص إعدادات القنوات؛ غياب القناة أو رجوع نتيجة غير مؤكدة يسجل للمراجعة بدل ادعاء التسليم. تفاصيل الاستعلام والقيود والاختبارات في [تقرير آثار الإنشاء](./SARI_SALES_BRAIN_SALLA_EFFECTS_2026-09-28.md).

## بوابة النشر العامة

## شروط البدء

1. يجب أن يكون commit المطلوب هو `origin/main` حرفيًا، وأن تكون بوابتا GitHub Actions خضراوين.
2. تؤخذ نسخة قاعدة بيانات مشفرة، ثم يُثبت restore فعليًا أو يُراجع أحدث تمرين صالح. لا يكفي نجاح أمر النسخ وحده.
3. يراجع المشغل نتائج preflight وهجرة البيانات التاريخية والتكاملات النشطة. أي عدد غير صفري أو اعتماد غير مشفر يوقف التفعيل.
4. لا تُستخدم مفاتيح Tap أو Meta أو Green الحية في canary الأول. يبدأ الاختبار بمفاتيح sandbox ومتجر داخلي ثم عميل تجريبي موافق.
5. ملف الأسرار خارج Git، قابل للقراءة لمستخدم النشر، وغير قابل للوصول إلى `other` على النظام.
6. ملف build مستقل لا يحتوي إلا مفاتيح `VITE_*` العامة المقصود تضمينها في المتصفح. لا تضع فيه DB أو tokens أو server secrets.

## متغيرات التشغيل

لا تضع القيم الحساسة في سجل الأوامر أو التقرير. جهزها في جلسة النشر من secret manager:

```text
SARI_RELEASE_SHA=<full-40-char-origin-main-sha>
SARI_SOURCE_DIR=<read-only-source-checkout>
SARI_RELEASE_ROOT=<dedicated-release-directory>
SARI_ENV_FILE=<absolute-shared-env-file>
SARI_BUILD_ENV_FILE=<absolute-public-vite-only-env-file>
SARI_PUBLIC_ORIGIN=https://sary.live
SARI_READY_ORIGIN=<https://sary.live-or-http://127.0.0.1:production-port>
SARI_BACKUP_ID=<verified-backup-reference>
SARI_BACKUP_VERIFIED_AT=<ISO-8601-within-60-minutes>
SARI_DEPLOY_CONFIRM=deploy-sary-production:<same-sha>
SARI_SCHEMA_CONFIRM=migrate-sary-production:<same-sha>
DATABASE_URL=<from-secret-manager>
```

ثم شغّل `bash scripts/deploy-production.sh` كمستخدم النشر غير root.

`SARI_READY_ORIGIN` لا يغير النطاق العام. هو عنوان probe للإصدار الذي بدأه PM2، ويقبل فقط
النطاق العام نفسه أو loopback صريحًا. يُستخدم loopback عند الانتقال من مشغل قديم إلى مستخدم نشر
مقيد، ثم يُحوّل Nginx إلى المنفذ الذي اجتاز readiness الصارمة.

## ما تنفذه البوابة

```text
flock واحد للنشر
→ fetch origin/main دون reset للمصدر
→ worktree معزولة بالـSHA المطلوب
→ ربط ملف VITE العام فقط وحذف DATABASE_URL/RUN_MYSQL_INTEGRATION من بيئة الاختبار
→ pnpm frozen install + audit + type-check + release tests + schema check + build
→ تبديل رابط البيئة داخل الإصدار إلى ملف runtime السري
→ preflights القديمة وcampaign 0042/0043/0044 قبل migration
→ إيقاف الكتاب والعمال المدارين إذا افتقد إصدارهم قدرات المخطط المطلوب
→ drizzle migrations المسجلة
→ postflights للمخطط والتكاملات والحملات
→ PM2 startOrReload مع wait_ready من كل worker
→ GET /ready ويجب أن يثبت database=connected وschema=current
→ تبديل symlink current ذريًا وتسجيل SHA/backup ID بلا أسرار
```

الإصدار القديم يبقى عاملًا أثناء التحضير. يستمر أثناء الترحيل فقط إذا اجتاز حارس توافق القدرات؛ انتقالات 0127 و0129 و0132 و0137–0140 من إصدار غير متوافق توقفه قبل DDL كما سبق. لا يبدأ الإصدار الجديد أي cron أو outbox worker قبل نجاح اتصال DB وعقد المخطط الكامل. عدد workers الافتراضي اثنان، والحد الأعلى أربعة لحماية ميزانية اتصالات MySQL.

## الفشل والتراجع

- الفشل قبل إيقاف الكتاب غير المتوافقين يترك التطبيق القديم كما هو. بعد إيقافهم يبقون متوقفين إذا لم يجتازوا حارس القدرات؛ يستكمل المشغل إلى إصدار متوافق.
- الفشل بعد محاولة PM2 يحاول إعادة تحميل الإصدار السابق إذا كان معروفًا ومتوافقًا مع حارس القدرات؛ لا يتجاوز الحارس لإعادة الخدمة بإصدار قديم.
- migrations لا تُحذف تلقائيًا ولا يُنفذ schema rollback من السكربت. التراجع التلقائي للكود يفترض أن migrations توسعية ومتوافقة خلفيًا؛ خلاف ذلك يجب إيقاف النشر قبل migration واستخدام خطة استعادة معتمدة.
- لا تحذف worktree الفاشلة قبل حفظ logs ونتائج preflight ورقم النسخة. تنظيف الإصدارات القديمة عملية منفصلة ومراجعة الهدف إلزامية.

## إثبات ما بعد النشر

إضافة `0134_ai_price_revisions`: شغّل المُحدّث المعتاد؛ الجدول توسعي ولا يعيد تسعير الحجوزات أو تغيير السقف اليومي 100 دولار. أوقف تعديل الأسعار من المشرفين أثناء انتقال الخادم والواجهة، ثم أعد تحميل الإعدادات قبل الاعتماد. كل تعديل جديد يحتاج إصدارًا غير مستخدم ومرجع اعتماد؛ تؤرشف البطاقة القديمة عند أول تعديل دون اختراع صاحبها أو تاريخها. لا تستبدل الأسعار بـSQL مباشر أو سكربت الإصدار القديم، لأنهما يتجاوزان التدقيق. عند الرجوع إلى كود قديم احتفظ بالسجل وراجع أي اختلاف قبل استكمال إدارة الأسعار. تفاصيل الحفظ والاستعادة والـCLI في [تقرير إصدارات الأسعار](./SARI_SALES_BRAIN_PRICE_REVISIONS_2026-09-27.md). لا يعتبر نجاح الترحيل أو البناء نشرًا مكتملًا؛ الإثبات يبقى `DEPLOY_OK`.

1. افحص `/health`؛ يجب ألا يعرض سوى الحالة العامة. افحص `/ready`؛ يجب أن يعيد `database=connected` و`schema=current`.
2. تحقق من SHA المنشور ومن أن PM2 لا يعيد التشغيل في حلقة، ثم راقب 5xx وp95 وDB pool وoutbox backlog وmanual review مدة 30 دقيقة.
3. نفذ tenant A/B للقراءات والكتابات، ثم Tap test، ثم webhook replay، ثم campaign opt-in/withdrawal على sandbox.
4. ابدأ canary بمتجر داخلي. لا توسع إلى العملاء التجريبيين قبل 24 ساعة بلا P0 أو drift أو رسائل مكررة.
