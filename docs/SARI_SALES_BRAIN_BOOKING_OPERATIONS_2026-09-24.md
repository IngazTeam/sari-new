# حماية عمليات الحجز من تجاوز الحقيقة المالية

التاريخ: 24 سبتمبر 2026. امتداد لخطة مخ ساري والمبيعات بعد `cf180fe`. هذه الدفعة تخص تنفيذ الاتفاق وحفظ الأدلة المرتبطة بالحجز، ولا تقيس جودة إقناع النموذج أو التحسن التجاري.

## الخلل الذي أُصلح

كان مسارا تعديل الحجز يقبلان `paymentStatus` مباشرة من المتصفح، ويسمح المساعد القديم بتحديث غير مقيد بسياق التاجر والفاعل. وكان الحذف المباشر قد يمحو محاولات الحجز المرتبطة به أو يفصل مدفوعاته عن أصلها. في الواجهة، كان مجرد تغيير اختيار الحالة يرسل التعديل فورًا.

أصبح التعديل التشغيلي منفصلًا عن تسوية الدفع. لا يُقبل تغيير المبلغ أو حالة الدفع أو التاجر أو هوية الفاعل أو توقيت التنفيذ أو هوية التقويم الخارجي داخل طلب التعديل. أُغلق المساران، المركب في `appRouter` والمستقل، مع المساعدات القديمة في قاعدة البيانات. صُحّح كذلك استخراج معرّف الحجز من نتيجة إدخال MySQL الفعلية، واختُبرت قراءته وقائمة الحجوزات والإحصاءات عبر ORM.

## السلوك بعد الإصلاح

| المسار | السلوك المحمي |
|---|---|
| تحديث حالة التنفيذ | يحتاج `orders.manage` وعضوية التاجر وهوية الجلسة، وحالة متوقعة ومعرف عملية. انتقالات مسموحة محددة، دون إعادة فتح حجز ملغى أو مكتمل أو مسجل كعدم حضور. |
| حالة الدفع | تبقى تحت سلطة تسوية الدفع الموثقة. التأكيد اليدوي لا يثبت تحصيلًا ولا يسجل نتيجة شراء للتعلّم. |
| إلغاء الحجز | يحفظ الحجز ومحاولاته ودفعاته وسجل إلغائه، ويعطل روابطه المحلية داخل المعاملة نفسها. التحصيل المتأخر يسجل كدفع دون إعادة فتح الحجز. |
| حذف مسودة | مسموح للحجز المعلق أو الملغى غير المستخدم فقط؛ يُرفض عند وجود أي رابط، محاولة، دفعة، حالة مالية، تأكيد أو إكمال سابق، تقييم، أو ربط بتقويم خارجي. يبقى سجل الحذف بعد زوال المسودة. |
| التكرار والتعارض | معرف عملية فريد لكل تاجر وبصمة تشمل الفاعل والطلب. التكرار المطابق يرجع النتيجة دون أثر جديد؛ تغيير الفاعل أو البيانات أو الحجز بنفس المعرف يُرفض. الحالة القديمة تُرفض أيضًا. |
| حفظ التدقيق | التعديل أو الحذف وسجله معاملة واحدة؛ فشل التدقيق يتراجع عن التعديل وتعطيل الروابط. فقد تأكيد `commit` لا يترك اتصالًا مشكوكًا فيه في المسبح، وإعادة الطلب تستعيد النتيجة. |
| إعادة جدولة قائمة | فحص الموظف والتاجر والخدمة والتعيين والمدة والتداخل؛ يمنع تغيير موعد له تاريخ مالي أو تقويم خارجي أو حالة تنفيذ نهائية. قفل الخدمة يسلسل التعديلات على الخدمة نفسها. |
| واجهة الإدارة | اختيار الحالة ثم زر حفظ صريح، ورسائل عربية وإنجليزية، وسجل آخر 20 إجراء بهوية الموظف والحالة قبل وبعد. الحذف داخل التفاصيل مع تصديق، وتحديث الدليل بعد النجاح أو الفشل. |

السجل يحفظ الحالة التشغيلية والمالية والموعد والمبلغ ومراجع التاجر والحجز والفاعل والحقول المتغيرة. لا يحفظ هاتف العميل أو نص ملاحظاته أو سبب الإلغاء؛ عرض السجل لا يكشف محتوى JSON الداخلي. ليس هذا سجل نسخ كاملًا لنصوص الملاحظات.

إلغاء الحجز **لا يلغي عملية بدأت لدى Tap ولا ينفذ استردادًا**. إظهار «ملغى» مع «مدفوع» ممكن عند وصول تحصيل متأخر، ويجب التعامل معه كتاريخ مالي حقيقي يحتاج الإجراء التجاري المناسب.

## التحقق

شُغلت الفحوص على نسخة مستقلة من Git index، وطوبقت **250 بصمة Git blob** مع ملفات الكوميت. مصدر الحقيقة هو [ملف الأدلة](./audits/sales-brain-implementation-2026-09-23/evidence.json)، لا SHA الأساس وحده.

|---|---|
| اختبارات فريدة بعد إزالة التكرار بين التقارير | **4566 ناجحة، صفر فشل وصفر تخطٍ** |
| مجموع التقارير قبل إزالة التكرار | 5626 نتيجة ناجحة: وحدة 760، قاعدة بيانات 1045، انحدار 1017، مبيعات قديمة 229، ميزانية 11، أمان 2564 |

| واجهة المكونات الفعلية | **291 سيناريو ناجح، 34 لقطة، صفر أخطاء متصفح**؛ منها 26 سيناريو جديد لعمليات الحجز |

| الترجمة | 6078 استدعاء و242 مفتاحًا ديناميكيًا؛ لا مفاتيح مفقودة أو أخطاء interpolation أو مفاتيح ديناميكية غير محلولة |
| المخطط والترحيل | `drizzle-kit check` ناجح؛ الترحيل 0084 مثبت ومطابق على قاعدتي الاختبار |

راجعت بصريًا لقطتي المكوّن بالعربية بعرضي 375 و1440، وتتحقق السيناريوهات آليًا من عدم التجاوز الأفقي وارتفاع عناصر التحكم 44 بكسل على الأقل. تُحفظ النتائج واللقطات في [دليل الواجهة](./audits/sales-brain-implementation-2026-09-23/ui/results.json).

ملفات القبول الجديدة:

- `server/booking-operations.mysql.test.ts`: MySQL فعلي، مع Tap مصطنع؛ معاملات وإعادة محاولة وعزل وتراجع وسباقات دفع وحذف.
- `server/booking-operations-pentest.test.ts`: استدعاء المسارين الفعليين بحالات صلاحيات ومدخلات عدائية، والتحقق من رفض تغيير السلطة المالية وحجب الأخطاء الداخلية.
- `scripts/testing/verify-sales-brain-ui.cjs`: المكوّن الفعلي بواجهات API مصطنعة؛ العربية والإنجليزية وعروض 320 و375 و390 و768 و1440، والحفظ الصريح والتصديق والتعارض والفشل والتحديث.

الفحص الأمني هنا محلي وسلوكي. لا يُعد اختبار اختراق إنتاجي مستقلًا، ولا تجربة على iPhone أو Safari فعليين. لا رسائل عملاء أو تحصيل حقيقي أو استدعاءات AI حية في هذه الدفعة.

## الترحيل والتشغيل

أضيف `0084_booking_operation_audits` بعد 0083، دون تعديل الترحيلات السابقة أو حالات الحجوزات أو مبالغها. طُبق على قاعدتي MySQL محليتين، وطوبقت بصمته وسجل الترحيل والقيد الفريد للتاجر ومعرف الطلب. لا يوجد FK من مرجع التدقيق إلى الحجز، حتى لا يُمحى السجل عند حذف مسودة مسموحة؛ يبقى ارتباطه بالتاجر قائمًا.

يلزم تطبيق الترحيل في الإنتاج وتحديث الويب والعمال معًا قبل استخدام المسارات الجديدة. يفحص المسار جاهزية المخطط ويرفض العمل عند نقصه. لم يُنفذ نشر أو ترحيل إنتاجي.

## ما بقي مفتوحًا في الخطة

- إنشاء الحجز القديم لا يشارك بعد معاملة حجز سعة موحدة؛ لا ضمان شامل لمنع ازدواج الموعد بين الإنشاء والتعديل، أو بين خدمات مختلفة تشترك في الموظف نفسه.
- صفحة قراءة الحجوزات وإنشاؤها كاملة ما زالت مرتبطة بالمالك؛ صلاحيات الإجراءات الجديدة لا تعني اكتمال رحلة الفريق كلها.
- اتفاق حجز محفوظ داخل محادثة البيع، بموافقة العميل على الخدمة والوقت والمبلغ، لم يُستكمل بهذه الدفعة.
- مراجعة الروابط العامة والتاريخ القديم، وتوحيد الآثار في التكاملات الخارجية، والاسترداد المالي التشغيلي ما زالت مفتوحة.
- بوابات جودة المزوّد الحي والتقييم البشري والتحسن التجاري والنشر المحدود ما زالت تحتاج أدلتها.

حالة البنود تبقى **4 مكتملة، 55 جزئية، و12 غير مغلقة**. حُدّثت أدلة B035 وB037 وB057 وB064 وB065 دون ترقيتها إلى اكتمال غير مثبت. اختيار OpenAI أو ZahyPi من السوبر أدمن وسقف المنصة المشترك **100 دولار يوميًا** لم يتغيرا.
