# توحيد سعة المواعيد وحماية مزامنة التقويم

التاريخ: 24 سبتمبر 2026. استكمال لخطة مخ ساري بعد `a19e452`. تغطي هذه الدفعة التعارض بين `appointments` و`bookings` وسلامة إنشاء وإلغاء حدث Google. لا تعني اكتمال خطة المبيعات أو اعتماد 10/10.

## النتيجة

كان مسار واتساب ومسارا التقويم يكتبان في `appointments` بينما إدارة الحجوزات والدفع تستخدم `bookings`. كل سجل يفحص نفسه، وبذلك كان يمكن قبول موعد وحجز للموظف نفسه في الوقت نفسه. وكان التقويم ينشئ حدث Google قبل الحفظ المحلي، ثم يلغي الحجز محليًا حتى عند فشل حذف الحدث الخارجي.

أصبح السجلان يستخدمان معاملة وقفل السعة نفسه لكل تاجر. لا يعاد نسخ السجلات ولا حذفها؛ قراءة التعارض تشمل السجلين. تستمر حماية الدفع والتعديل التشغيلي والتدقيق الموجودة في الدفعات السابقة.

| استبعاد الحجز الجاري تعديله | لا يُستبعد موعد قديم يحمل الرقم نفسه؛ هوية الاستبعاد منفصلة لكل جدول. |
| خدمة أو موظف لتاجر آخر أو معطل أو خارج إسناد الخدمة | يرفض قبل الحفظ أو الاتصال بالمزوّد. |
| تاريخ غير حقيقي أو وقت خاطئ أو عبور منتصف الليل | يرفض؛ النهاية مشتقة من مدة الخدمة المحفوظة، وليست من بيانات العميل. نهاية 24:00 تحتاج دعم مواعيد عابرة للأيام ولم تعد مقبولة ضمن عقد اليوم الواحد. |

| إلغاء أو اكتمال أو عدم حضور محلي | يحرر السعة دون حذف تاريخ الموعد؛ الإلغاء الخارجي له الشروط التالية. |

مسارا API المركب والمستقل يستخدمان إجراءات مشتركة، وصلاحية `orders.manage` للإنشاء والإلغاء، وهوية التاجر من العضوية. لا يقبلان تمرير حالة أو هوية تاجر أو نهاية وقت أو معرف حدث أو حالة مزامنة. أزيلت مساعدات التعديل والإكمال وعدم الحضور غير المستخدمة التي كانت تكتب بالمعرف وحده دون نطاق تاجر أو بروتوكول سعة؛ لا يوجد لها مستدعٍ إنتاجي في المستودع. مساعدا الإنشاء والإلغاء الباقيان يمران بالبروتوكول المحمي.

## مزامنة Google

الحجز المحلي يسبق الاتصال الشبكي. عند وجود تكامل نشط، تُحفظ حالة الإرسال ومرجع التكامل والتقويم وبصمة اعتماد الحساب داخل معاملة الحجز، ثم تُحرر أقفال SQL قبل الاتصال. لا يضاف تخزين جديد لنص المفاتيح السرية.

| حالة المزامنة | المعنى والتصرف |
|---|---|
| `none` | حجز محلي؛ لا طلب Google. يمكن إلغاؤه محليًا. |
| `creating` | حُفظت نية الإنشاء قبل الاتصال. تعطل العملية أو فقد تأكيد الحفظ لا يسمح بإعادة POST تلقائيًا. |
| `create_unknown` | لم يثبت معرف الحدث؛ قد يكون المزوّد أنشأه. الموعد محجوز محليًا، ولا يعاد الإنشاء أو الإلغاء آليًا. |
| `synced` | حُفظ معرف الحدث؛ الإلغاء يحتاج التكامل والتقويم وبصمة الاعتماد الأصلية. |
| `cancelling` | حُفظت نية الإلغاء، وتظل السعة مشغولة أثناء DELETE. |
| `cancel_unknown` | لم يتأكد الإلغاء الخارجي؛ تظل الحالة التشغيلية والسعة محفوظتين ولا يعاد DELETE تلقائيًا. |
| `cancelled` | أكد المزوّد الحذف، ثم حُفظ الإلغاء المحلي. التكرار يعيد نجاحًا دون اتصال إضافي. |
| `legacy` | سجل قديم يحمل معرف Google دون دليل محفوظ على حسابه وتقويمه؛ لا يخمن النظام الهدف من الإعدادات الحالية. |

إن تعذر الحفظ بعد تأكيد المزوّد، تبقى الحالة السابقة حاجزًا محافظًا. وإن تم الحفظ وفقد تأكيد `commit`، يتلف اتصال SQL المشكوك فيه؛ الاختبار يثبت أن إعادة الطلب لا ترسل حدثًا جديدًا. لا ندعي وجود معاملة موزعة أو تنفيذ خارجي مرة واحدة مضمون.

استجابة الإنشاء تفرق بين نجاح **الحجز المحلي** وحالة المزامنة. قائمة المواعيد تكشف `calendarSyncState` وتستبعد بصمة الاعتماد ومرجع التكامل والهدف الداخلي. فشل الإلغاء يرجع خطأً يوضح أن السعة لم تُحرر. لا تتغير المبالغ أو الدفع أو ذاكرة نجاح البيع.

**حد تشغيلي باقٍ:** لا توجد في هذه الدفعة واجهة أو مهمة استرداد لحالات `unknown` و`legacy` وعمليات `creating/cancelling` المتوقفة. يلزم بناء مراجعة بهوية فاعل ودليل مزوّد وتدقيق قبل تحريرها. لا تغيّر الحالة يدويًا ولا تعاود POST/DELETE اعتمادًا على المهلة وحدها. تغيير الحساب أو التقويم أو حذف الربط القديم يمنع الإلغاء الآلي إلى حين تلك المراجعة. قد يؤدي هذا التحفظ إلى بقاء موعد محجوز حتى التحقق.

## اقتراح المواعيد

الفترات المعروضة مصدرها الفترات المسجلة فقط؛ لا اختراع لدوام 9–5. تستبعد شغل الموظف والخدمة في السجلين حتى عند قدم عداد الفترة، وتطابق مدة الخدمة عند اقتراح موعد التقويم. القراءة تظل إرشادية ويعاد فحص السعة عند الحفظ.

عند ربط Google، تقرأ جميع صفحات الأحداث قبل عرض التوفر، وتحسب اليوم بوقت الرياض صراحةً، وتراعي الأحداث طوال اليوم، وتتجاهل الأحداث الملغاة أو المعلنة غير حاجزة للوقت. النتيجة غير المكتملة أو توقيت الحدث غير الصالح يمنع الادعاء بالتوفر. يستند عقد الصفحات والحدود الزمنية إلى [مرجع events.list](https://developers.google.com/workspace/calendar/api/v3/reference/events/list)، ودلالات اليوم الكامل والشفافية إلى [مرجع Events](https://developers.google.com/workspace/calendar/api/v3/reference/events). التحقق محلي بمزوّد مصطنع؛ لم يُستخدم حساب Google حي.

لا تمنع هذه القراءة مستخدمًا خارجيًا من إضافة حدث لاحقًا في Google، ولا تفرض بعد سياسة الدوام والعطل والفواصل على جميع الكتابات اليدوية. الحساب الحالي يفترض توقيت الرياض، وليس نظام مناطق زمنية متعددًا لكل تاجر.

## الترحيل والنشر والمتبقي

الترحيل `0086_appointment_calendar_sync` مطبق ومطابق على قاعدتي MySQL محليتين. بصمة SQL الخام المطابقة لسجل الترحيل: `62f2dbe07274a7388f95036763772cbe4f4353d0997e21691bfb7d495e6a5164`. أضيفت أعمدة المزامنة وفهرس `(merchant_id, appointment_date, status)`، وصُنفت السجلات ذات معرف الحدث القديم `legacy` دون تعديل معرفها أو تاريخها أو حالتها. اختُبرت تعبئة ثلاثة سجلات قديمة لكل قاعدة داخل جدول مؤقت، دون تعديل الجداول الفعلية أثناء هذا الفحص. لم تتغير حالات الدفع. يفشل إنشاء أو إلغاء موعد عند غياب المخطط المطلوب.

قبل نشر هذه الدفعة يلزم إيقاف الكتابات القديمة، وتطبيق الترحيل، وتحديث جميع نسخ الويب والعمال معًا، وفحص التعارضات القديمة وأحداث Google ذات الحالة `legacy`. لا يصح ضمان القفل إذا بقي كاتب قديم خارج البروتوكول. لم يُنفذ نشر أو ترحيل إنتاجي.
